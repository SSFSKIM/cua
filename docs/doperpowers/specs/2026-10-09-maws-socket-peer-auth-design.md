## Purpose

MAWS serves cua's browser primitives on one Unix socket per app session, `<userData>/browser/cua/<appSessionId>.sock`, and cua's host connects to it from inside `cua serve` (P1 A-51, A-52; the cua spec `2026-10-08-maws-in-app-browser-design.md`, "Session authorization"). That host then re-serves the same primitives to the vendor browser service on a relay socket of its own, `$CUA_HOME/chrome/m/<name>-<pid>.sock`. Neither socket checks who connects: a 0700 directory and a 0600 file are the whole boundary, and both are satisfied by every process running as the owner. Any such process that names either path gets the full primitive set the moment it connects, before a byte is read, and that set reaches every tab of the session, the owner's imported Chrome profile partition included (the tracker's E13 row, `docs/tech-debt-tracker.md:111`, records that one site's cookies at a time are readable through request events by such a client). Both paths are discoverable: the MAWS directory is listable, and cua publishes each live relay's pid and instance id in `$CUA_HOME/chrome/b/*.json`.

This initiative makes both sockets refuse every peer that is not a process of the tree they serve. The kernel is the only witness that cannot be forged from user space: it knows the peer's pid and uid, and the process table knows each process's parent and start time. MAWS's socket accepts a peer that runs as MAWS's user and descends from that session's engine process. cua's relay accepts a peer that runs as the same user and descends from the `cua serve` (or `cua profiles list`) process that opened it, which is exactly where the vendor service and the trusted worker come from. Between them the two checks refuse other applications, other sessions, Terminal clients and any connection made while nothing legitimate is running.

The boundary, stated plainly so nobody reads more into it. A peer is accepted by where it sits in the process tree, not by what it is. So a process the session's engine started (the model's Bash command among them) is accepted by MAWS, and a process `cua serve` started is accepted by the relay; what those can do is bounded by the rules MAWS enforces on every peer alike (the cookie-jar refusals, internal tabs out of reach, the takeover hold), so they do nothing the model cannot already do through cua's tools. Further, the engine starts with `--setting-sources user,project,local` and without `--strict-mcp-config` (`src/engine-host/launch.ts:41,53`), so a same-user process that writes a hook or an MCP server into `~/.claude/settings.json` or a project's `.claude/settings.local.json`, or edits the user-writable plugin files, gets its own code started as an engine descendant and is accepted. Two more same-user routes need no configuration write, and the spec names them rather than pretending the tree is sealed. (a) `cua serve` is a stock `node` process; a same-user `kill -USR1` opens Node's inspector on 127.0.0.1:9229 and lets the sender run code inside it, which is a descendant on MAWS's socket and the root itself on the relay. This one is closed here: the plugin starts the shim with `--disable-sigusr1` (M3), and the executor checks whether MAWS's main process answers SIGUSR1 the same way (M2) and records the answer. (b) MAWS's supervisor socket is guarded by a 0600 token file (`src/engine-host/detached.ts:216-223`) that any same-user process can read and use to take over the supervisor and the session's real engine; that is a MAWS-wide question outside this spec and goes into the tracker row. The check therefore stops a same-user process that neither modifies what the engine executes nor takes over the processes that already have access: other applications and casual or drive-by clients, not an attacker who can rewrite the owner's Claude Code configuration or read MAWS's own token files. That residual is accepted and written, in these words, into the tracker row (amended, not closed) and into the A-52 amendment.

## Facts this design rests on

1. **MAWS speaks first.** On accept, `CuaConnection`'s constructor sends the `hello` notification at once (`src/main/browser/cua/connection.ts:143`); the client sends no hello and no credential (cua `src/chrome/host.mjs:750`, `runHost` waits for the peer's hello). Every message after that is a primitive request. MAWS's check must run on accept, before `CuaConnection` exists, with the socket not yet read: Node starts reading an accepted socket at once unless the server is created with `pauseOnConnect: true`.
2. **The MAWS socket and its directory.** `startCuaBackend` creates `<userData>/browser/cua` 0700 and sweeps `*.sock` at start (`src/main/browser/cua/index.ts:76-79`); `listen()` creates the server and listens (`index.ts:90-99`); the socket file gets no `chmod` (the supervisor socket does, `src/engine-host/detached.ts:198`). Several connections per socket are expected and unlimited (`index.ts:68-72`). `closeSession` and `dispose` (`index.ts:101-105, 170-176`) know only constructed connections.
3. **cua's relay.** In client mode, `connector()` (`src/chrome/client-mode.mjs:48-96`) dials MAWS and runs `runHost` (`host.mjs:699`), which listens at `$CUA_HOME/chrome/m/<socketNameFor(path)>-<pid>.sock` (`createServer` at `host.mjs:763-788`, directory 0700, file 0600, no check of the peer) and forwards `createTab`, `attach`, `executeCdp`, `getUserTabs`, `claimUserTab` and the rest to MAWS with whatever `session_id` and `turn_id` the client supplies (`host.mjs:318-513, 633-640`). Its legitimate clients are the vendor service and the trusted worker that the same `cua serve` process launches (`src/runtime/launch.mjs`), which find it through `BROWSER_USE_BACKEND_PATHS`. `cua profiles list` runs the same host in the CLI process only to collect the hello (`src/cli.mjs:578-587`); it closes its relays before the inventory launch, so nothing legitimate ever connects to those (the check there is harmless and uniform). The status file `chrome/b/<name>.json` publishes the pid (`src/profiles/checks.mjs:95-110`). The Chrome-route host, launched by Chrome through native messaging, serves the same socket shape to a vendor service that is not its descendant; it stays outside this spec (its trust model is cua's Chrome spec's, Decision Log).
4. **A token would not be a secret.** The MAWS path reaches the engine as `extraSettings.env.CUA_BROWSER_BACKENDS` (`src/main/sessions/launch-mapping.ts:70`), serialised into `--settings <JSON>` on the engine's argv (`src/engine-host/launch.ts:208`), journaled verbatim (X8) and readable by any same-user process through `ps`; environment variables are readable the same way (`ps -E -p <pid>` on this Mac prints another same-user node process's environment, checked 2026-10-09). The vendor service, as a client, presents nothing cua could add. A token is rejected (Decision Log).
5. **Node exposes no peer credentials.** `net.Socket` has no pid or uid for a Unix-domain peer and the libuv `Pipe` handle has no `getsockopt`; the accepted socket's descriptor is `socket._handle.fd` (a prototype getter; valid under Electron 44.4.5's Node 24.21.0 and under Node 22.23.2). Nothing in either repository's `node_modules` provides `LOCAL_PEERPID`, `getpeereid` or `SO_PEERCRED`.
6. **What the kernel reports, and its edges** (checked empirically by the spec's review, 2026-10-09). `getsockopt(fd, SOL_LOCAL, LOCAL_PEERPID)` reports the pid of the process that last operated on the peer socket, not the one that connected: a descriptor passed to another process and used there reports the new holder. A pid is reusable once its process exits. `proc_pidinfo(pid, PROC_PIDTBSDINFO)` gives `pbi_ppid` and the start time `pbi_start_tvsec/tvusec`, which together identify a process instance; it returns 0 for a gone pid. On macOS an orphan's ppid becomes 1 at once (`sh -c '(node … &)'` yields ppid 1).
7. **The Codex desktop app's check** (`authorizeSocketPeer`, native addon `browser-use-peer-authorization.node`, `main-BvBtZhys.js:18774-18842` in the 26.928.40906 readable build) reads `LOCAL_PEERTOKEN`, converts the audit token to a pid, walks `proc_pidinfo` ppids up to 64 levels until it meets the Electron main process, and then requires the peer, its parent and its grandparent to carry its team's code signature. The ancestry half transfers; the signature half does not (cua is an unsigned node script, the engine an Anthropic-signed binary). Codex fails closed when the addon is missing.
8. **MAWS's engine is not a child of MAWS's main process.** The default engine host is a detached supervisor that outlives the app (`src/main/hosts/detached-transport.ts:391-418`); the engine is its child (`src/engine-host/transport.ts:167`). Main receives the engine pid with every `session.status` event (`EngineSessionStatusSchema.pid`, `src/shared/engine/status.ts:19`), the event that opens the socket today (`src/main/browser/index.ts:191-193`, inside `if (status.process !== 'exited' && knownSession(...))`), and an engine that outlived a main restart reports it with its first status (D-16). When the supervisor is lost, main emits no `session.status` for its sessions (`src/main/hosts/supervisor.ts:398-436`) and the engines die of stdin EOF; one live engine per app session (`src/engine-host/launcher.ts:72`).
9. **Native pieces already present.** MAWS: `node-pty` (an N-API prebuild loaded from beside the asar), the Swift dictation helper built by `scripts/build-voice-helper.sh` into `build/voice-helper`, shipped through `extraResources` and located by `helperPath()` (`src/main/voice/helper-backend.ts:26-29`). cua: none; it ships plain JS with no build step (`package.json` `files`, the plugin runs `node ${CLAUDE_PLUGIN_ROOT}/cua-shim.mjs` straight from the checkout), one dependency `ws`. `clang` and `xcrun` are present on the owner's Macs. The review built the addon as this spec describes and loaded it under Node 22.23.2 and under Electron 44.4.5 run as Node.
10. **The e2e fake host** (`e2e/browser-cua.spec.ts`, `test/support/cua-fake-host.ts` with a 5 s hello timeout) connects from the Playwright test process, which descends from no engine; the e2e sessions open their sockets through `socketPathFor` without an engine (`browser-cua.spec.ts:83`), and the restart scene (`:281`) relaunches the app. Under `MAWS_E2E=1` the default engine is `test/support/replay-engine.ts`, a shell script that answers `--version` and exits 64 on any real invocation; replay sessions report `pid: null` (`src/engine-host/replay-transport.ts:310`). `scripts/dev-stub.js` is the `pnpm dev:stub` launcher, not an engine. A live session's `session.status` carries the pid from `initializing` (`src/engine-host/session.ts:621,651`), and `FIRST_OUTPUT_MS` is 30 s. The engine binary is chosen by `MAWS_E2E_ENGINE_BIN`. `e2e:packaged` runs the packaged app with its own spec list (`playwright.config.ts:20`), not `browser-cua`. The seam is `globalThis.__maws_browser.cua` (`inspector.cua = cua`).
11. **macOS `lsof -U`** prints each Unix socket's kernel address and its peer's, 66 ms for a full scan on this Mac: the alternative that needs no native code (Decision Log).

## Design

### Shape

One C source, `peer-auth.c`, wraps three system calls and nothing else; it is built once with `clang` and the resulting `peer-auth.node` is committed in both repositories (MAWS `native/peer-auth/`, cua `native/peer-auth/`) with the source beside it. Each repository has a thin loader and the same policy, written in that repository's language: who the peer is (pid, uid, start time), and whether that process instance descends from a given root instance. MAWS's `startCuaBackend` runs the policy on every accept with the session's engine as root; cua's client-mode `runHost` runs it with its own process as root. A refusal destroys the socket before anything is read and logs one line with pid and reason. Both fail closed when the addon cannot load.

### The addon (M1)

`native/peer-auth/peer-auth.c`, plain C against the N-API C header (`node-api-headers`, a headers-only devDependency in each repository; `NAPI_VERSION 8`), compiled by `scripts/build-peer-auth.sh` with `clang -shared -fPIC -O2 -undefined dynamic_lookup -target arm64-apple-macosx13.0` into `native/peer-auth/prebuilds/darwin-arm64/peer-auth.node`. The prebuild is committed in both repositories: N-API is ABI-stable, so one file loads under Electron's Node, under the Node that runs the unit tests and under the Node that runs the plugin, and a fresh checkout needs no compiler. The script refuses off Apple-silicon macOS, like the voice helper's. It is run by hand when the C source changes; each repository's test compares the addon's exported `version` with the loader's `PEER_AUTH_VERSION` constant, and the two repositories' copies of the source are kept byte-identical (M4 diffs them).

Exports, each a thin wrapper that throws a plain `Error` carrying `strerror` on failure:

- `peer(fd: number): { pid: number; uid: number }` — `getsockopt(fd, SOL_LOCAL, LOCAL_PEERPID)` and `getpeereid(fd)`.
- `process(pid: number): { ppid: number; start: number } | null` — `proc_pidinfo(pid, PROC_PIDTBSDINFO)`; `start` is `pbi_start_tvsec * 1e6 + pbi_start_tvusec`; `null` when the process is gone or unreadable.
- `version: number`.

Loading: `process.dlopen` on a path the loader resolves. MAWS: `<resourcesPath>/peer-auth/peer-auth.node` when packaged (`electron-builder.yml` `extraResources` copies `native/peer-auth/prebuilds/darwin-arm64` to `Resources/peer-auth`), else `<appRoot>/native/peer-auth/prebuilds/darwin-arm64/peer-auth.node`. cua: `<package root>/native/peer-auth/prebuilds/darwin-arm64/peer-auth.node`, with `native/` added to `package.json` `files`. On any other platform or architecture the loader reports `unavailable` without trying.

### The policy, shared in shape (M1)

- `ANCESTRY_LIMIT = 64`.
- A **root** is a process instance `{ pid, start }`, captured when the root becomes known (`process(pid)` at that moment). A root whose `process(pid)` no longer returns the same `start` is dead and matches nothing.
- `descends(peerPid, roots, lookup)`: walks `pid → process(pid).ppid` at most 64 steps, starting at the peer itself (a peer that is the root process is accepted); true when it meets a root pid whose live `start` equals the stored one; false at `ppid 0`, `1`, a `null` lookup or the limit.
- `authorizePeer(fd, roots, deps)` runs in this order and returns the first refusal or `null`: `module_unavailable` (the addon failed to load), `peer_unavailable` (no fd or `peer()` threw), `uid_mismatch` (`uid !== process.getuid()`), `no_root` (no live root), `not_descendant`. It reads `peer(fd)` first, walks, then reads `peer(fd).pid` again and refuses `not_descendant` if the pid changed (Fact 6: the descriptor moved to another process during the walk). A peer whose `process(pid).start` is later than the accept time is refused `not_descendant` too (the connecting process is gone and its pid reused).

### MAWS: the authorizer on the cua socket (M2)

- `CuaBackend.engineProcess(appSessionId, pid: number | null)` sets or clears the session's root, capturing `{ pid, start }` on set. `src/main/browser/index.ts`'s `session.status` subscription calls it for every status of a known session, outside the existing `if`: the pid when `status.process !== 'exited'`, `null` when it is. `closeSession` clears the session's root. Host loss clears nothing: MAWS raises no host-loss event (only `hosts.onState('engine-host', …)` transitions, after which `ready` republishes every session's status), and a root is re-verified as a process instance on every walk, so a stale pid matches nothing.
- The addon is loaded eagerly in `startCuaBackend`; `inspect()` reports `peerModule: 'loaded' | 'unavailable'` per backend and `refused: number` per session.
- `listen()` uses `createServer({ pauseOnConnect: true }, …)` and `chmodSync(path, 0o600)` on `listening`. On accept: if the session has no live root and no trusted root exists, the socket joins the session's `pending` set and waits up to `PEER_ROOT_WAIT_MS = 3000` for `engineProcess` to set one (the engine's MCP servers start within the first second of the engine and the status event precedes them; the wait covers ordering, not a missing engine); when a root exists the check runs at once. Then `authorizePeer`. Acceptance resumes the socket and constructs `CuaConnection` as today. A refusal destroys the socket, logs `cua socket of <appSessionId>: refused peer pid <pid> (<reason>)` through `log` (no pid when unknown; `module_unavailable` adds `run scripts/build-peer-auth.sh`), and increments `refused`. `closeSession` and `dispose` destroy the session's pending sockets too.
- Existing connections are not re-checked when the root changes: an exited engine takes its `cua serve` with it, and the close handler already releases everything.
- E2E seam, compiled in only behind the existing `env.MAWS_E2E === '1'` branch: `inspector.cua.trustRoot(pid)` adds `{ pid, start }` to a backend-wide trusted set that `authorizePeer` consults beside the session's root. The fake-host scenes register the test's own `process.pid` after every app launch, the restart scene included.

### cua: the authorizer on the client-mode relay (M3)

- `src/chrome/peer.mjs`: the loader and the policy above, with `PEER_AUTH_VERSION`.
- `runHost` takes an `authorize` option; `connector()` (client mode) passes `authorizePeer` with the root `{ pid: process.pid, start }` captured at start. The Chrome-route host (`src/chrome/host.mjs` run directly by Chrome's native-messaging launcher) passes nothing and keeps today's behaviour. With the option set, `createServer({ pauseOnConnect: true })`, and each accept runs the check before any read: a refusal destroys the socket and writes one diagnostics line `relay <name>: refused peer pid <pid> (<reason>)` through the host's existing log; `module_unavailable` names the build script. The host's status file gains `peerCheck: 'on' | 'off' | 'unavailable'` so `cua doctor` and `profiles_list` diagnostics can say why a vendor connection fails.
- Legitimate clients are the vendor service and the trusted worker launched by this process (`src/runtime/launch.mjs`), hence descendants; `cua profiles list`'s inventory launch is a child of the CLI process that opened the relay. Nothing else is meant to connect.
- Plugin version 0.6.0 → 0.7.0 (plugin-visible: a relay that refuses outsiders, a new status field).

### Lifecycle and failure table

| Situation | MAWS socket | cua relay |
| --- | --- | --- |
| `cua serve` of the session connects after the engine's first status | root known; accepted at once | its vendor service connects; accepted |
| `cua serve` connects before main processed the status | waits ≤ 3 s for the root; accepted when it arrives | n/a |
| a fork subagent's `cua serve`; `cua profiles list` run by the model's Bash | descendants of the engine; accepted | each opens its own relay with itself as root |
| a Terminal `nc -U <path>`; another app; another session's process | `not_descendant`; destroyed before the hello; one log line | `not_descendant`; destroyed before any read; one diagnostics line |
| a root-owned process | `uid_mismatch` | `uid_mismatch` |
| the engine exited, or the supervisor was lost; a peer connects | `no_root` after the wait | the relay died with `cua serve` |
| the engine outlived a main restart | its first status carries the pid; accepted | unchanged |
| a connector passes its descriptor to another process and exits | the re-read pid differs, or the start time is later than the accept: refused | same |
| the addon fails to load (missing file, wrong platform) | every peer refused `module_unavailable`; `inspect().peerModule = 'unavailable'`; the socket still listens so cua's retries show the symptom | every vendor connection refused; status `peerCheck: 'unavailable'`; `cua doctor` says so |
| the peer process exits mid-walk | `process()` returns null; `not_descendant` | same |
| e2e under `MAWS_E2E=1` | the test's pid is a trusted root; the fake host is accepted; an orphaned connector is refused; a connector the stub engine spawns is accepted with no trusted root | cua's tests spawn their vendor stand-in as a child: accepted; an orphan: refused |

### What users see change

Nothing in the app when everything is in place. A same-user process outside the session that connects to either socket is cut off at once. If the addon is missing, the agent's browser stops working in every session and the browser log, `inspect()`, cua's status file and `cua doctor` all say why.

### Out of scope

Executable or code-signature identity of the peer (forgeable or inapplicable here). The Chrome-route host socket (cua's trust model for it stands; Decision Log). Linux and Intel Macs (client mode is MAWS-only, and MAWS is Apple-silicon macOS; the loader reports `unavailable` elsewhere). Re-checking live connections on root change. Any change to the primitive filter (A-51). `--strict-mcp-config` or settings-source hardening of the engine launch (a separate decision for MAWS's charter; named in the tracker row).

## Acceptance

1. **Unit, the addon (both repositories):** a child spawned by the test connects to a listening socket; `peer(fd)` reports the child's pid and the test's uid; `process(childPid).ppid === process.pid` and `start` is stable across two reads; `descends(childPid, [{pid: process.pid, start}])` is true. ## Surprises & Discoveries

- 2026-10-09, the spec's first review: the relay socket inside `cua serve` re-serves the primitives to any same-user client (Fact 3), so a check on MAWS's socket alone would protect only the moments when nothing is connected; the design grew to both sockets (Decision Log). `LOCAL_PEERPID` names the last operator of the peer socket, not the connector (Fact 6).
- 2026-10-09, execution pre-flight: the SIGUSR1 route (Purpose (a)) is not specific to `cua serve`: any stock Node process inside an accepted tree (the engine's other Node MCP servers, a Node process the model starts, the vendor runtime's processes if they are Node, `spawnUpstream`'s anchor) answers a same-user `kill -USR1` with an inspector and is a descendant. `--disable-sigusr1` closes it only for the processes cua starts itself. M2 and M3 check which processes in each tree are Node and record it here; M4 writes the general form into the tracker row's residual and the A-52 text.
- 2026-10-09, M2's SIGUSR1 check (instances it launched over scratch e2e user data; Playwright's own launches carry `--inspect=0`): MAWS main answers SIGUSR1 with an inspector on 127.0.0.1:9229, dev and packaged alike, and so does the packaged binary run as Node (the detached supervisor); the fuse `EnableNodeCliInspectArguments` is enabled. An inspector in main is the whole app, a route past both checks, in the same class as Purpose (b)'s supervisor token. A `process.on('SIGUSR1', () => {})` listener in main and at the supervisor's entry suppresses it on Electron 44.4.5 and keeps Playwright's `--inspect=0` working; `NODE_OPTIONS=--disable-sigusr1` stops it for both Node binaries in a session's tree (the shim's `node`, nvm Node 22.23.2, the vendor runtime's Node 24.21.0, all of which answer SIGUSR1 unflagged). Related fuses: `EnableNodeOptionsEnvironmentVariable` enabled, `OnlyLoadAppFromAsar` disabled. The engine is Bun (not checked further).
- 2026-10-09, M3's SIGUSR1 check (processes its own probes started): `cua serve` and the anchor, now flagged, open no inspector and stay alive. The vendor launcher runs stock Node (`cua_node/bin/node`) and opens an inspector on 127.0.0.1:9229 on SIGUSR1: the vendor-side residual. The sandboxed kernel and trusted worker try, but the default sandbox blocks the listener. Node accepts the flag in `NODE_OPTIONS`, but `launch.mjs` strips `NODE_OPTIONS` and the vendor runtime stays unmodified (the owner's ruling), so nothing is applied. A copy of the real vendor runtime against a fake MAWS peer got through the checked relay (`tabs.create` seen) with nothing refused.
