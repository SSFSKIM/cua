# Gate #258: an element click on a text field keeps its selection

- **Ticket:** [#258](https://github.com/SSFSKIM/cua/issues/258), "macOS engine: an element click on a text field keeps
  its selection (AXPress), where the vendor's click places a caret" (labelled P2; the pre-flight's §6 lists it with
  #259 as P1). Gate of the macOS default switch (M5 pre-flight §6), task T8e.
- **State:** the witness cell is built into the native matrix (`d0942e93b`) and unit-proven. Its hosted reading waits on sitting C's
  pilot. No engine change. **Open.**

## The report

Registered from #187's slot on 2026-11-01 (cell 3 (i)), with the Electron fixture frontmost and the word at offsets
20+7 selected in its text area:

- cua: the selection was kept (20+7). The element click went by route 1, the field's AXPress
  (`cua/elementClick`: plan action, AXPress, reason advertised).
- The vendor: the selection was cleared, and the caret was at offset 44 (line 3, column 10). No input route was
  reported.

A model that clicks a text field and then types replaces the selected text on cua, and inserts at the caret on the
vendor.

## What the code says today

#283, #313 and #324 changed the ground around this path, but not this path. On today's head (`8bf3ff37b`), a plain
left element click on the frontmost fixture's text area goes like this:

1. `elementClickPlan` (`native/engine/Sources/Engine/Routes.swift:32-46`) chooses route 1, the advertised AXPress. That
   happens unless cua's hit-test at the element's clickable point lands on a strict descendant of the element.
2. cua hit-tests against the application element (`ElementInput.swift:52`, `Input.swift:1090`). The vendor hit-tests
   under the element's window (`Routes.swift:52`; `F-helper-logic.md` §5, item 1). The vendor's ladder is otherwise
   the same: AXPick, else AXPress, synthesized when the point lands on nested content.
3. The click then takes `textEntryClickRoute` (`WebAreaFocus.swift:639-645`). For an AXTextArea in a Chromium process
   that gives `.pressConfirmingFocus(selecting: false)`: the press, then a focus read-back. No caret is written.
4. `carryActionClick` (`WebAreaFocus.swift:715-738`) writes a caret only on a WebKit page (`selecting`).
5. What each ticket changed instead:
   - #283 is the background web-area focus route, for a pointer into a background page.
   - #313 confirms a text-entry action by its focus, and writes the caret on WebKit pages only.
   - #324 is caret-first focusing for set_value and select_text on WebKit pages.

So the code still carries this click by AXPress wherever cua's hit-test does not find a descendant. AXPress kept the
selection on 2026-11-01. The difference very likely still shows.

The code does not settle two things:

- whether the vendor's window-rooted hit-test lands on a descendant of this text area (its 2026-11-01 caret suggests a
  posted click);
- whether cua's application-rooted one does not.

Both are runtime facts of Chromium's tree. The engine is therefore not changed before the runner reads them, as the
dispatch required. The cell records cua's own plan and hit relation (`engineMeta.act.elementClick`) beside the reading,
so a difference names its cause.

## The witness

**The cell:** `electron/frontmost/click.selection` (`scripts/native-matrix/plan.mjs`, `CARET.selection`), a method
case of the full matrix. It runs in the frontmost regime only, as the ticket registered it. In the background a web
page takes no pointer, and that is the declared refusal's question.

1. **Prepare.** The fixture's field is given the matrix's known value (`FIELD_LINES`) and focused. "charlie" is
   selected in it, which is offsets 20+7 (`selectedIn`, the same preparation as the `typeText.replace` row).
2. **Device read before the click.** The approved bundle's `--probe text-view` reads the field's
   AXSelectedTextRange, outside either engine (`matrix-device.mjs text-range`, `caret.mjs fieldRange`).
   - It must read 20+7, or the row is invalid and nothing is sent.
   - This is the reader that produced the ticket's readings (#187's `188-range`).
3. **Act.** One element click by index, `__app.click(index)`.
4. **Device read after the click.**
5. **Check.** The value is read back through the engine's observation, and must be unchanged.

**What it reads.** The row's outcome is the reading: `range {location, length}`, `collapsed`, `kept` (the prepared
selection still there), and the caret's `line` and `column` (0-based), plus `valueKept`. The row also carries
`caret {before, after}`, each `{range, focused}`, where `focused` says whether the app's focused element is the field.
These are offsets and booleans only, never the field's text.

**How it is judged.**

- **The row's own check:** the selection collapsed to a caret (a person's click, and the vendor's as registered), with
  the value kept.
- **The verdict** is the T10a judge's, in a mode added for these rows (`cell-verdict.mjs` `'reading'`).
  - It works as any frontmost row against the vendor's sample of the same run (ruling 1116's pairing; NO VERDICT for
    an alert, a failed activation, missing readings or an unpaired sample).
  - Two passes are equal only with the same reading, every recorded field alike, so a caret elsewhere in the field is
    worse.
  - Two failures are equal only as the same failure. cua passing where the vendor failed is better.
- **No departure may name the row** (`departures.mjs`, R3 and the pre-flight's §6: neither difference can be
  declared).

**Where it runs.**

- In every full matrix run on both lanes, so sitting C reads it: the pilot reads it once a lane, and the full sitting
  three times.
- If the vendor is not live on a runner, the same cell runs in the first MacBook lane as the narrowed method cell:
  `node scripts/native-matrix.mjs cell method --scene electron …` on each lane.

## Closing condition (open)

- **Equal to the vendor's.** In sitting C's full run, `electron/frontmost/click.selection` judges `equal` and qualifies
  (three complete run pairs, every sample with a verdict). Either both collapse the selection to the same caret, or
  both leave the same range. Record the run's URL here and close #258.
- **Worse.** The selection is kept on cua and cleared on the vendor, or the caret lands elsewhere. This is cua acting
  differently from the vendor, which R3 does not let anyone declare, so it is **fixed**.
  - The likely fix is the element click's gate for text-entry roles: hit-test under the element's window as the
    vendor does, or synthesize a click on a text field. The cell's `elementClick.hit` shows which one.
  - The fix moves `engineVersion` unless 0.3.0 is still unshipped.
  - The cell is then run again.
- **Better.** cua collapses the selection and the vendor does not. This does not close the gate by itself: it is not
  "equal to the vendor's". It goes to the design session.
- **No verdict.** The gate stays open.
