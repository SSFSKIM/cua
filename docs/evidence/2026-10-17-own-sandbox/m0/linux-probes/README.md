# #115 M0: the Linux probes (XShm, app launch, the home's nesting)

Spec: `docs/doperpowers/specs/2026-10-17-own-sandbox-design.md`, Plan of Work M0 "Linux probes"; Design "Linux computer sessions" (facts a and b) and "Policy" (the nesting). The probes ran on the GCE box `cua-gce` (README in `../gce-box/`) on 2026-10-17 at 08:30Z, from the box's clone of this branch at `aacc675`.

## Verdicts

| Probe | Verdict | What it selects for M3 |
|---|---|---|
| (a) XShm | **sky_linux is unaffected; MIT-SHM itself is broken inside the sandbox.** sky_linux's `get_screenshot` works inside the worker-shaped sandbox (it uses plain `GetImage`; its binary names no MIT-SHM). Any other X client that uses MIT-SHM inside the sandbox gets its private-namespace segment id resolved in the X server's namespace: the raw client's `XShmAttach` "succeeded" against a foreign segment and the image never arrived in its own (`imageArrived: false`), and GTK clients (gedit, zenity) die at start with `BadAccess` on `X_ShmAttach`. | Matters only for applications that run inside the worker's sandbox, which is (b). With (b)'s contingency, nothing that uses MIT-SHM runs inside it. |
| (b) App launch | **Breaks.** sky_linux launches an application by fork/exec (`posix_spawnp`/`execvp` on the desktop entry's `Exec`; outside the sandbox the launched gedit's parent is `sky_linux_arm64`). Inside the worker-shaped sandbox both applications it launched died at start: gedit within 150 ms and zenity within 900 ms, each with MIT-SHM `BadAccess` and dconf's "Read-only file system" for `/run/user/<uid>/dconf/user`. Even an application that survived would sit in the worker's PID namespace with a read-only root and end with it. | **Contingency 1, the supervisor-side launch.** The launch path can be redirected without touching sky_linux: every `launch_app` reaches cua's trusted sky service (`src/services/sky.mjs`) as `{type: "execute", method: "launch_app", args: [{app}]}` before it is delegated to the vendor, so cua can answer it from the supervisor, outside the sandbox (`gio launch` of the desktop entry, or `systemd-run --user`; both are on the box, `/usr/bin/gio` and `/usr/bin/systemd-run`), as `launch-services.mjs` does with `open` on macOS. The worker stays confined. |
| Nesting | **Not expressible on Linux** at rust-v0.159.2 (the vendor `codex`): a read entry nested in a denied (`none`) directory is not re-bound. The denied home becomes a mode-111 tmpfs; the launch's run directory and session temp, as writable roots, are re-bound inside it and work; `runtimes/`, `node/` and the helper's directory read `ENOENT`. So the helper placed at `$CUA_HOME/sandbox/<tag>/` cannot even re-execute itself (`bwrap: execvp …/codex-linux-sandbox: No such file or directory`). | **The fallback, with `run/` added.** Deny `state/`, `remote/` and `chrome/` one by one, and also `run/` with the launch's `run/<id>` and session temp re-exposed writable inside it: that shape holds completely (every denied read and write refused, every link `EACCES`/`ENOENT`, runtimes/, node/ and the helper directory readable, the run directory and session temp writable), so other sessions' run directories stay denied on Linux too, which the Design's fallback gave up. M3 re-runs the probe against its own helper build before relying on this (`--helper-source`). |

## Findings beside the verdicts

- **Screenshots land in TMPDIR.** sky_linux writes `get_screenshot`'s JPEG to `std::env::temp_dir()`, so under the worker's profile it lands in the session temp (`underSessionTmp: true` both outside and inside). With `TMPDIR` unset it writes to `/tmp`, which the scoped profile does not make writable: M3's worker must carry the per-session TMPDIR (the spec's per-session TMPDIR already guarantees it).
- **A restricted network silences a socket stdout.** Under `network: restricted` the helper's seccomp refuses the socket calls Node makes on a stdout that is a socket (the socketpair `child_process.spawn` creates for `stdio: 'pipe'`): the child ran, wrote its marker file, exited 0, and its output vanished. The probes give their children file descriptors of plain files. This is the reason the own host keeps FIFO stdio (Design, "The own host launches through it directly"); M3's tests should not use spawn's default pipes for a confined child.
- **What the helper adds inside every writable root.** Read-only tmpfs placeholders `.git`, `.agents`, `.codex`, `.aws` in the run directory and the session temp, and a read-only bind `codex-bwrap-synthetic-mount-targets-<uid>` in the session temp (the `mounts` arrays in `probes.json`).
- **Upstream at rust-v0.163.0 reads the same way.** `linux-sandbox/src/bwrap.rs` `create_filesystem_args` (lines 414–720 at rust-v0.163.0) re-binds only writable roots inside an unreadable ancestor (step 3–4 of its documented order); readable roots are bound one by one only for a policy without `:root` read, and the unreadable masks come after them. This is a source reading, not a run: M3's probe against its own build decides.
