# Original OpenAI Chrome backend: source reassessment and metadata handshake

## Scope and outcome

After the user pointed to ChatGPT's installed Chrome extension/full-CDP settings, the original OpenAI extension/native-host route was reassessed before proceeding with the Playwright live probe. No existing browser registration was changed. The Playwright M8 worker paused before any live browser action; its unfinished files are preserved separately.

**Observed:** the relocated, pinned OpenAI `node`/`node_repl` successfully requested `getInfo` from two already-running, signature-verified original OpenAI Chrome native hosts. Both returned `type: extension`, `family: chrome`. The probe sent no tab-list, attach, navigation, input or screenshot request. This proves the original host's metadata peer gate accepts our relocated signed runtime through the owned launcher/anchor chain. It does not prove the full browser service's policy/authentication path, browser operations, native-host relocation, or operation after the desktop app is absent.

The desktop was present and running (26.930.21537). Its installed cua_node manifest still names `0.0.27/20260927214556-b77d38801cca`, matching the inspected/pinned runtime archive version. Do not assume the Chrome native-host binaries are identical across those desktop releases: they are not (hashes below).

## Verified path

```text
our Node probe / owned anchor
  -> relocated vendor node / cua-repl
  -> relocated node_repl
  -> sandboxed trusted metadata-only service
  -> nodeRepl.nativePipe
  -> existing OpenAI Chrome native-host socket
```

Each target socket was selected from `lsof` for a running `ChatGPT for Chrome` process whose parent executable was the user's existing Chrome. The vendor node, node_repl and host executable passed strict Apple-anchor/team `2DC432GLL2` signature checks. Only the two live socket paths were contacted; the stale socket directory was not scanned or modified.

The trusted service implemented only `getInfo` (and answered a peer ping if necessary). It decoded 4-byte little-endian length-prefixed JSON-RPC with an 8 MiB limit and a five-second reply timeout. Session/turn IDs were newly generated by the probe. Results were reduced to a whitelist before reaching the untrusted cell/output: backend type, family, capability IDs, metadata-presence booleans and the header-capability boolean. No profile name, extension instance identifier, token, tab URL, raw result or browser content was recorded.

The higher-level `@oai/browser-desktop` service was deliberately **not loaded**: this avoids its profile-enrichment reads while isolating native-host reachability. No identity initialization or origin-policy result is established by this probe. A blank REPL banner and a private metadata-only trusted service were probe-only configuration, not a production launcher change or a claim of browser support.

## What the screenshot corresponds to

In readable `chatgpt-26.928.40906`, `renderer/app/settings-plugin-selection-70245f6ad5a5.js` contains the Browser Use full-CDP setting/description and history policy. The runtime's `cua_node/@oai/browser-desktop/scripts/browser-service.mjs:62613-62634` checks `browser/config.toml`'s `full_cdp_access_enabled` plus enterprise requirements; raw-CDP operations additionally check origin access. This authorizes a capability on an already connected backend, not an extensionless Chrome connection.

The original browser path uses Chrome's Native Messaging host `com.openai.codexextension`, not Playwright's WebSocket token. The host is Chrome-launched. Source/process topology alone does not settle whether the host requires desktop-presence metadata on restart.

## The original registration seam is real

The plugin ships `scripts/installManifest.mjs`, exporting `install({appServerRuntimePaths: ...})`. Reading the currently installed script (without executing it) showed that it writes a native-messaging manifest and adjacent `extension-host-config.json`. The **actual inspected writer** accepts `schemaVersion`, optional `channel`/`browserClientPath`, `codexCliPath`, `nodePath`, `nodeReplPath`, `proxyHost` and `proxyPort`. Earlier source-agent summaries listing `codexHome`/`browserServicePath` in this writer were not supported by that inspected function and must not be used as its schema.

The installed script can write several browsers' registration locations, so it was not run against the owner's environment. The existence of this installation seam is evidence against treating desktop-owned registration as proof of inseparability. Precedence relative to `chrome-native-hosts-v2.json`, presence-liveness checks and compatibility of a fully relocated host remain untested.

The already pinned official archive contains:

```text
ChatGPT.app/Contents/Resources/plugins/openai-bundled/plugins/chrome/extension-host/macos/arm64/ChatGPT for Chrome
ChatGPT.app/Contents/Resources/plugins/openai-bundled/plugins/chrome/scripts/installManifest.mjs
```

This was verified by archive directory listing; it means the original host is an obtainable component of the same pinned release, not a hypothetical new extension we must write. Static SHA-256 comparison:

| Host binary | SHA-256 |
|---|---|
| Archived/extracted 26.928.40906 | `28a658af20507111b3cf8ebeff59b97bd61acd0d8dd7988322ddb3b56b392ce0` |
| Installed `chrome/latest` (26.930.21537) | `5991312956422b600611abbed0d971ac2049ee96e3d8a0411b7833c335250928` |

The successful handshake targeted the installed host, not a launched copy of the archived host. Version differences remain part of the next compatibility gate.

## Next decision and limits

Prioritize proving the original OpenAI Chrome host's independent registration/startup before completing a parallel Playwright transport. The original backend already implements richer user-tab and browser features; the completed CUA runtime work is reusable for either route. Keep Playwright work as an alternative, not discard it or call it mandatory.

Next probes must not silently overwrite current NativeMessagingHosts/registry files, stop the user's apps, auto-accept system/browser prompts or read credentials. Desktop-absent/cold-start evidence needs an explicitly coordinated environment. A metadata handshake is not a substitute for those tests or for actual browser operations and legitimate policy/authentication behavior.
