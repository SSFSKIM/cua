# Gate #190: Chrome's selectText.notText refusal sentence

- **Ticket:** [#190](https://github.com/SSFSKIM/cua/issues/190), "Reconcile Chrome selectText.notText refusal wording
  with its expected contract" (P2). Gate of the macOS default switch (M5 pre-flight §6), task T8a.
- **State:** the expectation was the wrong side and is corrected. No engine change. The runner witness is prepared and
  has not run. **Open.**

## Which side was wrong

The expectation was wrong. cua's sentence is the vendor's.

- The vendor's `select_text` refuses at two points, in this order (`docs/doperpowers/research/2026-10-18-own-native-engine/F-helper-logic.md`
  §16.2, read from the binary): "Cannot select text for an element that does not support a settable selected text
  range" when `AXSelectedTextRange` is not settable, and "Could not find the requested text to select in the element"
  when the search finds no unique match. The engine carries both verbatim (`TextSelection.swift`,
  `selectTextNotSettable` and `selectTextNotFound`). `ElementMethodTests.swift` already pins the second sentence
  exactly.
- The Chrome row selects "Scene" in the page's checkbox ("Scene option"). Chromium answers the checkbox's
  `AXSelectedTextRange` settable, so both engines pass the first check and refuse at the search.
- Hold 3 recorded the same sentence in all three samples it has of the row: **one vendor run and two cua runs**
  (`docs/doperpowers/research/2026-10-18-own-native-engine/m2b/hold3/matrix/{vendor/run-1,cua/run-1,cua/run-2}/result.json`).
  Hold 3 has no second vendor run. On row `chrome/frontmost/selectText.notText` each sample read "Computer Use server
  error -10005: Could not find the requested text to select in the element", with `refused: true, unchanged: true,
  expected: false`. In the same three samples, TextEdit's and Finder's rows got the settability sentence and passed.
  The background Chrome row was invalid in all three ("the user window (textedit) did not come to the front").
- The plan's `REFUSALS.notText` was written from AppKit's behaviour and applied to all three scenes. Changing the
  engine to match it would make cua differ from the vendor, which R3 forbids.

## The fix

The Chrome row expects `REFUSALS.textNotFound`, the search's sentence. It is matched whole: the bare sentence, or the
sentence inside the server error's envelope (`^(?:Computer Use server error -?\d+: )?<sentence>$`), with the watched
state unchanged. `refusedAs` tests a regular expression's source, so an unanchored sentence would also have matched
another error that quoted it, such as a focus timeout. TextEdit and Finder keep `REFUSALS.notText`. The rows that are
regular expressions on purpose (`noWindow`) are unchanged.

- Commit `e4f2d53a9`: "native matrix: Chrome's selectText.notText row expects the search's refusal, the sentence both
  engines answer there (refs #190)". Files: `scripts/native-matrix/plan.mjs`, `test/native-matrix/plan.test.mjs`.
- Commit `f2099567d`, from the fix wave: "native matrix: Chrome's notText row matches the search's refusal whole, bare
  or in the server error's envelope (refs #190)".

## Unit witness

`test/native-matrix/plan.test.mjs`, "selectText.notText expects each scene's own refusal sentence and no other". The
row's cells run against the recorded goldens with a fake app that throws a given sentence:

- Chrome passes on the not-found sentence.
- Chrome fails on the settability sentence, a timeout and an `actionFailed` sentence. Nothing else is normalized into
  a match.
- The sentence inside another error fails: a focus timeout quoting it, the sentence with text after it, an `Error: `
  prefix, a trailing period. The bare sentence and the enveloped one pass.
- TextEdit and Finder pass on the settability sentence and fail on the not-found one.

Before the fix (`node --test --test-name-pattern='notText expects' test/native-matrix/plan.test.mjs`), it failed
with hold 3's own outcome:

```

  {"ok":false,"outcome":{"refused":true,"expected":false,"unchanged":true,"errorName":"Error","message":"Computer Use server error -10005: Could not find the requested text to select in the element"}}
```

After: `node --test test/native-matrix/plan.test.mjs`: 24 tests, 24 pass.

## Closing condition (open)

The sentence and the expected file agree. `chrome/frontmost/selectText.notText` passes on both engines with
`expected: true`, in valid samples of both engines, and the background row also passes once it is valid. A sentence
other than the search's sentence, matched whole, fails the row. A missing or invalid sample does not count toward
closing. After a pass, record the run's URL here and close the ticket. If Chrome ever answers the checkbox's
range not settable, both engines would refuse with the settability sentence and the row would fail on both. That would
be a fixture change to re-record, not a regression of cua.
