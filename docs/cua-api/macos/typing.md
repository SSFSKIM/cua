`typeText` reads the focused field back after typing, and succeeds only once the field holds what it held before with its selection replaced by the text; for an app in the background that names no focused field, it looks through the app's front window for the one text field that reads as focused, and reads that one. Otherwise it fails with `typeUnconfirmed`: the text was sent, but the field does not read as expected, so some of it may have gone in. Observe the field with `getAXState()`, then put it right with `setValue`; do not type the text again. When the field reads other text, the error shows the expected and the actual text around the first difference; for a `{{secret:…}}` it says only that the field does not match. It fails the same way where the field cannot be read back, such as a field longer than accessibility reports in full. A password field's text is never read, so `typeText` checks its length instead: it succeeds only once the field has taken exactly as many characters as were typed, in place of any selection, with its caret right after them where the app reports one, and the result's text then says it was confirmed by its length only; text that is only a Tab, or only a Return in a single-line field, and not a `{{secret:…}}`, checks no length, so its result says nothing of one. A password field that reports no length at all is checked by its caret alone, which must move from an empty selection to right after the text. Either way, `typeText` succeeds only once the field has held that for 220 ms, and only if it took the text within 680 ms. When it fails, how long it took can depend on the text typed, a `{{secret:…}}` included, and so can its reason. A length shows that no character was dropped or added, not that the right ones went in: under another keyboard layout or an input method, or in a page that rewrites what is typed, the same number of other characters still succeeds. Where a password field's length cannot be read, or it reports no length while text is selected in it, or its selection cannot be read while it already holds text, `typeText` fails with `typeUnconfirmed`; a screenshot shows how many masked characters the field holds. A password field that stops being one while the text is typed, as a page's show-password button makes it, is read no further, and `typeText` fails with `typeUnconfirmed`; the field may then show its text, so if that is a secret, do not take a screenshot of it or call `getAXState()`, and put it right with `setValue`. In Firefox, accessibility can name the page rather than a password field as focused; `typeText` then fails as it does for an element that is not a text field, even when the text went in. An observation never shows the text of a password field or its length: its value reads `secure text`, and `selectText` cannot select in it, so `typeText` into a password field right after a `selectText` types nothing and fails with `typeUnconfirmed`; a screenshot shows what the field displays. Firefox in the background does not report its caret moving as text is typed, so a `{{secret:…}}` typed there fails with `typeUnconfirmed` even when it went in: observe the field to see whether it did. Typing into an element that is not a text field, such as Finder's list when you type a name to select a row, also fails with `typeUnconfirmed` once the keys are sent: observe the selection to see whether it moved. macOS's own text substitutions, such as a period added after a double space, automatic capitalisation or text completion, change what was typed, so they make `typeText` fail with `typeUnconfirmed`, never succeed silently. In a multi-line field a Return is checked like any other character, except in Firefox's editable regions, where it is handled as a Tab is; a Return that ends the text may read back with an empty last line, which counts as typed when the caret sits at that line's start, so where the caret cannot be read, a doubled ending Return may read as confirmed in a multi-line field. A Tab, or a Return in a single-line field, is pressed only once the text before it reads back, and what it does, such as moving to the next field or submitting a form, is not confirmed; inside a `{{secret:…}}` it is sent with the rest of the secret, which is checked once, at its end. To replace a field's text, use `setValue`, or `selectText` and then `typeText`, rather than a select-all key and typing: `pressKey` answers once its keys are sent, without confirming what an editing key such as super+a, super+z or super+v did, so text typed right after it can land before the key takes effect. `typeText` within a second of `pressKey` in the same app first waits, up to a tenth of a second, for the field to hold still before taking what it held as its starting point; a key whose effect lands later still can make `typeText` fail with `typeUnconfirmed` while the field holds the right text, so observe the field, as for any `typeUnconfirmed`, to see which. A click is sent at once but an app can take it in later, so within a second after a click in the same app, `selectText`, `setValue` and `typeText` first wait, up to about 0.3 s, for the field's selection to hold still; `typeText` right after `selectText` types only over the selection `selectText` made, and when a late click has moved it, it types nothing and fails with `typeUnconfirmed`: observe the app, then select the text again. A click can still land after that wait; then `typeText` fails with `typeUnconfirmed` rather than claiming the text, which may already have gone in at the click's point, so observe the field and put it right with `setValue`. Under an input source that is not a Latin keyboard layout, `typeText` pastes its text instead, a line at a time with a Return between lines, and reads the field back the same way, except that its error never quotes the field, so observe the field to see what it holds; a Tab is then pasted as text and checked like any other character, so what is said above of a Tab, that it is pressed with its effect not confirmed and that text of only a Tab checks no length, holds for typed keys only, and a Return between lines is pressed as soon as the field shows any change, before the text before it is read back, so a form that Return submits may have received text that went in wrong. In Firefox in the background, pasted text cannot yet be read back, so `typeText` fails there with `typeUnconfirmed` even when the text went in: observe the field to see whether it did.
