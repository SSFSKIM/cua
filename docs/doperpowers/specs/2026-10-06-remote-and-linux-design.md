# cua over the network and on Linux: remote control of a user's Mac, and a cloud agent's own Linux VM

Parent: `docs/doperpowers/specs/2026-10-02-standalone-cua-design.md` (the standalone server this document extends; its terms, components and acceptance items are referenced, not restated). Board: Phase E is issue #11, Phase F is issue #51; Phase F's basis is spike #12 (`docs/evidence/2026-10-06-spike-12-linux-runtime.md`) and the arm64 deb inspection recorded in the Decision Log. Approved by the owner on 2026-10-06 after the brainstorming round recorded in the Decision Log; revised the same day after the two independent reviews (design review, buildability review), whose fold-back is the Decision Log's block of entries dated 2026-10-06 "review fold-back".

## Purpose

Today `cua serve` works only where the agent and the computer are the same Mac: a Claude Code session on a Mac starts `cua serve` over stdio and drives that Mac's apps and that Mac's Chrome. The owner's next use of cua is a **cloud-resident agent**: a Claude Code session (headless or SDK) living in a Linux VM. Two things must become possible that cannot happen now:

1. **The agent drives the user's own Mac on request** (Phase E, "remote control"). The user's Mac runs a resident cua process in the user's GUI login session; it dials out to a relay the owner hosts; the cloud agent registers that relay URL as an ordinary HTTP MCP server named `cua_repl` and gets exactly the `cua_repl` tool surface it has locally: `js`, `js_reset`, `end_task`, `secrets_list`, `profiles_list`, the same host notes, the same per-connection runtime and cleanup. Seen from the user's chair: after `cua agent install` once, a cloud agent asked "open my school calendar in Chrome and read tomorrow's events" does it on the user's screen, and `$CUA_HOME/run` is clean once the session ends (the client's DELETE, or the idle close). The operating requirement, stated plainly in the README: while a remote agent drives it, the Mac is unlocked and awake; a locked or sleeping console cannot receive input or render screenshots.

2. **The agent drives its own Linux VM** (Phase F, "Linux"). One VM per user, with an X11 desktop, Google Chrome (deb) holding the user's Chrome profile with the ChatGPT extension signed in, and `cua install`/`cua serve` working there as they do on macOS. Seen from the agent: `cua doctor` passes on Linux, `cua serve` over stdio gives the same tools, and the browser route uses the ChatGPT extension exactly as on a Mac.

Both phases keep every rule of the parent: unmodified, pinned vendor runtime; one connection, one owned runtime, one random session; explicit `end_task`; no permission model of cua's own beyond who may connect (the owner's policy: the agent is trusted; app and site approvals are auto-accepted by the owner's Claude Code hooks, which match the MCP server name `cua_repl`).

## Orientation: what exists, and the seam each phase uses

`src/mcp/server.mjs` has two layers. `createServer({input, output, upstream, …})` is one MCP connection: it reads newline-delimited JSON-RPC from `input` (a JSON array body is rejected there with `-32600`, so batches are split before they reach it), writes to `output`, owns one vendor runtime (`upstream`), and closes on `input` EOF, `output` loss or a signal through `close(reason)`, which runs the completion attempt, the runtime and secrets-broker teardown and the final flush. `serve({home, env, input, output, …})` is the stdio process around it: it sweeps `$CUA_HOME/run`, installs signal handlers, claims a run session (`src/runtime/run-dir.mjs` `claimRunSession`), opens the secrets broker, builds the launch (`src/runtime/launch.mjs` `buildLaunch`), spawns the upstream, and releases everything in `finally`; it exits 1 when the runtime's teardown was unconfirmed (`listingLeftover`). Phase E's seam is that `createServer` already takes any stream pair: a network session is a `PassThrough` pair fed from HTTP. What has to move is the per-connection half of `serve` (claim, broker, launch, spawn, release), so several connections can live in one process.

`$CUA_HOME/run` already supports several sessions per process: `claims` in `run-dir.mjs` is a map keyed by session id and the exit hook releases every unreleased claim.

Phase F's seam is the pin: `runtime/releases/<release>.json` is selected by `{platform, arch}` (`src/runtime/manifest.mjs` `selectPin`, `assertHostSupports`), and `install`, `doctor`, `launch` and the Chrome registration take `host` or read the pin's `layout`. Spike #12's table (d) names every darwin assumption behind that seam and the Linux value for each; the Interfaces section below lists the signatures that change.

Terms used below. **Relay**: the small WebSocket server the owner hosts (`relay/` in this repository) that accepts one outbound connection per user Mac and exposes one HTTP MCP endpoint per device. **Device**: one enrolled user Mac, identified by a random id and an enrolment secret from which two leg credentials are derived. **Agent** (in `cua agent`): the resident cua process on the user's Mac. **Channel**: one HTTP request tunnelled over the device's WebSocket. **Session**: one MCP session, `Mcp-Session-Id` → one `createServer` connection → one vendor runtime.

## Phase E design: remote control of a user's Mac

### Wire: MCP Streamable HTTP

The cloud side speaks **MCP Streamable HTTP, protocol revision 2025-03-26** (modelcontextprotocol.io, "Transports"), because Claude Code registers such a server with one command (`claude mcp add --transport http cua_repl <url> --header "Authorization: Bearer <client credential>"`) and any other MCP client can too. The alternative, an SSH reverse tunnel carrying stdio, is quicker to build but needs sshd and key management on every user Mac; it is not offered. Clients on the 2025-06-18 revision send an `MCP-Protocol-Version` header and no batches; the server accepts that header when it is absent, names the version the session's own `InitializeResult` negotiated, or names one of `2025-03-26`, `2025-06-18`, `2025-11-25`, and answers `400` to any other value (the 2025-06-18 revision requires that; the vendor runtime, rmcp 1.5.0, negotiates up to `2025-11-25`, which is what Claude Code 2.1.287 asks for), and accepts single messages and batches both (a batch is split into lines by the HTTP layer; its stream ends when every request in it is answered).

The endpoint path is **`/mcp`**. E1 exposes it as `cua agent run --http <host:port>` (also `cua serve --http`), E3 behind the relay as `https://<relay>/d/<device>/mcp`, which the relay rewrites to `/mcp` before forwarding. It behaves as the revision says:

| Request | Behaviour |
|---|---|
| `POST` with an `initialize` request and no session header | Opens a session: a new connection (runtime resolution, claim, broker, launch, spawn, `createServer`), the `InitializeResult` answered as a plain JSON body (`Content-Type: application/json`) with `Mcp-Session-Id: <connection's session id>` (the same random UUID the connection uses for `run/<session>` and turn metadata). If opening fails (nothing installed, claim conflict, broker or spawn failure, `assertSandboxFits`): `500` with a JSON-RPC error body, code `-32000`, message `cua: <code>`, and no session. |
| `initialize` with a session header | `400`. |
| `POST` carrying one or more requests, with a session header | Written to the connection's `input`. The response is `Content-Type: text/event-stream` with `Cache-Control: no-cache`; the response to each request in the body goes on this stream and the stream ends once all are answered (routing rule below). |
| `POST` carrying only notifications or responses | Written to `input`; `202 Accepted`, no body. This is how elicitation answers and `notifications/cancelled` arrive. |
| `GET` with a session header | Opens the session's standing SSE stream (one at a time; a second GET answers `409`). Server-initiated messages not attributable to an open POST go here, and a `Last-Event-ID` header replays what the named stream had not delivered (resumability below). |
| `DELETE` with a session header | Ends the session: `close('eof')` on the connection, `200` once `closed` settles, which is after the claim, the broker socket, the approval file and the run entry are released (its code and `listingLeftover` are logged, not returned). The session id answers `404` from the moment DELETE is accepted. |
| Session header missing (not `initialize`) | `400`. Unknown or ended session id: `404` (the client re-initializes, per the revision). |
| Any method without a valid bearer | `401`, before anything else is read. `Origin` present and not an allowlisted origin (`CUA_AGENT_ALLOWED_ORIGINS`, comma-separated, empty by default; `null` is never allowlisted): `403`. Requests without `Origin` (non-browser clients) pass. |
| `initialize` when the session cap is reached and no session is Idle | `503` with a JSON-RPC error body, code `-32000`, message `cua: session limit reached (<n>)`. |
| `POST` whose body is not valid JSON | `400` with a JSON-RPC parse error body; no session effect. |

**Routing rule.** Two kinds of message leave a connection. A *response* (a message with `id` and `result` or `error`) goes to the POST stream whose body carried that request id; the HTTP layer records id → stream when it parses the POST and closes the stream when all its ids are answered. A *server-initiated request or notification* (the vendor's `elicitation/create`, progress, log notifications) goes to the oldest open POST stream of the session, else the GET stream, else a per-session buffer drained into the next stream that opens; the buffer is capped at **16 MB** and a session whose buffer would exceed it is closed as `eof` with a logged reason. Responses never go on the GET stream (the revision forbids it outside resumption) and are never buffered as new messages.

**Small resumability.** Every event on a POST stream carries an `id:` line, `<stream>-<n>`, and the stream opens with a priming event (`retry: 15000`, `id: <stream>-0` and an empty `data:` line) so that a stream dropping before its first response still hands the client an id to resume from, and the client's two reconnection attempts are spaced to span a relay restart. Every open SSE stream (POST and GET) carries an SSE comment line (`: keepalive`) after any full 20 s interval in which nothing was written (so no stream is silent for 40 s), so a proxy's read timeout and a NAT's idle timer never cut a long `js` call. When a POST stream drops before its requests are all answered, the HTTP layer keeps the responses that arrive for those ids until a client `GET` with `Last-Event-ID` naming that stream replays them, in order, after which the retained set is cleared. Claude Code's bundled client reconnects a dropped POST stream only when it has received an event id, which is why the ids are there; a dropped stream with no later GET loses nothing until the session itself ends. The GET stream itself is not resumable beyond reopening it (its messages are buffered by the rule above).

**Session end.** A session ends by `DELETE`, by the connection closing on its own (runtime exit, failure: its open streams end, the session is removed, later requests get `404`), by a signal to the process (every session closes as `signal`), or by idling. **Idle** means: no request for 15 minutes *and* no open POST stream *and* no pending elicitation (a server request awaiting the client counts only while some stream of the session, POST or GET, is open, and while one is pending with no stream open, requests left on dropped streams do not count either, because a cell blocked on an approval cannot progress without the client: a client that vanished mid-approval holds no stream and must not hold the runtime forever); an idle session closes as `eof`, because a cloud client that vanished would otherwise hold a vendor runtime forever, while a long `js` cell or an approval waiting for a human never counts as idle. The cap is **1 concurrent session** per process by default (`CUA_AGENT_MAX_SESSIONS` overrides; the owner raises it for experiments), because every session is a runtime on the same mouse, keyboard, front window and Chrome extension, and two agents driving one Mac interfere. When `initialize` arrives at the cap, the oldest Idle session (no task, no open stream, no pending elicitation, whatever its age) is evicted first; only when every session is active does the request get `503`. This is what keeps headless `claude -p` runs, which may exit without a DELETE, from locking the device for 15 minutes. Both numbers are limits on resource use, environment-overridable and documented.

### Connections inside one process

`serve()`'s per-connection half becomes `openConnection({home, env, sessionId, input, output, …})` in `src/mcp/connection.mjs`, returning `{sessionId, closed, close}`; it resolves the runtime itself (per session, so a `runtime use` or a first `cua install` takes effect on the next session without restarting the agent; invalid settings fail the open with a clear code), and releases its claim, broker, approval file and run entries before `closed` settles. The stdio `serve` is then: sweep, signal handlers, one `openConnection` on `process.stdin`/`stdout`, exit code (1 on `listingLeftover`, as today). The HTTP mode is: sweep, signal handlers, a listener, one `openConnection` per session. The sweep runs once per process start, never per session (a sweep removes only dead owners, but it is a directory walk the listener need not repeat). The seams `serve` exposes for tests today (`keychainHelper`, `prepareLaunch`, `chrome`, `listBackends`) are parameters of `openConnection`, and `serve` forwards them, so `test/serve-cli.test.mjs` and the probes keep calling `serve` unchanged.

### Credentials and the device record

Enrolment produces one secret and two credentials derived from it, one per leg, so that the copy a cloud VM holds cannot be used to impersonate the Mac. `cua remote enroll [--relay <wss url>] [--rotate] [--json]` writes `$CUA_HOME/remote/device.json` (mode 0600, directory 0700): `{schema: 1, deviceId, secret, relayUrl?, enrolledAt}`, where `deviceId` is 16 random bytes base64url and `secret` is 32 random bytes base64url. From the secret:

```
deviceCredential = hex(HMAC-SHA256(secret, "device"))     // the agent presents this to the relay (E3)
clientCredential = hex(HMAC-SHA256(secret, "client"))     // the cloud client presents this to the endpoint
```

`enroll` prints, once, the client credential (for `claude mcp add`) and the exact line to paste into `relay/devices.json`: `"<deviceId>": {"deviceCredentialSha256": "<hex>", "clientCredentialSha256": "<hex>"}`. With `--json` it prints `{deviceId, clientCredential, devicesEntry, relayUrl}`. Re-running `enroll` on an enrolled device refuses (`remote_already_enrolled`) unless `--rotate`, which replaces the secret (the relay line and the client registration both change) or, with only `--relay` given, updates `relayUrl` in place without rotating. `cua remote show [--json]` prints the device id, relay URL, enrolment time and the `devices.json` line (hashes only); no command prints the secret or the client credential again.

The endpoint checks the bearer against the client credential derived from its own secret; the relay checks the bearer against `clientCredentialSha256` and **forwards the `authorization` header unchanged**, so the agent re-checks it and E1's handler is literally the same code on both paths (defense in depth; no "pre-authenticated" flag exists). The relay checks the agent's WebSocket bearer against `deviceCredentialSha256`. Comparison is constant-time everywhere (`crypto.timingSafeEqual` on equal-length buffers; unequal length is a mismatch without comparing). `agent run --http` without an enrolled device refuses to start (`remote_not_enrolled`, hint: run `cua remote enroll`).

Exposure the README states: the client credential sits in plaintext in `~/.claude.json` on the client machine (the cloud VM is the credential store), appears in the shell history of whoever ran `claude mcp add`, and, like every MCP payload including screenshots, is visible to the relay operator after TLS termination. Per-client, revocable credentials and accounts are the first thing to add when devices are shared; out of scope.

### The relay and the agent

The relay keeps one map, device id → the device's WebSocket, plus the device table it was started with (`relay/devices.json`: `{"<deviceId>": {deviceCredentialSha256, clientCredentialSha256}}`, hashes hex, edited by hand in v1 from `enroll`'s output). It has no session state. Each HTTP request to `/d/<device>/mcp` is a **channel** on that device's WebSocket, and the agent answers it with its E1 handler unchanged. The envelope, JSON text frames:

```
relay → agent   {ch, t: "open", method, path, headers}     path is always "/mcp" (rewritten); headers lower-cased, see the forwarded set below
relay → agent   {ch, t: "body", data}                      data: base64 chunk
relay → agent   {ch, t: "end"}
agent → relay   {ch, t: "head", status, headers}
agent → relay   {ch, t: "data", data}                      one SSE event or JSON body chunk, base64
agent → relay   {ch, t: "end"}
either          {ch, t: "abort"}                           the HTTP client went away / the handler failed; the receiver fires the channel's AbortSignal
agent → relay   {t: "hello", deviceId}                     first frame after the WebSocket opens (the device credential is in the connect request's Authorization header)
```

Headers forwarded in `open`: `authorization`, `mcp-session-id`, `accept`, `content-type`, `last-event-id`, `mcp-protocol-version`, `origin`; nothing else. A channel id is an integer the relay allocates per device, unique while the WebSocket lives. The relay translates between HTTP and frames and nothing else; a device with no live WebSocket answers `503 device offline`. Two WebSockets for one device: the newer wins and the older is closed with code 4001 (`replaced`); a `hello` whose device id is not the authenticated device closes with 4003. **Liveness:** the relay pings every WebSocket every 25 s and closes it after two missed pongs; the agent runs the mirror watchdog (no ping for 60 s → close and reconnect), so a NAT or proxy that drops an idle socket is noticed on both ends within about a minute. The relay listens on `--port` for both the HTTP endpoints and the WebSocket path **`/ws`**; `relay/README.md` states what the TLS proxy in front must do: pass WebSocket upgrades on `/ws`, disable response buffering for SSE (`X-Accel-Buffering: no` is set by the relay; nginx also needs `proxy_buffering off`), and a read timeout above the longest `js` call the owner expects (the agent's own streams keep flowing, so 10 minutes is a safe floor).

The agent (`cua agent run`, the process the launchd job keeps alive) connects to `relayUrl` with `Authorization: Bearer <deviceCredential>`, sends `hello`, serves channels through a request/response adapter over the E1 handler, and reconnects on loss with backoff 1 s doubling to 30 s. It does **not** reconnect after close codes 4001 or 4003: it logs the reason and exits 1, so two agents for one device (a terminal `agent run` beside the launchd job) do not replace each other forever; `$CUA_HOME/state/agent.lock` (pid, link(2)-published like the registration lock) makes the second `agent run` on one Mac refuse with `agent_already_running` naming the pid, whatever its flags. Sessions belong to the agent process, not to the WebSocket: a reconnect keeps every session; channels open at the moment of loss are aborted (their SSE streams end; responses to their unanswered ids are retained for `Last-Event-ID` replay; the connection's server-initiated messages queue in the session buffer until the next stream). The idle rule still applies, so a cloud client that never returns releases the runtime.

`cua agent run [--http <host:port>] [--relay]`: `--http` is E1's LAN mode, `--relay` E3's (requires `relayUrl` in `device.json`, else `remote_no_relay`); both may be given; neither is a usage error. The `ws` package is imported lazily inside the relay code path only, so `cua serve` and `agent run --http` (and the plugin copy, which runs without `node_modules`) never load it.

### launchd

`cua agent install [--http <host:port>] [--surfaces <list>] [--json]` writes `~/Library/LaunchAgents/com.ssfskim.cua.agent.plist`: `ProgramArguments` = the resolved `node` and `bin/cua.mjs agent run`, followed by `--relay` when `device.json` has a `relayUrl` and `--http <host:port>` when given; `install` with neither (no relay enrolled, no `--http`) refuses with `agent_nothing_to_serve`. `KeepAlive` true, `RunAtLoad` true, `StandardOutPath`/`StandardErrorPath` = `$CUA_HOME/state/agent.log`, `EnvironmentVariables` carrying `CUA_HOME` when set and `CUA_SHIM_SURFACES` from `--surfaces` (default `computer,browser`, since remote use is for the browser as much as the desktop). Paths are XML-escaped in the plist; the resolved `node` path is recorded in `agent status` output because a Homebrew or nvm upgrade that moves it breaks the job (the README says to re-run `install` after upgrading node). It loads with `launchctl bootstrap gui/$UID <plist>`; `uninstall` runs `launchctl bootout gui/$UID/com.ssfskim.cua.agent` then removes the plist; `status` reports the job's pid or absence from `launchctl print gui/$UID/com.ssfskim.cua.agent`. A GUI-session job is the point: `docs/evidence/second-mac-acceptance.md` records that TCC prompts and Keychain access need the console session, and `launchctl bootstrap gui/` is how a process gets one without a terminal.

`cua doctor` gains four rows: `agent.installed` (plist present and parseable by cua's own reader, naming its program path and node path), `agent.running` (launchd reports a pid), `agent.enrolled` (`remote/device.json` present, mode 0600, naming the relay URL or "local only"), and `agent.console` (the user's session is the console session and the screen is not locked, read from `CGSessionCopyCurrentDictionary` through a tiny Swift or `osascript`-free helper already available to doctor: `kCGSSessionOnConsoleKey` and `CGSSessionScreenIsLocked`). Doctor gains a fourth status, **`skip`**: "not applicable here"; it is neither a failure for `ok` nor counted by `summarize` as blocked, and the CLI prints it like the others. The three `agent.*` rows other than `console` read `skip` on a Mac that never enrolled, with the hint "run cua remote enroll / cua agent install"; `agent.console` reads `fail` when locked or off-console, because that is exactly the state in which remote control silently does nothing. The same check backs a classified refusal: a `js` or `js_reset` call arriving over HTTP while the console is locked or the session is not on the console is answered with a tool error `console_locked` ("the Mac's screen is locked or the session is not on the console; unlock it and retry") instead of the vendor's confusing failure.

### What Phase E does not do

No TLS termination in the relay (it sits behind a reverse proxy); no accounts, device lists or credential rotation beyond `enroll --rotate`; no per-client credentials; no change to the vendor runtime, the host notes' content (except the one README paragraph on remote use), the profile registry or secrets. Secrets work remotely exactly as locally, because substitution happens in the agent process on the user's Mac, under the same requirement that the console be unlocked (the login Keychain is locked with the screen).

## Phase F design: a Linux pin

Spike #12 established the facts (evidence doc, sections (a)–(e)); the arm64 deb was inspected afterwards and matches the amd64 one in layout (same `@oai/*` files by hash, aarch64 binaries in the same places). The design is the set of decisions on top of them.

**Source and trust.** Two Linux pins, `runtime/releases/26.928.40906-linux-x64.json` and `26.928.40906-linux-arm64.json`, from the vendor's public APT pool. Trust is the archive hash: the pins have no `signing` section, `runtime.signatures` reads `pass` with "archive hash is the trust root on linux", and `install`, `runtime use` and doctor skip `codesign`; every place that dereferences `pin.signing` or `pin.chromePlugin.signing` today (`chrome-component.mjs` `componentSigning`, its doctor detail line, `parseChromePlugin`'s "must list the host") branches on `signing` being absent or empty. The alternative, checking the APT repository's GPG signature chain at install time, was rejected: the pool file is pinned by hash, which is a stronger statement about this exact file than a repository signature. The provenance of the hash is established once, **at F1 authoring**: the executor verifies each deb's `_gpgorigin` member against the vendor key `3BFA0E4AE8B8CC16A2D9BA684A3B4A566C4660E4` and records the result in the pin's `notes`; and because the pool's signed `Packages` index lists only the latest version and retention of old files is not promised, the owner keeps a mirror copy of both debs at a location of their choosing (the installer already accepts a local file). `runtime.ipc` and `layout.ipcClient` are darwin-only and absent from the Linux pins; `checkIpc` reads `pass` "not applicable on linux"; `runtime.version` and `runtime.node` stay, because `checkVendorManifest` compares them.

**Pin schema.** `parsePin` branches on `platform`: `darwin` keeps schema 1 as is; `linux` requires `archive.format: "deb"`, `components` (each may be a directory or a file; `install.mjs`'s "component directory" check becomes "component exists"), `layout` with the keys above (`LAYOUT_KEYS` becomes per-platform: no `skyServiceApp`, no `ipcClient`; `skyLinuxBin` added), no `signing`, `notes` optional, and `chromePlugin.signing: []` permitted. The Chrome plugin source is taken from `chromePlugin.from` as on darwin, not listed under `components`.

**Extraction.** `install` recognises a deb by `archive.format`: `ar` extracts the `data.tar.xz` member into staging, `tar` with `xz` unpacks it, and the components and the plugin source are taken from the paths in the pin. `install` checks for `ar`, `tar` and `xz` before download and refuses with `missing_tool` naming the tool and its package (`binutils`, `xz-utils`). The verified tree, record and pointer are unchanged.

**Home, environment, launch.** Default home on Linux: `${XDG_DATA_HOME:-$HOME/.local/share}/cua` (`defaultHome(env, host)`). `buildLaunch` on Linux passes `DISPLAY`, `XAUTHORITY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `XDG_DATA_DIRS` through the ambient allowlist; when `DBUS_SESSION_BUS_ADDRESS` is unset and `XDG_RUNTIME_DIR` is set it derives `unix:path=$XDG_RUNTIME_DIR/bus` (an SSH session lacks the former and has the latter); it does not set `SKY_CUA_SERVICE_PATH`, sets `OAI_SKY_LINUX_BIN` to the pinned helper and `CODEX_CLI_PATH` to `<release>/codex`. `cua login` prints the URL when `xdg-open` is absent. Because `DISPLAY` and `XAUTHORITY` reach the runtime, a model cell on Linux can talk to X directly; the host notes and README say in one sentence that the trusted wrapper is not a boundary on Linux (nothing changes today under the allow-all policy with no Linux secrets).

**Doctor on Linux.** `helper.live` and `helper.permissions` are replaced by `display` (`DISPLAY` set and `xdpyinfo` lists `XTEST`, `Composite` and `XFIXES`; `missing_tool` names `x11-utils` when `xdpyinfo` is absent), `accessibility.bus` (the session bus answers `dbus-send --session --print-reply --dest=org.freedesktop.DBus / org.freedesktop.DBus.ListNames` and the list contains `org.a11y.Bus`; the address is derived as in launch), `sandbox.userns` (`bwrap --ro-bind / / true` exits 0; otherwise `blocked` with the stderr, naming `kernel.apparmor_restrict_unprivileged_userns` when the distro is Ubuntu ≥ 23.10); the darwin group-container socket, LaunchServices, `lsof` and `plutil` paths are never consulted; `secrets.*` reads `skip` (unsupported platform). `countLiveHosts` (`src/profiles/chrome.mjs`) matches the Linux host path (`extension-host/linux/<arch>/extension-host`) and reads processes with `ps -eo pid,args`; `profiles open` uses `google-chrome --profile-directory=<dir>` detached; `verify.mjs`'s native-socket holder step reads `skip` on Linux (the helper is a child process, not a socket holder).

**Chrome.** `browsersFor({host, env, userHome})` replaces the `BROWSERS` constant. On darwin it returns today's table unchanged. On Linux it returns, under `${CHROME_CONFIG_HOME:-${XDG_CONFIG_HOME:-~/.config}}` for Chrome's own entries and `${XDG_CONFIG_HOME:-~/.config}` for the others (`CHROME_CONFIG_HOME` is Chrome's variable, honoured by Chrome only):

| key | name | dataDir |
|---|---|---|
| `chrome` | Google Chrome | `google-chrome` |
| `chrome-beta` | Google Chrome Beta | `google-chrome-beta` |
| `chrome-unstable` | Google Chrome Unstable | `google-chrome-unstable` |
| `chromium` | Chromium | `chromium` |
| `edge` | Microsoft Edge | `microsoft-edge` |
| `brave` | Brave | `BraveSoftware/Brave-Browser` |
| `opera` | Opera | `opera` |
| `vivaldi` | Vivaldi | `vivaldi` |

The manifest goes to `<dataDir>/NativeMessagingHosts/com.openai.codexextension.json`; its body is unchanged. The vendor's table also lists `google-chrome-for-testing`; cua omits it because no user profile lives there. Keys are what `registration.json` and the backups record, so the darwin keys keep their names and the three new ones are Linux-only. Profile discovery (`chromeFacts({host, env})`, `CHROME_USER_DATA` becomes a function of host and env) reads `~/.config/google-chrome`. The desktop-presence probe looks for `/usr/lib/chatgpt` and `~/.codex`. The README says: deb or rpm Chrome, never Flatpak or snap.

**Secrets.** No Linux secrets backend: `openSecrets({host, …})` reports `unavailable` with code `secrets_unsupported_platform`; `secrets_list` returns that; a `{{secret:…}}` reference in any input refuses before dispatch with the same code (the Linux `type_text` shape is never matched); `cua secrets set|list|remove` print it and exit 1. A libsecret backend is a later initiative.

**Surface text.** `hostNotesFor(surfaces, {platform})` returns a second constant on Linux that replaces the macOS-only sentences: apps are bound by window (`cua.getApp({windowId})`, `listWindows`), `setValue`/`selectText` do not exist, `paste` types, key names are X keysyms, there is no per-app approval (one connection can drive every window of the session; the owner's allow-all decision, no allowlist in the sky wrapper), and the trusted wrapper is not a boundary on Linux. The 2,048-character budget test covers both constants.

**What Phase F does not do.** Wayland, multi-user VMs (shared `/tmp/codex-browser-use`, spike (e)), a Linux secrets backend, Flatpak or snap Chrome, Linux support for the relay and agent (platform-neutral Node, expected to work, untested until a later initiative).

## Surprises & Discoveries

- 2026-10-06 (E1 LAN proof): the first live client failed to connect. Claude Code 2.1.287 offers protocol `2025-11-25` (its `LATEST_PROTOCOL_VERSION`), the vendor runtime (serverInfo `rmcp 1.5.0`) agrees to it (and answers `2025-11-25` to any newer offer), and the client then sends `MCP-Protocol-Version: 2025-11-25`, which E1's fixed list `{2025-03-26, 2025-06-18}` answered `400`. The earlier m3 evidence of `2025-06-18` was the version that client offered then, not the runtime's ceiling. The gate now also accepts the session's negotiated version and `2025-11-25` (Wire section revised).
- 2026-10-06 (E1): Node 22's `IncomingMessage` `'close'` fires once the request body has been read, not when the client disconnects; the response's `'close'` with `writableEnded` false is the disconnect. The abort signal is wired from the response (Interfaces corrected). `node:http`'s default `requestTimeout` (300 s) does not cut a long SSE response once the body is in, so long `js` calls are safe on the listener. The vendor runtime answers `initialize` with protocol `2025-06-18`, so clients send `MCP-Protocol-Version: 2025-06-18` afterwards.
- 2026-10-06 (pre-flight, on the mini over SSH): a one-shot job loaded with `launchctl bootstrap gui/501 <plist>` from an SSH session runs in the `Aqua` session (`launchctl managername` inside the job prints `Aqua`; the SSH shell itself prints `Background`), so the GUI-session vehicle E2 ships is reachable without anyone at the console.
