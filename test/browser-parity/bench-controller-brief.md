# Own-browser-service benchmark controller

You are running the **agent-level benchmark**, not the deterministic parity corpus. Its question is whether cua's replacement browser service preserves task outcomes and latency through the same plugin/device route. Source contract: `docs/doperpowers/specs/2026-10-13-own-browser-service-design.md`, “Benchmark baseline and comparison” and M0/M5.

## Inputs and route

The dispatcher supplies `service` (`vendor` or `cua`), `profile` (the mini's prepared key, normally `ssfs`), resident checkout commit, runtime release, and an evidence directory on this Mac. Do three consecutive runs, serial and unattended, with the same model and profile. The owner/session must first make that mini profile ready on **cua's extension route**. If readiness or service attestation disagrees, stop and report it; a run through the old ChatGPT extension is not this baseline (spec's execution pre-flight discovery).

Use the cua plugin: finish any open task, `devices_use mini`, `profiles_list`, select exactly the supplied key's `extensionInstanceId` with `cua.getBrowser`. Only tabs you create are yours to close. Call `end_task` only after the run's final scoring and file copy, between runs and at completion. The resident agent serves vendor until the session updates its checkout/agent at M5; setting a shell variable in your client does not switch it. Record the supplied resident commit and the selected browser's documentation header/marker as the attestation. Vendor has no `cua browser service <version>` marker; cua requires it. Never restart/reconfigure the resident agent to make a benchmark run.

Start exactly your fixture process on the mini with `node /tmp/bench-browser/fixture/serve.mjs` in a tracked SSH/Bash process (BatchMode for SSH), record its PID, and wait for loopback port 48731 to answer. If the port is already occupied, establish who owns it rather than killing it. Stop only that recorded process after the three runs. This is a different server/port from the parity harness's 48732. Remote setup touches the fixture directory, not the resident cua checkout or Chrome's profile data.

Read TASKS.md and select the fixture README by its exact Markdown section headers, not by a phrase range. Before T8 finishes, read `## Pages and element ids` up to `## Ground truth`, and `## MiniWoB++ block` through its subsections. ## Recorder and consistent timing

On this Mac, read `test/browser-parity/bench-recorder.js` from the repository and evaluate its complete contents unchanged in the first `cua_repl.js` cell, after selecting the mini device and before browser API calls. Then call `await bench.init({service, run})`, with service `vendor` or `cua` and run number 1–3. It creates `${os.tmpdir()}/cua-bench/<service>-run-<n>/` on the mini and returns `{directory, completed, currentTask}`. Record `directory` as `remoteDirectory` in `meta.json`.

Use the returned path, not `/tmp`: the device sandbox permits writes under `os.tmpdir()` but denied `/tmp` in the live probe. Every completed call, failure, done mark and score audit is appended to `calls.jsonl` immediately; each done/score also atomically refreshes `outcomes.json`. Reopening the same service/run after a device REPL reset replays that journal without erasing it, recovers interrupted outcome snapshots and refuses duplicate completed tasks such as T0. Resume from `completed`/`currentTask` rather than restarting T0 or repeating recorded page actions. A prior run directory is a continuation, not a new clean attempt; let the dispatcher resolve old evidence rather than deleting it.

Call `bench.start(taskId)` before a task. Wrap **every browser API call** in `await bench.call(toolName, kind, () => browserCall(), note)`, including selection, navigation, reads, screenshots and actions. The recorder captures the task ID, call-start ISO timestamp and `performance.now()` duration around that exact awaited call. A rejected call is recorded with its duration and error message, then rethrown; catch it only to decide the task's outcome. Do not time judged calls in the shell or time a whole REPL cell containing several calls.

For example, after `bench.start('T1')`, use `await bench.call('tab.goto', 'action', () => tab.goto(url), 'open fixture')`, then separately record each read. Finish with `bench.done(answer, ok)`. For fixture tasks awaiting ground-truth review, use `bench.done(answer, null)` at their actual completion; after T8 read the ground-truth section and call `bench.score(taskId, boolean)` for T1–T8. Scoring appends `{task, scored:true, ok, t}` and updates the outcome snapshot; the original done row retains `ok:null` and its completion timestamp. The summarizer excludes score audits from timing and checks the last score agrees with the final outcome. MiniWoB answers can be objects carrying raw/discounted rewards and the reason; score immediately from the observed completion and raw reward.

`profiles_list` is an MCP tool outside JS. Measure it with shell-side start/end clocks, retain that measurement until the first JS cell has initialized the recorder, then start T0 and call `bench.recordExternal('profiles_list', 'other', {t, ms, ok, note})`. External timing cannot enter judged tasks. T9 contains only your browser cleanup calls and final outcome; **do not record `end_task`**. The live device route resets the REPL at `end_task`, so finalize every score and copy both files before calling it.

Copy evidence directly from the mini after the fixture block has been scored, after the MiniWoB block, and after T9. For example, with the returned path in `remoteDirectory` and the local run directory already created:

```sh
scp -o BatchMode=yes "mini:${remoteDirectory}/calls.jsonl" \
  "mini:${remoteDirectory}/outcomes.json" "$evidence/$service/run-$run/"
```

These are byte-preserving file transfers. Never write, transcribe, relabel, reconstruct or edit those two files yourself. `bench.dump()` is diagnostic only: the pilot's model-mediated transfer introduced transcription errors. Copies made between blocks bound interruption loss; the final copy, made after the last score and before `end_task`, is the one the summarizer judges. Author `meta.json` locally, including the remote directory path, but obtain calls/outcomes only through `scp`.

## Evidence contract

For each run write `<evidence>/<service>/run-<1|2|3>/`:

- `meta.json`: `{service, commit, profile, model, runtime, started, finished, attestation, remoteDirectory}`. Times are ISO timestamps. Model/runtime/profile stay identical across both service groups; commit pins each group's implementation. `attestation` contains `{route:'resident-agent', residentCommit, selectedBrowserHeader, marker}`; vendor marker is null.
- `calls.jsonl`: copy the recorder's on-device file with `scp`; its call rows are `{t,task,tool,kind,ok,ms,note}` (failed calls also carry `error`). `t` is call **start**, `ms` measured elapsed; `kind` is `action|observe|wait|other`. The recorder adds exactly one `{task,done,answer,ok}` completion row per task, including failures. Preserve actual timestamps: reasoning gaps are part of reported wall time, not judged tool time. Every call in T1–T8 and the MiniWoB tasks needs a finite, nonnegative `ms`; unmeasured calls invalidate judged timing. T0/T9 may have unmeasured durations because their timing is diagnostic only. Finalize fixture correctness through `bench.score` after T8; do not alter timestamps.
- `outcomes.json`: copy the on-device outcome snapshot with `scp`; it is keyed by identical task IDs across runs, each `{ok:boolean, answer}`. Structured answers can contain `rawReward`, `discountedReward` and `reason`. Deferred `ok:null` values must be scored before final export; a finalized deferred score lives in the audit row and outcome snapshot, while the original done row stays `ok:null`. Failed/blocked tasks remain in both files, not silently omitted.

Keep notes about fixture data and observed errors, not unrelated tabs, credentials or approval content. Do not read secret stores, auth files, tokens or Chrome profile files to solve setup friction.

After run 3, run `node scripts/bench-summary.mjs <evidence>` on this Mac and return its output plus the evidence directory. With fewer than three runs in a present service group, the summarizer prints per-run measurements and `incomplete: <service> has N of 3 runs`, exits 1, and gives no verdict. Three vendor runs without cua end `cua runs: none`, not a parity verdict. With all six runs, judged timing is each task's tool-call time: sum the `ms` of its call rows, then compare medians over three runs. A task passes when cua's tool-time median is no more than vendor's plus `max(10%, 500 ms)` and cua's success count over its three runs is at least vendor's over its three. Wall time (first call to done mark) is printed beside tool time but not judged because it includes the controller's thinking. T0 setup and T9 cleanup are excluded from judged timing and call-duration validation; their outcomes still count. Success is the scored `ok` flag: fixture answers are scored against ground truth; MiniWoB uses completion with raw reward 1. Answers and rewards are recorded and printed, never compared: answer wording may vary, and discounted reward is time-dependent. One task outside that boundary yields `regression`. The summarizer rejects invalid or incomparable measurements rather than inferring absent data.
