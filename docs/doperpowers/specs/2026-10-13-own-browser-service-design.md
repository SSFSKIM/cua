# cua's own browser service (board #113; child 1 of the independence composite #114)

## Purpose

Today every browser action an agent takes through cua passes through OpenAI's browser service, a 2 MB module (`@oai/browser-desktop/scripts/browser-service.mjs`) pinned inside the vendor runtime and loaded into node_repl's trusted worker. That module decides, for each navigation, to ask `chatgpt.com/backend-api/aura/site_status` whether the full URL (path and query included) may be visited and ends the session when the answer is no (#111); it initialises Statsig, Sentry and an identity fetch at setup; it reads policy through the Codex app-server; it caps every locator action and `evaluate` at 3 seconds; and it runs `evaluate` behind a read-only membrane. After this change the browser surface of `cua serve` is served by cua's own module, `src/browser-service/`, behind the same two contracts: upward the unchanged REPL client (`@oai/cua`'s browser-client, the API the model learns from the first-call document), downward cua's unchanged extension host (`src/chrome/host.mjs`) and MAWS's in-app client mode. Nothing leaves the machine; no site policy; locator and `evaluate` budgets are the caller's up to 120 s; `evaluate` runs in the page like Playwright's; every command the vendor serves on the Chrome route is served, eventually all of them, with the same results, measured by a differential harness that runs one scenario corpus through the real REPL client against both services and by a benchmark re-run on the mini. A person sees it working by setting `CUA_BROWSER_SERVICE=cua` (the default once M5 lands), opening a tab on a site the vendor blocks (nytimes.com) and driving it, by asking for `tab.playwright.locator(...).click({timeoutMs: 15000})` on a slow page and seeing it wait, and by running `node scripts/browser-parity.mjs diff` and reading "0 unexpected differences".

Owner's rulings (2026-10-13, board #113 and #114): independence is for distribution to others and for the owner's own use; the phase's purpose is full independence from OpenAI with no performance regression; the engine is rewritten in the vendor's shape (Playwright's injected script bundled, our own CDP orchestration), ported from the readable vendor tree, which is the primary reference for all cua work from now on; coverage, fidelity and capability parity losses are minimised, staged, with everything covered at the end; no approval prompts of our own (Claude Code's permission modes are the gate); the model-facing API stays vendor-compatible with extensions; no site policy (a local host denylist is an option, off by default); the baseline and the comparison run on the mini, a registered profile, unattended, three times.

## Design

### Shape: one module in the same slot, two unchanged contracts, a switch

`src/browser-service/` is a cua-owned ES module whose `index.mjs` exports `handleRpc(request)` with the vendor's semantics for `setup`, `execute` and `executeWithRecovery`, registered in the trusted worker in place of the vendor module. `src/services/browser.mjs` keeps its role (secret substitution, MAWS default-instance rewriting, error sanitising) and gains the selection: `CUA_BROWSER_SERVICE=cua` loads `src/browser-service/index.mjs`, `vendor` (the default until M5) loads the pinned vendor module as today. `buildLaunch` passes the variable through from `cua serve`'s environment and, when `cua` is selected, adds the real path of `src/browser-service/` (and nothing wider: not the repository, not `src/`, not a writable state directory) to `NODE_REPL_TRUSTED_CODE_PATHS`, so the worker's import boundary admits the module and its transitive imports; the trusted-worker import test (`test/services-sky-trust.test.mjs`'s pattern) is extended to load the selected cua service under exactly buildLaunch's environment. Both services run under the same `globalThis.nodeRepl` and the same host, so the switch is the differential harness's lever and the user's rollback for one release. The vendor module is deleted by #116, not here.

Why this shape and not a new process: the trusted worker already owns the privileged bridge (`nodeRepl.nativePipe`, `addTurnEndedHandler`, `fetch` for the optional features) and the wrapper's substitution runs before the service sees a command; a separate daemon would need its own socket, ancestry check and secret path for no gain. Why not playwright-core's full stack over a CDP transport adapter (the strongest alternative, proven feasible by MAWS's E0b bridge): the owner chose vendor-shape fidelity, because every semantic of the vendor's flat commands (strictness, waits, snapshot flattening, dialog blocking) is what the model has learned and what "no regression" measures against; a stock Playwright stack would shift those semantics in ways the harness would flag by the hundred.

### The REPL contract, exactly

`setup` returns `{apiManifest, disabledMemberIds}` and no `credentialRecoveryErrorVersion`: credential recovery (the vendor's `BrowserCredentialRecoveryError` and its `{ok:false, error}` envelope) is OpenAI's cloud-login machinery and is dropped, so the client uses `execute`. `execute` resolves to the command's result value or rejects with a `BrowserServiceError`. `executeWithRecovery` is still served (the wrapper and old manifests may call it): it resolves `{ok:true, value}` or rejects exactly as `execute` does; it never returns `{ok:false, ...}`, because the only envelope the client accepts there is the recovery-details schema, which no longer exists. Ordinary failures (timeouts, strict-mode violations, an open dialog, a detached tab) therefore reach the model as rejections with the same sentences the vendor uses, which the M1a proof exercises through the real bundled client (`BC`), not only through direct `handleRpc` calls.

`BrowserServiceError` carries `name: 'BrowserServiceError'`, `code` (the kept vocabulary below), `message` (the vendor's sentence where one exists), `retryable`. The wrapper's `rejectionKind` gains a branch: `error.name === 'BrowserServiceError' && KEPT_REASONS.has(error.code)` → `service:<code>`, so a substituted call that fails is still reported with a fixed, value-free classification; `SECURITY_REASONS` and the recovery branch stay for the vendor selection.

The version guard keeps its fail-closed shape: `actualServiceVersion()` reads the real version of whatever is selected (the vendor package's `package.json` as today; for cua, `src/browser-service/VERSION`) and the wrapper compares it with the independently pinned expectation for that selection (`PINNED_VENDOR_VERSION = '0.1.1'`, `PINNED_CUA_VERSION = '0.1.0'`); a missing, malformed or mismatched version fails with `unsupported_browser_runtime` before any secret is read or any substituted input dispatched. `test/services-browser.test.mjs`'s mismatch cases cover both selections.

### What the service keeps, lifts and drops

Kept as the vendor has it (parity): every command the vendor serves on the extension route and its result shape; selector semantics and strict-mode errors; the aria snapshot grammar; dialog blocking ("a dialog is open; call getJsDialog"); download waits that pause while a Chrome dialog is up; beforeunload auto-accepted; screenshot format and scale; `markTab` and the turn-end cleanup delegated to the host; the `client_timeout_ms` field accepted and ignored by the transport as today; the secret hook points unchanged.

Lifted, from M1, as behaviour extensions on the same methods (owner's ruling), and only where the unchanged client can reach them: the clamp keeps its 3,000 ms default but its maximum becomes 120,000 ms, so `timeoutMs` on locator actions, waits and `evaluate` raises the budget instead of only lowering it; `evaluate` and `evaluateAll` run in the page's main world with Playwright's ordinary semantics (DOM mutation, `fetch`, `XMLHttpRequest`, cookies, navigation, all as the page itself could do them; no `require`, no module import, which the isolated REPL never had), returning the same serialised projection (depth 8, arrays 2,000, keys 200, strings 200,000, cycles marked). The locator engine keeps its own isolated world for the injected script, separate from the page's world, as the vendor does. Not lifted here: the visible-DOM caps (20,000 chars / 200 elements) stay fixed, because the unchanged client's `get_visible_dom()` cannot carry an option; a configurable cap is #116's, when the client is ours.

The no-replay rule for user code (a deliberate departure from the ported evaluator): selector resolution may poll and retry until its deadline before the user's script is dispatched; once a user script has been dispatched to the page (`Runtime.callFunctionOn` or `Runtime.evaluate` issued), it is never dispatched again by the service, whatever follows: an execution-context-loss error, a navigation, a detach or a timeout returns `evaluate_interrupted` (a kept code) with the vendor's sentence and the note that the page may have run it. The `Deadline` object carries the remaining budget into every CDP call so the host's `timeoutMs` never exceeds what the command has left, and into the outer RPC. A timeout cannot roll back page effects; the documentation says so. Fixtures pin this: a page whose button POSTs to a counter endpoint, a page that navigates during the script, a page whose context is lost mid-script, a script that completes after the budget; each asserts at most one dispatch on the fixture's counter and a usable session afterwards.

Dropped, with nothing in their place: site_status and the two `site_status_*` reasons; the identity gate, background identity, Statsig, Sentry, OTEL audit, every telemetry span; `nodeRepl.config` reads and the Codex app-server; persisted grants under `CODEX_HOME/browser`; Auto-review, elicitation and the `approval_*`, `guardian_*`, `enterprise_policy_*`, `persisted_user_denied`, `user_declined`, `browser_navigation_blocked`, `browser_capability_blocked` reasons; credential recovery; GaaS and cloud-only paths; the classic-level profile discovery (cua binds profiles itself). The service calls none of `nodeRepl.fetch`, `nodeRepl.config`, `nodeRepl.telemetry` except where an M3 feature names its one URL (a YouTube caption URL, a Google Docs export URL, the page's own origin for assets); the fake-runtime test makes every other call to those hooks throw. A local host denylist is out of scope for this spec (option recorded; a one-line follow-up when wanted).

Kept error vocabulary (`errors.mjs`, `KEPT_REASONS`): `invalid_url`, `unsupported_protocol`, `tab_not_found`, `browser_not_found`, `dialog_open`, `tab_detached`, `strict_mode_violation`, `timeout`, `evaluate_interrupted`, `download_not_found`, `file_chooser_not_found`, `unsupported_command`, `unsupported_backend`, `browser_capability_unavailable` (the one vendor reason that still has a meaning: a capability the backend did not announce).

### The parity harness (the verification system)

The harness is `scripts/browser-parity.mjs`, an MCP client of its own. It does not replay flat commands: it runs scenarios written as JavaScript cells through the real REPL client (the `cua` API the model uses), because that is the only path the unchanged client's contract can be proven on and because many mutations answer `{}` and are only observable through their effects. A scenario (`test/browser-parity/scenarios/<concern>/<case>.mjs`) exports `{id, milestone, commands: [types it exercises], setup, cells: [...], assert}`: `setup` names the fixture page and state; `cells` are js cells in order, each with a label, with the harness's helpers for concurrent start and join (`start(cell)`, `join(handle)`, used by download and chooser waits that need an armed wait plus a triggering action), for turn completion (`endTask()`) and for disconnect (`drop()`); `assert` checks the fixture's state (through the fixture server's `/state` endpoint) and the cells' results against expected success or expected error code, independently of the other service. Scenario results are written as JSONL, one line per cell: `{case, cell, ok, value (normalised), error:{code, message}, ms, trace:[...]}` plus one line per case with the assertion outcome; `ms` is kept for the timing summary and excluded from the semantic projection.

Comparison (`browser-parity.mjs diff <a> <b>`) first checks cardinality (the same case and cell sets in both, no skips unless the case lists a skip reason), then the semantic projection (ok, normalised value, error code and message, assertion outcome) exactly, then the trace as a multiset of CDP method names per cell with bounded allowances for polling methods (`Runtime.callFunctionOn`, `DOM.*`, `Page.getLayoutMetrics` may differ in count within the allowance the case states); every other difference is listed and the run exits 1 unless the difference is in `test/browser-parity/expected-differences.json` (the lifted limits, the dropped prompts, the no-replay rule, each with a reason and the cases it covers). Normalisation: tab and browser ids mapped by order of creation, timestamps and random ids masked, screenshot values replaced by a perceptual hash compared within a tolerance, snapshot text compared exactly. The comparator has its own tests: a removed case, a changed value, a changed error and a changed assertion each fail the diff. The vendor-versus-vendor determinism run uses no allowance file at all.

Execution topology on the mini (the live surface): the harness keeps a second clone of cua on the mini, `~/Developer/GitHub/cua-parity`, checked out over ssh (BatchMode) at the commit under test; for each run it starts `node bin/cua.mjs serve` there over an ssh pipe with the chosen environment (`CUA_BROWSER_SERVICE=vendor|cua`, `CUA_SHIM_SURFACES=browser`, the mini's `CUA_HOME`), speaks MCP stdio through that pipe, and never touches the resident agent or its checkout. Attestation: before the first scenario the harness records the clone's commit, the environment it set, and the first-call documentation's "# Selected Browser" header line (the vendor's text and `docs.mjs`'s text differ by a fixed marker, `cua browser service <version>`), and refuses to proceed if the marker does not match the requested service. The fixture server (`test/browser-parity/fixture/serve.mjs`: the benchmark fixture's pages plus pages for dialogs, downloads, a file input, an OOPIF, a popup, a slow element, a strict-mode duplicate, the POST counter) runs on the mini on 127.0.0.1:48732 started and stopped by the harness over ssh. The profile is the one the harness binds once with `cua profiles bind <key>` on the mini and records in every run's `meta.json`; M5 reuses that profile. `--device local` runs the same topology on this Mac for development only, never against the owner's Chrome profile here (the local backend is the fake host under `test/support/` unless the executor has its own scratch Chrome with the unpacked extension).

Host trace: the host (`src/chrome/host.mjs`) checks for `$CUA_HOME/state/host-trace.json` (`{path}`) at each session start and, when present, appends one line per backend request and notification for that session to `path`: `{t, session, name, kind:'request'|'notification', method, tabId?, target?, cdp?: method, paramKeys?: [...], ms?, ok, code?}`, never a parameter value, never a URL beyond its origin; the session's `nameSession` name (the harness names each session by case id) attributes lines to cases. The harness writes and removes that file over ssh. The trace is diagnostic in the diff, not the correctness oracle.

Capability parity (`test/browser-parity/inventory.test.mjs`): M0 produces and commits `test/browser-parity/inventory.json`, one row per wire `type` from the union of `Rf`, `zN` and the capability commands that reach `executeUnhandledCommand`, with `{type, schemaSource (BS line), reachability (always | capability:<id> | disabled-on-extension), milestone, cases: [scenario ids]}`; the test fails for any row without either an executable case or an explicit capability-disabled assertion, for any row whose milestone is at or before the current one without a handler in `src/browser-service/`, and for any member of the vendor manifest (read from the installed vendor module under a fake `nodeRepl` and a fake backend answering cua's `getInfo`) that our manifest lacks or adds. Where the vendor is not installed the vendor-dependent assertions skip with a visible line.

Network and disk proof: `test/browser-service/no-network.test.mjs` runs setup, browser selection, a tab's commands and each M3 feature under a fake `nodeRepl` whose `fetch`, `config`, `telemetry` and `createElicitation` throw on any call except the allowances the M3 features name; and the live observation in M5 runs one whole session (setup, selection, ordinary commands, each M3 feature) on the mini's parity clone with `nettop -P -L 0 -p <serve pid tree>` sampling and before/after listings of `$CUA_HOME/state/codex/` (`browser/` must not appear or change), recorded in the evidence directory.

Benchmark baseline and comparison: the archive's task set (`TASKS.md`, fixture, MiniWoB 33c3b4d) is run on the mini by a controller subagent through the plugin's `devices_use mini` on the recorded profile, serial, one attempt per task, three consecutive unattended runs per service, writing `calls.jsonl` (`{t, task, tool, kind, ok, ms, note}`) and `outcomes.json` per run under `docs/evidence/2026-10-<dd>-own-browser-service-benchmark/<vendor|cua>/run-<n>/` with `meta.json` (`{service, commit, profile, model, runtime, started, finished}`); the fixture lives at `/tmp/bench-browser` on the mini as `TASKS.md` assumes. `scripts/bench-summary.mjs <evidence dir>` reads the six runs and prints per task the median and spread of the task's tool-call time (the sum of the `ms` of the task's calls in `calls.jsonl`) and, beside it, of task wall time (from the first call of the task to the done mark), and the outcomes, then the comparison verdict on tool-call time: equal or better when the cua median is within max(10 %, 500 ms) of the vendor median or lower, outcomes equal or better (Decision Log, M0 task 1 review); one task outside fails. Wall time is reported, not judged: it includes the controller model's own thinking. T0 (setup) and T9 (cleanup) are reported but not judged for time; every judged task's call durations must be finite, else the summary refuses; fewer than three runs of a service prints the descriptive table and "incomplete", not a verdict. The controller's brief is `test/browser-parity/bench-controller-brief.md`, self-contained (device, profile, fixture start and stop, TASKS.md, output layout). The vendor benchmark runs through the resident agent (whose service is the vendor's, by construction, until M5 lands and the mini's checkout is updated), which M0 records in `meta.json` as the service attestation; the cua benchmark in M5 runs after the mini's checkout and agent are updated to the M5 head (the session's step, done as on 2026-10-13), so both go through the same route.

In `src/browser-service/backend.mjs`: `discoverBackends(env) → [{id, path, info}]`; `connect(path) → Backend` with `request(method, params, {sessionId, turnId, deadline})`, `on(notification, handler)`, `close()`; the session fields and the `getInfo` shape are the host's.

In `src/browser-service/cdp.mjs`: `class CdpController { attach(tabId); detach(tabId); send(target, method, params, {deadline, preserveOnTimeout}); on(event, handler); dialogs: {current(tabId), blockIfOpen(tabId)} }`.

In `src/browser-service/tabs.mjs`: `class TabRegistry { create(browserId); select(browserId); claim(browserId, tabId); mark(tabId, status); name(name); endTurn() }`.

In `src/browser-service/selectors.mjs` (M1b): `resolve(selector, frame, {deadline, strict}) → ElementHandle`; `resolveAll(...)`. In `evaluate.mjs`: `evaluateInPage(frame, script, args, {deadline})` with the no-replay rule.

In `src/services/browser.mjs`: `createBrowserService({loadService, actualServiceVersion, expectedVersion, secrets, ...})` where `loadService` resolves by `CUA_BROWSER_SERVICE` (`cua` → `src/browser-service/index.mjs`; `vendor` → `CUA_BROWSER_VENDOR_SERVICE`), `actualServiceVersion` reads the real version of the selected module and `expectedVersion` is `PINNED_CUA_VERSION` ('0.1.0') or `PINNED_VENDOR_VERSION` ('0.1.1'); `rejectionKind` gains the `BrowserServiceError` branch.

In `src/runtime/launch.mjs`: `BROWSER_SERVICE_IMPL_DIR = ownedPath('../browser-service')` added to the trusted code paths only when the browser surface is enabled and `CUA_BROWSER_SERVICE=cua`.

Host trace (`src/chrome/host.mjs`): activation file `$CUA_HOME/state/host-trace.json` `{path}` read at session start; line schema as the design states.

Harness (`scripts/browser-parity.mjs`): subcommands `prepare`, `run`, `diff`; `run` flags `--service vendor|cua`, `--device <name>|local`, `--scenarios <glob>`, `--out <dir>`; `diff` flags `<a> <b> [--expected test/browser-parity/expected-differences.json]`; JSONL shapes as the design states; exit 0 on no unexpected differences. Scenario module shape: `export default {id, milestone, commands, setup:{page, state}, cells:[{label, code, start?:boolean, join?:label}], assert({results, fixtureState}) → {ok, reason?}}`.
