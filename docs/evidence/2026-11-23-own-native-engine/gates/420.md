# Gate #420: type_text and a character outside the BMP in Chromium apps

- **Ticket:** [#420](https://github.com/SSFSKIM/cua/issues/420), "macOS engine: type_text drops a non-BMP character
  (an emoji) in Chromium-based apps" (P2). Gate of the macOS default switch (M5 pre-flight §6), task T8a.
- **State:** fixed for plain (non-concealed) text, unit-proven. The runner witness is prepared and has not run. A
  concealed request is unchanged; see "Not covered by this fix". **Open.**

## What the record shows

- **Password fields drop it.** #414's hosted qualification (`docs/evidence/2026-11-18-secure-type-confirm/`; kit
  `probe/414-qual`, `scripts/probe-414/README.md`) typed ASCII with one non-BMP scalar as **concealed** requests into
  password fields. The text was exact 0 of 20 on Chrome for Testing 157 and on both Electron 44 lanes, on main and on
  the fix alike. The shape diagnostic ([run 44353014580](https://github.com/SSFSKIM/cua/actions/runs/44353014580))
  showed only the scalar missing, 5 of 5. Safari and AppKit got it exactly, 20 of 20.
- **Plain fields did not drop it in October.** In M2b's hold 3 on the mini (an older Chrome), cua's keyed rows
  `chrome/latin/typeText.emoji` and `electron/latin/typeText.emoji` were exact in both runs, as were the `acceptance4`
  rows. Nobody has measured plain Chromium fields on a runner since.
- **The vendor drops it everywhere.** Hold 3's vendor lane read length 1 of 6 on every emoji row: it logs and drops
  what the layout cannot key.
- **The paste route works in Chromium.** #361's qualification measured it on Chrome for Testing and Electron, in the
  background, 480 of 480 exact pastes confirmed (`docs/evidence/2026-11-18-paste-readback/`).

## The fix

The fix is the pre-flight's (§6): the paste route for a character outside the BMP. A non-concealed `type_text` takes
the paste route in a Chromium-family app when its text holds any scalar above U+FFFF. Chromium-family means
Info.plist's principal class is `BrowserCrApplication` or `AtomApplication`, the engine's existing `chromiumFamily`.
This holds even under a reliable Latin source.

Nothing else changes route: BMP text (Hangul, CJK, combining marks), other apps (Safari, AppKit, Firefox) and the
spike's `spikeKeyed` override all stay where they were. The answer reports `cua/inputRoute: "paste"`, as every paste
fallback does.

Which Chromium fields drop the scalar is not known before typing, so plain fields are pasted too. The cost is the
paste route's: the pasteboard is snapshotted and restored around the text, and each line waits for its effect.

- Commit `f129d2620`: "macOS engine: type_text pastes a text holding a character outside the BMP into a Chromium or
  Electron app (refs #420)". Files: `native/engine/Sources/Engine/Routes.swift` (`textRoute`'s `keysDropText`,
  `keyedTextDropsCharacters`), `native/engine/Sources/Engine/Input.swift` (`typeText`),
  `native/engine/Tests/EngineTests/RouteTests.swift`. It rides on `engineVersion` 0.2.0.

## Not covered by this fix: a concealed request

A secret is never pasted (the spec's Design, "Text"). So a concealed `type_text` with a non-BMP scalar into a
Chromium app is still keyed, as before. In a password field the scalar is dropped. #414's length read-back then
answers `typeUnconfirmed` (`lengthMismatch`), and the wrapper says the secret may have been partly entered. This fails
closed, but it fails after keying.

Refusing such a request before anything is entered would also need the wrapper's fixed `concealedInputUnavailable`
sentence (`src/services/secret-input.mjs`, `CONCEALED_REASON`) to stop naming the input source as the cause. That
choice is left to the design session. The other way out, a keyed form that Chromium's password path accepts, has no
measurement behind it.

## Unit witness

`KeyRouteTests.testATextTheKeysWouldDropTakesThePasteRoute` (`native/engine/Tests/EngineTests/RouteTests.swift`):

- the predicate: an emoji, and a non-emoji scalar above U+FFFF, in a Chromium app;
- not for a non-Chromium app, BMP text or empty text;
- the route: `.paste` under a reliable Latin reading and under an unreliable one;
- concealed stays `.keyed`, and the spike override stays `.keyed`.

Before the fix, the test did not compile (`cannot find 'keyedTextDropsCharacters' in scope`; `textRoute` had no
`keysDropText`). After: `swift test --filter testATextTheKeysWouldDropTakesThePasteRoute`, 1 test, 0 failures. The
whole engine suite: 1661 tests, 1 skipped (`CUA_304_TREES` unset), 0 failures.

## Runner witness (prepared, not run)

These are the Unicode matrix's emoji rows in the Chrome page's textarea and the Electron fixture's field, cua's lane,
on a GitHub-hosted macOS runner. They are part of sitting C. The rows that change route with this fix:

- `chrome/latin/typeText.emoji`, `chrome/latin/typeText.acceptance4`
- `electron/latin/typeText.emoji`, `electron/latin/typeText.acceptance4`

Each is read back by SHA-256 against its string ('😀 이모지', '한글 테스트 😀'). After this fix, cua's `inputRoute` there
must read `paste`. The Korean and composing rows of the same strings already took the paste route and stay as they
were. The `perContext@` rows are out of the judged matrix (ruling 1119, #185).

The smallest form is the `korean` cell, per field. T10 provides the device, install and workflow:

```
node scripts/native-matrix.mjs cell korean --scene chrome --device hosted-macos --host cua --engine cua ...
node scripts/native-matrix.mjs cell korean --scene electron --device hosted-macos --host cua --engine cua ...
```

`...` stands for the run's `--approved-runtime`, `--approved-engine`, `--sitting` and `--out`. No change to the plan
or the expected file was needed: `expected/unicode.json` declares nothing, and an exact row needs no declaration.
Because the vendor drops the scalar, cua exact is "better" in the judge, never a departure.

The ticket's own check is broader and is not part of §6's witness. It asks for 20 of 20 in a plain field and in a
password field on CfT and both Electron lanes, with Safari, AppKit and Firefox not regressing. `probe/414-qual`'s
non-BMP rows are concealed, so after this fix they still miss (see above). A literal (non-concealed) non-BMP row in
that kit's password lanes would show the fix there.

**What it needs:** T10's hosted harness with Chrome for Testing, the Electron fixture and Korean 2-Set selectable, at
a head that carries `f129d2620`.

## Closing condition (open)

The text lands exactly on cua: the four rows above `ok` with `exact: true` on cua in every valid sample, and `inputRoute`
`paste`. For the ticket as a whole, the design session also rules on the concealed case: refuse before keying, or
accept it as a fail-closed limit recorded in the Decision Log.
