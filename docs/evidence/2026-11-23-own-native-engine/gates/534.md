# Gate #534: a web button pressed by element reaches its pointerdown handler

- **Ticket:** [#534](https://github.com/SSFSKIM/cua/issues/534), rulings 1168 and 1169. Gate of #506 (the M5 sittings),
  task 10 of wave 1.
- **State:** the cell is built into the native matrix and unit-proven. Sitting C reads it. No engine change. **Open.**

## Ruling 1168: the pointerdown-only cell

**Why it exists.** Web UI kits often open menus and popovers on `pointerdown`, not `click`; Radix-style triggers are
the common case. As #534 records, cua still presses a web button by AXPress after #258, where the vendor posts a real
click. `F-helper-logic.md` §18 (the #258 reading, which corrects §5.1's gate) gives the vendor's rule: inside a web view
it posts a real click at the frame's midpoint, when that midpoint is visible and the hit-test there answers "the
element itself or a descendant". cua's #258 fix takes the element itself as a hit only for text-entry roles, so a web
button still gets AXPress. The suspicion was that Chromium's AXPress dispatches no pointer event, so cua would miss these
handlers where the vendor reaches them. Ruling 1153's principle applies: a known suspect gets a cell that would catch it.

**What the source says (the #538 probe's question, read after the cell was built).** The suspicion is false at source.
Chromium's AXPress reaches `EventDispatcher::DispatchSimulatedClick` with `SimulatedClickCreationScope::kFromAccessibility`
(Blink main, `core/dom/events/event_dispatcher.cc`). On the node itself, with no hit test and no pointerover or
pointermove, it dispatches pointerdown, mousedown (skipped when pointerdown was cancelled), pointerup, mouseup (skipped
likewise) and click. `core/events/simulated_event_util.cc` builds that pointerdown trusted (`SetTrusted` for
kFromAccessibility), with pointerId 1 (`kMouseId`, the real mouse's), pointerType `"mouse"`, isPrimary, button 0 and
buttons 1, at the element's centre. Chrome and Electron share this code. The #538 probe saw the same live: an Electron
AXPress moved the document-level pointerdown counter by one (run 45272638524). So the pointerdown-only button's own
listener fires on cua's AXPress as on the vendor's posted click, and the cell cannot tell the two apart.

That is the cell's purpose, not its defect (the design session). It measures what a user sees: whether a
pointerdown-only button responds. Where cua's AXPress reaches the handler, cua passes and the gap is not real on that
scene. **The cell proves reach, not path.** The route cua took stays visible: each row carries the action's
`cua/inputRoute` from `_meta`, and the matrix summary's method table shows each side's routes beside the verdict
(`cell-verdict.mjs` `routes`), unjudged. A page could still tell the two apart (the AX event's `sourceCapabilities` is null and its
`pressure` 0, where a real mouse down reads an InputDeviceCapabilities and 0.5), but recording that fingerprint was
ruled out: it would cost a new fixture build hash, a CSP hash and PROVENANCE churn for what `_meta` already names.
A stricter #534 that judges the path (cua delivering a non-virtual pointerdown wherever the vendor does) was declined.
The declared difference, that an AX press gives a pointerdown react-aria's `isVirtualPointerEvent` calls virtual
(width and height 1, pressure 0, detail 0, "mouse"), is #551 (P3, deferred). #534 closes only when the cell passes live
on both Chrome and Electron in sitting C, its closing note citing C's run and this source reading.

**The cells.**

- `chrome/frontmost/click.pointerdown`, on Chrome for Testing's scene page.
- `electron/frontmost/click.pointerdown`, on the Electron fixture.

Both are method cases in `scripts/native-matrix/plan.mjs` (`pointerdownCase`). Each is the last case of its target, so
every earlier row starts from the same state as before. Each also gets its timing row
(`<scene>/method.click.pointerdown`).

1. **Prepare.** Find the button `Pointer target` by name and read the count in the status `Pointer status`
   ("Pointer downs: N"). If either is missing, the row is invalid and nothing is sent: the scene is not the matrix's
   variant.
2. **Act.** One element click by index, `__app.click(index)`, on both engines.
3. **Check.** Read the count again. The row passes when it rose by exactly one. The outcome records
   `{pointerDownOnce, rose}`.

**The page change.** Each scene gets a pair inline after its own button: a button whose only handler is `pointerdown`
(no `click` handler), and beside it a `role="status"` span counting the pointer downs.

- Chrome: the page variant `pointerdown` (`scripts/native-matrix/fixtures/scene-page.mjs`, `pointerdownPage`).
  It is the shared page with the pair after Apply, in the name field's line, plus one more script. Its CSP adds only
  that script's hash. It is built only when the variant is requested (`pointerdownPage`), and that build throws if a
  part it replaces is missing from the shared page: a broken anchor stops the matrix's page, never another consumer's.
- Electron: `renderer.js` adds the same pair after the fixture's button when the page's URL carries
  `?page=pointerdown`. `main.js` loads it that way only when launched with `--cua-fixture-page=pointerdown`.
  `index.html` is unchanged.

**Placement (ruling 1169).** A first version put the pair on a line of its own below the status line. At the hosted
800 × 600 Chrome frame that line fell below the fold: the web area starts at about window y 143, and the line sat at
about content y 488–510 against a viewport of about 457 points. Where the midpoint is not visible, the vendor takes the
action as well (§18, item 5), so both sides would read 0.

Inline after Apply, the pair sits at about content y 232–254 and adds no height. It comes after every field in the Tab
order, so the `pressKey.tab` rows are unchanged. It stays clear of both drag paths and every coordinate cell's point:
Chrome's drag points and `ELECTRON_FIELD_LAYOUT` lie in the text fields above it, and neither moved.

**The gating.** The buttons appear only in the matrix's trees.

- `./run.mjs` brings the two scenes up with `MATRIX_SCENE_ARGS`: `--page pointerdown` for Chrome, and
  `--electron-arg --cua-fixture-page=pointerdown` for Electron.
- Nothing else passes them. The renderer goldens' recorder, sitting B's native-mac suite, the live hold, the cursor
  sitting and the spike bring up the shared page and the plain fixture.
- The shared page stays byte-identical (its hash is pinned in `test/scenes-counters-page.test.mjs`). Without the flag,
  the fixture's DOM is `index.html`'s alone.
- The scenes' targets (`PAGE_CONTROLS`, `FIXTURE_CONTROLS`) do not name the new controls. The finding cells and the
  fixed-state checks are unchanged.
- `test/native-goldens/` and the repl-parity tests are untouched.
- Changing the fixture's source changes its build directory (`44.9.0-<source hash>`), as any source change does. Both
  lanes of a run share one build. `test/native-goldens/PROVENANCE.md` is updated once both this branch and
  m5/placement, which also moves the hash, are merged.

**The judgement.** The rows are frontmost method rows, judged against the vendor's sample of the same run (the
`'reference'` mode, ruling 1116's pairing).

The vendor posts a real click. If its count does not rise by exactly one, the scene is broken, not cua. Such a pair is
**NO VERDICT** (cause `reference`), with the vendor's count named in the summary's NO VERDICT section
(`plan.mjs` `pointerdownReference`, `cell-verdict.mjs` `reference`). It is counted like every other NO VERDICT and is
evidence about #534 neither way.

| vendor's count | cua's count | verdict |
|---|---|---|
| rose by 1 | rose by 1 | equal |
| rose by 1 | unchanged | **worse**: sitting C FAILs |
| rose by 1 | rose by 2 | **worse**: sitting C FAILs |
| unchanged, by 2 or more, or unread | anything | NO VERDICT (`reference`): "the reference side did not register the pointerdown" |

- **No departure may name either row** (`departures.mjs`, ruling 1168). A press that misses a pointer handler the
  vendor's click reaches is fixed, never declared.
- Each act is an element click, so it is a pointer cell. It goes through `steps.mjs` `guardLane` like every other, and
  is refused unsent when an alert overlaps the scene's window or holds the front or key
  (`test/native-matrix/alert-guard.test.mjs` lists both acts).

**Frontmost only.** These cells follow #258's and #259's choice: they do not run in the background. A background row is
judged against ground truth alone. It would ask cua to deliver a pointer into a background page, which nobody has
measured the vendor doing.

**No runtime visibility check (the coordinator's ruling, option (c)).** Neither engine's observation carries element
frames (`get_app_state` answers text and a screenshot), and no device reader of an element's frame exists in the
matrix. The check is not built, for three reasons:

- The pair sits inline and adds no page height, so it lies inside the 800 × 600 frame by construction.
- A button the vendor's click cannot reach leaves the vendor's count short of +1. That pair is a named NO VERDICT
  (`reference`), never a FAIL and never a close.
- An engine probe of the element's frame would only re-label that NO VERDICT, which is not worth moving the engine
  version.

## Closing condition (open)

- **Close #534.** In sitting C's full run, both cells judge `equal` and qualify: every sample's count rose by one on
  both engines, so Chromium's AXPress reaches pointerdown handlers. Record the run's URL here and close #534, citing
  the cells.
- **Go to design.** The vendor's count rose by one and cua's did not, or rose by two. This blocks #506 and goes to the
  design session: how cua presses a web control (for example a posted click where the vendor posts one) is a design
  call, not a harness one. The cell is then run again.
- **Fix the scene.** The vendor's count did not rise by exactly one. The pair is NO VERDICT, and the scene is fixed
  before it can say anything.
- **No verdict.** The gate stays open.
