# #395: Safari marker route privacy probe

This is experiment evidence, not a product implementation. The probe targets a nonce-bound, runner-owned Safari fixture with one focused input in a small page and one behind 1,600 AX children. Typed cells exercise the unchanged native engine at `2e5b3059` and its actual sky wrapper; substituted cells use a synthetic store in a temporary `HOME`. Password cells use synthetic DOM setup, not the typing engine. No live GUI or app was used outside GitHub-hosted macOS.

The [registration smoke](https://github.com/SSFSKIM/cua/actions/runs/44292750956) built the kit but failed to bring its TextEdit cover forward after DOM setup. The [retry smoke](https://github.com/SSFSKIM/cua/actions/runs/44293634687) and [first full dispatch](https://github.com/SSFSKIM/cua/actions/runs/44294313576) stopped during bootstrap: the sidecar's nested optional collapsed an empty stdin queue into EOF. None contributed any AX marker observations. Before the corrected dispatch, the compiled sidecar passed a closed-stdin check and a scripted stream that idled before and between commands, emitted ordered replies, and exited only at real EOF. That local check used no Safari, other GUI, or AX calls.

## Method

The primary matrix is two page sizes × three field conditions (literal into a normal input, sky substitution of the entire typing argument into the same normal input, password) × three input lengths (8, 32, 128 UTF-16 units) × 20 trials. Typed cells insert at offset 3 in a 29-unit public seed. Password cells are preloaded to the corresponding total lengths and carets. The controls vary text at fixed geometry, vary the length after a fixed caret and prefix, repeat unchanged text, and select nonempty ranges on both plain and password fields. A no-key scenario does not mean no events from `type_text`: the harness sends no *preceding* key and rejects trials where the exact edit, selection and focused DOM node are not verified independently.

The foreground witness runs across typing and observation. Timing below uses median p50 and nearest-rank p95; the marker-path clock starts immediately before the range getter, while the scope clock covers primary-window and web-area lookup before the getter. The marker probe resolves the target by identity against a separately looked-up fixture element. It stores only AX status, safe type/role categories, timings, structural endpoint comparisons, and designed synthetic quantities. It never stores the values, returned strings, marker bytes, marker hashes or decoded offsets. Only the synthetic diagnostics attempt range-to-string, length and index queries; these are not steps of the timed route or a proposal for production. The test does not measure arbitrary providers, other Safari builds, end-to-end model-visible latency, or correctness of a production `type_text` using this route. The same-run walk is a metadata-only replay of #354's bounds (200 nodes, depth 12, 40 ms), measured after the marker path. The historical engine walk is reported separately.

## Final live findings

[Hosted run 44297805982](https://github.com/SSFSKIM/cua/actions/runs/44297805982) passed on Safari 27.2, image `20261102.0473.1`, kit `8ca751a9`, unchanged engine/source `2e5b3059`. **462/462 valid scored trials**, plus two unscored warmups; zero wrong targets, zero privacy violations, and no witnessed foreground change. Cover activation needed a pre-input retry in 14 scored rows; none was sampled until the cover and witness agreed. Every large row verified 1,600 AX filler children (not just DOM nodes).

### 1. Plain fields, including synthetic substituted content

The selected range, opaque start lookup and parent chain gave the same types, return statuses and correct target in 240/240 primary normal-field rows. Counting controls, all 330 normal-field rows had **28 bytes per endpoint**, with LE32 words at byte offsets **8 and 20** matching the designed positions. The positions followed the caret and selection endpoints, not total value length when the caret was held fixed. Every one of the 150 matched comparisons had the same field but a different `AXStaticText` origin and unequal whole endpoint bytes, including all 10 unchanged-content/unchanged-geometry pairs. This does not support treating bytes as a content key; it does support treating them as sensitive position data. The WebKit struct has no text payload (source below); that fact plus the experiment is not a stable ABI guarantee.

The path did not parse those bytes: it type-checked the range, copied the opaque start object, passed it to `AXUIElementForTextMarker`, and took `AXParent`. Passing the whole range instead failed with `kAXErrorNoValue` in all 20 nonempty public controls. No marker bytes, hashes, positions or range contents need to survive or be emitted by the route.

| Page / typed mode | Selected range p50/p95 | Element lookup p50/p95 | AXParent p50/p95 |
|---|---:|---:|---:|
| Small / literal | 0.067 / 0.150 | 0.063 / 0.146 | 0.070 / 0.174 |
| Small / secret | 0.095 / 0.198 | 0.079 / 0.175 | 0.074 / 0.134 |
| Large / literal | 0.067 / 0.204 | 0.063 / 0.148 | 0.062 / 0.200 |
| Large / secret | 0.077 / 0.170 | 0.077 / 0.200 | 0.065 / 0.139 |

All times above are milliseconds, 60 samples per row. Within each page and length, paired secret-minus-literal path medians ranged from **−0.053 to +0.064 ms** (20 pairs per cell). Within rounds, 128-minus-8-unit path medians ranged from **−0.027 to +0.012 ms** across page/mode combinations. Fixed-geometry primary A/B synthetic content variants differed by **0.012–0.049 ms** in path medians (30 samples per variant per page/mode); the smaller independent content controls, five per variant, varied more and did not isolate content from changing leaf identity. There is no repeatable content/length timing trend across these conditions, but this is not a constant-time claim: e.g. the small secret/128 paired difference had a p95 of +1.983 ms. The point of a pre-input-only route is to avoid depending on a negative timing experiment.

### 2. Secure fields

For the type-switched fixture, **132/132** secure observations (120 collapsed, 12 selected; half of each on each page) verified `AXFocused=true`, `AXTextField/AXSecureTextField`, and found the actual secure input through `AXStaticText` and one `AXParent`. Both web-area and field range getters returned a usable `AXTextMarkerRange` every time. For either token origin on either receiver, element lookup returned an AX element, index gave the exact caret/start, length gave the exact selection length, and string gave either an empty string for a caret or one mask glyph per selected unit for a nonempty range. All **48** nonempty diagnostic combinations (12 rows × 2 token origins × 2 receivers) returned masked text, **none** unmasked; all **480** collapsed combinations were empty. On the field, `AXNumberOfCharacters` and `AXSelectedTextRange` disclosed the expected actual count and range; the same two attributes on the web area gave `kAXErrorNoValue`. These results reproduce the first measured run below. Synthetic diagnostics queried them deliberately; the proposed route must not. No trial used a password-from-load AX object; the follow-up qualification fixture covers that case separately.

These results are independent of the unmodified production confirmation: the latter still returned `typeUnconfirmed` for all 120 large literal/secret main rows despite exact DOM input. The standalone marker probe found the field in every case.

## Earlier hosted evidence

[Run 44295383179](https://github.com/SSFSKIM/cua/actions/runs/44295383179), Safari 27.2, image `20261102.0473.1`, returned the correct ordinary field in all eight valid scored plain/secret observations plus two warmups. In all ten the opaque endpoints were each **28 bytes**; little-endian 32-bit words at byte offsets **8 and 20** matched the designed start/end offsets, including separate endpoints on the nonempty selections. A selection changed endpoint bytes without changing width. For a collapsed caret conventionally left at the end of a value, the position can equal the entire field length; in the middle it is an offset, not the total length. A stable field handle does not mean stable whole bytes: both small plain/secret pairs and the single unchanged large control pair had identical field handles but different `AXStaticText` origin handles and different endpoint bytes. Whole-byte differences alone do not show content dependence. All ten took `AXStaticText → AXParent → AXTextField`. In each of the two public nonempty-range controls, handing the range object itself to `AXUIElementForTextMarker` gave `kAXErrorNoValue`, but extracting and passing its opaque start marker gave an element. Deliberate synthetic controls confirmed that `AXStringForTextMarkerRange`, `AXLengthForTextMarkerRange` and `AXIndexForTextMarker` are separate value-bearing operations.

The six password rows in this run were not measured: after focusing the synthetic password while Safari was foreground, macOS accepted the cover activation request without actually switching out of Safari, on both page sizes and both selection shapes. The run stopped at its setup-failure bound. This is not evidence of password marker refusal. [Run 44296356927](https://github.com/SSFSKIM/cua/actions/runs/44296356927) switched the already-focused fixture from `text` to `password` only after the cover was front and the activation witness was armed. It preserved the DOM node; **none** of the 60 measured password rows needed another `focus()` call, and all 60 had `AXFocused=true` and `AXTextField/AXSecureTextField`. WebKit can rebuild its AX object on a type change; these are not rows for an input that was a password from page load. In total 238/245 attempted rows were valid (140 primary, 98 controls), with 0 wrong fields and 0 privacy violations. All seven invalid rows fell before any marker measurement: six cover-activation failures followed by an abort at that setup-failure limit, plus one failed cover ownership check before arming. No invalid row contributes to the rates below.

### Secure-field answers (first measured run)

All 60 valid secure rows (24 collapsed plus six noncollapsed **per page**) returned a marker range on both the web area and the field. The route returned `AXStaticText`; one `AXParent` resolved the exact focused `AXTextField` with subrole `AXSecureTextField`, all 60/60. For both token origins on both receivers, `AXUIElementForTextMarker` returned an element and `AXIndexForTextMarker` returned the exact synthetic caret/selection start. For the 48 collapsed selections, range-to-string returned an empty string and range-to-length returned zero. For the 12 nonempty (16-unit) selections, range-to-string returned only mask glyphs, one per selected unit, and range-to-length returned 16. The secure field's `AXNumberOfCharacters` and `AXSelectedTextRange` exposed the exact designed field count and selection; those two scalar accessors gave `kAXErrorNoValue` on the web area. `AXValue` was not requested even by the diagnostic. Secure marker bytes were not decoded: the exact index from the token establishes position-bearing capacity without copying its bytes.

**Meaning:** requesting a web-area marker range can receive information from a secure selection. The object-only lookup did not return a value, text or number; it resolved its backing element. The experimental string/count/index reads were deliberately separate, synthetic-only calls. The evidence says not to use those calls in the product, not that Safari protects them. The [20-per-cell follow-up](https://github.com/SSFSKIM/cua/actions/runs/44297805982) applies cover retries only before any input or sampling.

## Proposed production boundary

1. Use direct focus first. Never use a marker on a known secure or unclassifiable field and never use it to discover what is in the field. If authorized, try the scoped Safari path before the bounded walk. Resolve only within the approved Safari process and the already identified, same active page/window; reject missing, stale, ambiguous or mismatched scope.
2. **Design ruling 824 (A): permit Safari-only opaque focus discovery, gated on `noFocusedElement`.** A web-area `AXSelectedTextMarkerRange` asks for a descendant's selection *before* it can identify or classify that descendant. [Ruling 811](https://github.com/SSFSKIM/cua/blob/4291f3ba24772fcce9359c51ebc6abc14d04f458/docs/doperpowers/specs/2026-10-18-own-native-engine-design.md#L5754) allows briefly receiving provider data that is never decoded, cached, logged or emitted; the opaque start marker is compatible with that handling rule, and is narrower than a value read. But classifying the receiver cannot classify its descendant, and the position data would expose the caret (often the password length if the caret is at the end) if a provider ever supplies a secure-field marker. [Ruling 808](https://github.com/SSFSKIM/cua/blob/4291f3ba24772fcce9359c51ebc6abc14d04f458/docs/doperpowers/specs/2026-10-18-own-native-engine-design.md#L5714) permits reading a classified secure target's range and count internally to confirm a paste, with only `{secure:true}` metadata, not arbitrary selection or value inspection; a focus-discovery token is not that confirmation. Safari did in fact supply a position-bearing token in the measured password fixture; do not rely on the provider to withhold it. The approved interpretation treats the opaque, tightly scoped pre-input token as consistent with 811's trust-domain rule: the native engine may pass the object unchanged to the provider for element identity and discard it, but never exercise its capability to disclose positions or text. Ruling 808 is not a basis for reading it. If the same focused element cannot be safely classified or proven, keep `noFocusedElement`/unconfirmed; do not extend the rule to other providers or use the token to confirm a secure field.
3. If that exception is approved, make one route attempt before posting the input. On the classified web area: get `AXSelectedTextMarkerRange`, type-check it, obtain its opaque start endpoint with `AXTextMarkerRangeCopyStartMarker`, and pass only that object to `AXUIElementForTextMarker`. Drop both objects immediately after lookup. Never parse, inspect, copy bytes, hash, serialize, compare, cache or emit either marker in product code. Do not ask for the end marker, text/attributed text, range or character lengths, or marker indexes.
4. On the candidate and each bounded `AXParent`, obtain role and subrole in a classification-only batch before touching anything value-bearing; stop on secure, failed classification, a cross-scope element or an exhausted budget. Verify that a supported, readable candidate belongs to the same window/page and is actually focused, not merely selected-looking. Reconfirm the same handle after typing through metadata (`AXFocused`, ownership and role/subrole), not via a new marker dependent on the typed secret. If safe identity or classification fails before any ordinary read-back work, return the existing unconfirmed result rather than weakening it or retrying with data-bearing calls.
5. Preserve #354's existing exact equality and caret confirmation for normal classified fields, fixed concealed schedule and no checkpoint inside a secret. Secure targets never enter that equality path. Ruling 808's existing classified secure paste confirmation is a separate count-delta read, with only `{secure:true}` on the wire; the marker is not a confirmation read and supplies no count to it. No additional per-marker counts, timing fields, path/errors, offsets, selection contents or lengths in model output, logs, audit, tracing or caches. Back the fallback with a stub-marker leak test (distinct canary bytes/offsets in a fake provider reply, absent from everything reachable after lookup), and with negative tests for focus changes including to a password field, stale handles, cross-tab/window ambiguity and unavailable marker symbols. The probe tests particular distributions; it cannot prove constant-time provider or transport behavior. Do not put such an unproven post-input AX route on the concealed critical path.

## Historical comparison

In [#354's run 44031200818](https://github.com/SSFSKIM/cua/actions/runs/44031200818), on Safari 27.2, image `20261102.0473.1`, engine `a7529ee0`, independent AX counting verified 1,600 filler children. The native 200-node walk stopped without a claim in 20/20 trials, at **24.14 / 28.99 ms p50 / p95**. The probe's marker route found the plain input in 20/20, in each case via `AXStaticText → AXParent → AXTextField`. The sum of the measured marker-path AX calls including classification, not including Swift overhead or window/web-area lookup, was **0.63 / 3.61 ms**. That run did not measure marker bytes or concealed and secure marker paths.

## Reusing the kit

The discovery workflow has a pinned engine/source SHA; changing it is enough to repeat the fixture and standalone AX measurements on another build. That does **not** qualify a product PR: this probe intentionally measures edits after an independently verified `typeUnconfirmed` and does not assert the product's fallback ordering or retain its full sanitized read-back record. The separate `probe/395-qual` lane is for real A/B confirmation, privacy and request audit; it takes main and candidate SHAs.

## Source references (not a substitute for measurements)

- WebKit's [macOS marker bridge](https://github.com/WebKit/WebKit/blob/5ce5bb9354f89853915a6e5ed5667a556edf8e86/Source/WebCore/accessibility/mac/AXObjectCacheMac.mm#L1081) converts between the opaque system objects and a fixed-width [`TextMarkerData`](https://github.com/WebKit/WebKit/blob/ebc7485bc5bc227311569ec0c20a6eac29be9de2/Source/WebCore/accessibility/AXTextMarker.h#L153): tree/object identifiers, position and character offsets, anchor/affinity, origin and redaction metadata, not a copy of the selected string. This is upstream source, not a promise of the Safari ABI.
- [`AXUIElementForTextMarker`](https://github.com/WebKit/WebKit/blob/ebc7485bc5bc227311569ec0c20a6eac29be9de2/Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm#L3735) resolves the marker's object/wrapper. [`AXStringForTextMarkerRange`](https://github.com/WebKit/WebKit/blob/ebc7485bc5bc227311569ec0c20a6eac29be9de2/Source/WebCore/accessibility/mac/WebAccessibilityObjectWrapperMac.mm#L4095) calls `toString()`. These are different operations. The [secure-field checks in marker construction](https://github.com/WebKit/WebKit/blob/47748b2d9481297b9f8ee6ace6cfe453aff7ea23/Source/WebCore/accessibility/AXObjectCache.cpp#L5736) are provider behavior, not classification of the underlying focused field by the client. Do not infer that arbitrary AX providers behave the same.
- [#354's read-back design](https://github.com/SSFSKIM/cua/blob/2e5b3059c6fe09d2240fe11a6d952cd3f06c3274/docs/doperpowers/specs/2026-10-18-own-native-engine-design.md#L4889) requires equality only for concealed typing and checkpoints only outside a secret. [#411](https://github.com/SSFSKIM/cua/pull/411) now enforces same-reply classification and drops secure value attributes before conversion, caching or output; a parameterized text read requires its own immediately preceding classification. Classifying a web area as `AXWebArea` does not classify the descendant whose selection the area might expose.
