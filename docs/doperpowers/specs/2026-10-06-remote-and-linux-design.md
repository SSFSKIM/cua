# cua over the network and on Linux: remote control of a user's Mac, and a cloud agent's own Linux VM

Parent: `docs/doperpowers/specs/2026-10-02-standalone-cua-design.md` (the standalone server this document extends; its terms, components and acceptance items are referenced, not restated). Approved by the owner on 2026-10-06 after the brainstorming round recorded in the Decision Log; revised the same day after the two independent reviews (design review, buildability review), whose fold-back is the Decision Log's block of entries dated 2026-10-06 "review fold-back".

## Purpose

Today `cua serve` works only where the agent and the computer are the same Mac: a Claude Code session on a Mac starts `cua serve` over stdio and drives that Mac's apps and that Mac's Chrome. The owner's next use of cua is a **cloud-resident agent**: a Claude Code session (headless or SDK) living in a Linux VM. Two things must become possible that cannot happen now:

1. **The agent drives the user's own Mac on request** (Phase E, "remote control"). The user's Mac runs a resident cua process in the user's GUI login session; it dials out to a relay the owner hosts; the cloud agent registers that relay URL as an ordinary HTTP MCP server named `cua_repl` and gets exactly the `cua_repl` tool surface it has locally: `js`, `js_reset`, `end_task`, `secrets_list`, `profiles_list`, the same host notes, the same per-connection runtime and cleanup. Seen from the user's chair: after `cua agent install` once, a cloud agent asked "open my school calendar in Chrome and read tomorrow's events" does it on the user's screen, and `$CUA_HOME/run` is clean once the session ends (the client's DELETE, or the idle close). The operating requirement, stated plainly in the README: while a remote agent drives it, the Mac is unlocked and awake; a locked or sleeping console cannot receive input or render screenshots.

2. **The agent drives its own Linux VM** (Phase F, "Linux"). One VM per user, with an X11 desktop, Google Chrome (deb) holding the user's Chrome profile with the ChatGPT extension signed in, and `cua install`/`cua serve` working there as they do on macOS. Seen from the agent: `cua doctor` passes on Linux, `cua serve` over stdio gives the same tools, and the browser route uses the ChatGPT extension exactly as on a Mac.

Both phases keep every rule of the parent: unmodified, pinned vendor runtime; one connection, one owned runtime, one random session; explicit `end_task`; no permission model of cua's own beyond who may connect (the owner's policy: the agent is trusted; app and site approvals are auto-accepted by the owner's Claude Code hooks, which match the MCP server name `cua_repl`).

## Orientation: what exists, and the seam each phase uses

`src/mcp/server.mjs` has two layers. `createServer({input, output, upstream, …})` is one MCP connection: it reads newline-delimited JSON-RPC from `input` (a JSON array body is rejected there with `-32600`, so batches are split before they reach it), writes to `output`, owns one vendor runtime (`upstream`), and closes on `input` EOF, `output` loss or a signal through `close(reason)`, which runs the completion attempt, the runtime and secrets-broker teardown and the final flush. `serve({home, env, input, output, …})` is the stdio process around it: it sweeps `$CUA_HOME/run`, installs signal handlers, claims a run session (`src/runtime/run-dir.mjs` `claimRunSession`), opens the secrets broker, builds the launch (`src/runtime/launch.mjs` `buildLaunch`), spawns the upstream, and releases everything in `finally`; it exits 1 when the runtime's teardown was unconfirmed (`listingLeftover`). Phase E's seam is that `createServer` already takes any stream pair: a network session is a `PassThrough` pair fed from HTTP. What has to move is the per-connection half of `serve` (claim, broker, launch, spawn, release), so several connections can live in one process.

`$CUA_HOME/run` already supports several sessions per process: `claims` in `run-dir.mjs` is a map keyed by session id and the exit hook releases every unreleased claim.

Phase F's seam is the pin: `runtime/releases/<release>.json` is selected by `{platform, arch}` (`src/runtime/manifest.mjs` `selectPin`, `assertHostSupports`), and `install`, `doctor`, `launch` and the Chrome registration take `host` or read the pin's `layout`. Spike #12's table (d) names every darwin assumption behind that seam and the Linux value for each; the Interfaces section below lists the signatures that change.

Terms used below. **Relay**: the small WebSocket server the owner hosts (`relay/` in this repository) that accepts one outbound connection per user Mac and exposes one HTTP MCP endpoint per device. **Device**: one enrolled user Mac, identified by a random id and an enrolment secret from which two leg credentials are derived. **Agent** (in `cua agent`): the resident cua process on the user's Mac. **Channel**: one HTTP request tunnelled over the device's WebSocket. **Session**: one MCP session, `Mcp-Session-Id` → one `createServer` connection → one vendor runtime.

## Phase E design: remote control of a user's Mac

### Wire: MCP Streamable HTTP

The cloud side speaks **MCP Streamable HTTP, protocol revision 2025-03-26** (modelcontextprotocol.io, "Transports"), because Claude Code registers such a server with one command (`claude mcp add --transport http cua_repl <url> --header "Authorization: Bearer <client credential>"`) and any other MCP client can too. The alternative, an SSH reverse tunnel carrying stdio, is quicker to build but needs sshd and key management on every user Mac; it is not offered. Clients on the 2025-06-18 revision send an `MCP-Protocol-Version` header and no batches; the server accepts that header when it is absent, names the version the session's own `InitializeResult` negotiated, or names one of `2025-03-26`, `2025-06-18`, `2025-11-25`, and answers `400` to any other value (the 2025-06-18 revision requires that; the vendor runtime, rmcp 1.5.0, negotiates up to `2025-11-25`, which is what Claude Code 2.1.287 asks for), and accepts single messages and batches both (a batch is split into lines by the HTTP layer; its stream ends when every request in it is answered).

The endpoint path is **`/mcp`**. E1 exposes it as `cua agent run --http <host:port>` (also `cua serve --http`), E3 behind the relay as `https://<relay>/d/<device>/mcp`, which the relay rewrites to `/mcp` before forwarding. It behaves as the revision says:

| Request | Behaviour |
|---|---|
| `POST` with an `initialize` request and no session header | Opens a session: a new connection (runtime resolution, claim, broker, launch, spawn, `createServer`), the `InitializeResult` answered as a plain JSON body (`Content-Type: application/json`) with `Mcp-Session-Id: <connection's session id>` (the same random UUID the connection uses for `run/<session>` and turn metadata). If opening fails (nothing installed, claim conflict, broker or spawn failure, `assertSandboxFits`): `500` with a JSON-RPC error body, code `-32000`, message `cua: <code>`, and no session. |
| `initialize` with a session header | `400`. |
| `POST` carrying one or more requests, with a session header | Written to the connection's `input`. The response is `Content-Type: text/event-stream` with `Cache-Control: no-cache`; the response to each request in the body goes on this stream and the stream ends once all are answered (routing rule below). |
| `POST` carrying only notifications or responses | Written to `input`; `202 Accepted`, no body. This is how elicitation answers and `notifications/cancelled` arrive. |
| `GET` with a session header | Opens the session's standing SSE stream (one at a time; a newer GET replaces the older, which ends, because a client reconnecting after a silent drop must not be refused by a stream the server has not yet seen die). Server-initiated messages not attributable to an open POST go here, and a `Last-Event-ID` header replays what the named stream had not delivered (resumability below). |
| `DELETE` with a session header | Ends the session: `close('eof')` on the connection, `200` once `closed` settles, which is after the claim, the broker socket, the approval file and the run entry are released (its code and `listingLeftover` are logged, not returned). The session id answers `404` from the moment DELETE is accepted. |
| Session header missing (not `initialize`) | `400`. Unknown or ended session id: `404` (the client re-initializes, per the revision). |
| Any method without a valid bearer | `401`, before anything else is read. `Origin` present and not an allowlisted origin (`CUA_AGENT_ALLOWED_ORIGINS`, comma-separated, empty by default; `null` is never allowlisted): `403`. Requests without `Origin` (non-browser clients) pass. |
| `initialize` when the session cap is reached and no session is Idle | `503` with a JSON-RPC error body, code `-32000`, message `cua: session limit reached (<n>)`. |
| `POST` whose body is not valid JSON | `400` with a JSON-RPC parse error body; no session effect. |

**Routing rule.** Two kinds of message leave a connection. A *response* (a message with `id` and `result` or `error`) goes to the POST stream whose body carried that request id; the HTTP layer records id → stream when it parses the POST and closes the stream when all its ids are answered. A *server-initiated request or notification* (the vendor's `elicitation/create`, progress, log notifications) goes to the oldest open POST stream of the session, else the GET stream, else a per-session buffer drained into the next stream that opens; the buffer is capped at **16 MB** and a session whose buffer would exceed it is closed as `eof` with a logged reason. Responses never go on the GET stream (the revision forbids it outside resumption) and are never buffered as new messages.

**Small resumability.** Every event on a POST stream carries an `id:` line, `<stream>-<n>`, and the stream opens with a priming event (`retry: 15000`, `id: <stream>-0`, `event: priming` and `data: {}`: a named event with a non-empty body, which an SSE-normalising proxy keeps and a client ignores, Decision Log) so that a stream dropping before its first response still hands the client an id to resume from, and the client's two reconnection attempts are spaced to span a relay restart. Every open SSE stream (POST and GET) carries an SSE comment line (`: keepalive`) after any full 20 s interval in which nothing was written (so no stream is silent for 40 s), so a proxy's read timeout and a NAT's idle timer never cut a long `js` call. When a POST stream drops before its requests are all answered, the HTTP layer keeps the responses that arrive for those ids until a client `GET` with `Last-Event-ID` naming that stream replays them, in order, after which the retained set is cleared. Claude Code's bundled client reconnects a dropped POST stream only when it has received an event id, which is why the ids are there; a dropped stream with no later GET loses nothing until the session itself ends. The GET stream itself is not resumable beyond reopening it (its messages are buffered by the rule above).

**Session end.** A session ends by `DELETE`, by the connection closing on its own (runtime exit, failure: its open streams end, the session is removed, later requests get `404`), by a signal to the process (every session closes as `signal`), or by idling. **Idle** means: no request for 15 minutes *and* no open POST stream *and* no pending elicitation (a server request awaiting the client counts only while some stream of the session, POST or GET, is open, and while one is pending with no stream open, requests left on dropped streams do not count either, because a cell blocked on an approval cannot progress without the client: a client that vanished mid-approval holds no stream and must not hold the runtime forever); an idle session closes as `eof`, because a cloud client that vanished would otherwise hold a vendor runtime forever, while a long `js` cell or an approval waiting for a human never counts as idle. The cap is **1 concurrent session** per process by default (`CUA_AGENT_MAX_SESSIONS` overrides; the owner raises it for experiments), because every session is a runtime on the same mouse, keyboard, front window and Chrome extension, and two agents driving one Mac interfere. When `initialize` arrives at the cap, the oldest Idle session (no task, no open stream, no pending elicitation, whatever its age) is evicted first; only when every session is active does the request get `503`. This is what keeps headless `claude -p` runs, which may exit without a DELETE, from locking the device for 15 minutes. Both numbers are limits on resource use, environment-overridable and documented.

### Connections inside one process

`serve()`'s per-connection half becomes `openConnection({home, env, sessionId, input, output, …})` in `src/mcp/connection.mjs`, returning `{sessionId, closed, close}`; it resolves the runtime itself (per session, so a `runtime use` or a first `cua install` takes effect on the next session without restarting the agent; invalid settings fail the open with a clear code), and releases its claim, broker, approval file and run entries before `closed` settles. The stdio `serve` is then: sweep, signal handlers, one `openConnection` on `process.stdin`/`stdout`, exit code (1 on `listingLeftover`, as today). The HTTP mode is: sweep, signal handlers, a listener, one `openConnection` per session. The sweep runs once per process start, never per session (a sweep removes only dead owners, but it is a directory walk the listener need not repeat). The seams `serve` exposes for tests today (`keychainHelper`, `prepareLaunch`, `chrome`, `listBackends`) are parameters of `openConnection`, and `serve` forwards them, so `test/serve-cli.test.mjs` and the probes keep calling `serve` unchanged.

### Credentials and the device record

Enrolment produces one secret and two credentials derived from it, one per leg, so that the copy a cloud VM holds cannot be used to impersonate the Mac. `cua remote enroll [--relay <wss url>] [--rotate] [--json]` writes `$CUA_HOME/remote/device.json` (mode 0600, directory 0700): `{schema: 1, deviceId, secret, relayUrl?, enrolledAt}`, where `deviceId` is 16 random bytes base64url and `secret` is 32 random bytes base64url. From the secret:

```
deviceCredential = hex(HMAC-SHA256(secret, "device"))     // the agent presents this to the relay (E3)
clientCredential = hex(HMAC-SHA256(secret, "client"))     // the cloud client presents this to the endpoint
```

`enroll` prints, once, the client credential (for `claude mcp add`) and the exact line to paste into `relay/devices.json`: `"<deviceId>": {"deviceCredentialSha256": "<hex>", "clientCredentialSha256": "<hex>"}`. With `--json` it prints `{deviceId, clientCredential, devicesEntry, relayUrl}`. Re-running `enroll` on an enrolled device refuses (`remote_already_enrolled`) unless `--rotate`, which replaces the secret (the relay line and the client registration both change) or, with only `--relay` given, updates `relayUrl` in place without rotating. `cua remote show [--json]` prints the device id, relay URL, enrolment time and the `devices.json` line (hashes only); no command prints the secret or the client credential again.

The endpoint checks the bearer against the client credential derived from its own secret; the relay checks the bearer against `clientCredentialSha256` and **forwards the `authorization` header unchanged**, so the agent re-checks it and E1's handler is literally the same code on both paths (defense in depth; no "pre-authenticated" flag exists). The relay checks the agent's WebSocket bearer against `deviceCredentialSha256`. Comparison is constant-time everywhere (`crypto.timingSafeEqual` on equal-length buffers; unequal length is a mismatch without comparing). `agent run --http` without an enrolled device refuses to start (`remote_not_enrolled`, hint: run `cua remote enroll`).

Exposure the README states: the client credential sits in plaintext in `~/.claude.json` on the client machine (the cloud VM is the credential store), appears in the shell history of whoever ran `claude mcp add`, and, like every MCP payload including screenshots, is visible to the relay operator after TLS termination. Per-client, revocable credentials and accounts are the first thing to add when devices are shared; out of scope.

### The relay and the agent

The relay keeps one map, device id → the device's WebSocket, plus the device table it was started with (`relay/devices.json`: `{"<deviceId>": {deviceCredentialSha256, clientCredentialSha256}}`, hashes hex, edited by hand in v1 from `enroll`'s output). It has no session state. Each HTTP request to `/d/<device>/mcp` is a **channel** on that device's WebSocket, and the agent answers it with its E1 handler unchanged. The envelope, JSON text frames:

```
relay → agent   {ch, t: "open", method, path, headers}     path is always "/mcp" (rewritten); headers lower-cased, see the forwarded set below
relay → agent   {ch, t: "body", data}                      data: base64 chunk
relay → agent   {ch, t: "end"}
agent → relay   {ch, t: "head", status, headers}
agent → relay   {ch, t: "data", data}                      one SSE event or JSON body chunk, base64
agent → relay   {ch, t: "end"}
either          {ch, t: "abort"}                           the HTTP client went away / the handler failed; the receiver fires the channel's AbortSignal
agent → relay   {t: "hello", deviceId}                     first frame after the WebSocket opens (the device credential is in the connect request's Authorization header)
```

Headers forwarded in `open`: `authorization`, `mcp-session-id`, `accept`, `content-type`, `last-event-id`, `mcp-protocol-version`, `origin`; nothing else. A channel id is an integer the relay allocates per device, unique while the WebSocket lives. The relay translates between HTTP and frames and nothing else; a device with no live WebSocket answers `503 device offline`. Two WebSockets for one device: the newer wins and the older is closed with code 4001 (`replaced`); a `hello` whose device id is not the authenticated device closes with 4003. **Liveness:** the relay pings every WebSocket every 25 s and closes it after two missed pongs; the agent runs the mirror watchdog (no ping for 60 s → close and reconnect), so a NAT or proxy that drops an idle socket is noticed on both ends within about a minute. The relay listens on `--port` for both the HTTP endpoints and the WebSocket path **`/ws`**; `relay/README.md` states what the TLS proxy in front must do: pass WebSocket upgrades on `/ws`, disable response buffering for SSE (`X-Accel-Buffering: no` is set by the relay; nginx also needs `proxy_buffering off`), and a read timeout above the longest `js` call the owner expects (the agent's own streams keep flowing, so 10 minutes is a safe floor).

The agent (`cua agent run`, the process the launchd job keeps alive) connects to `relayUrl` with `Authorization: Bearer <deviceCredential>`, sends `hello`, serves channels through a request/response adapter over the E1 handler, and reconnects on loss with backoff 1 s doubling to 30 s. It does **not** reconnect after close codes 4001 or 4003: it logs the reason and exits 0 (a deliberate stop, which the launchd job's `KeepAlive {SuccessfulExit: false}` does not restart), so two agents for one device (a terminal `agent run` beside the launchd job) do not replace each other forever; `$CUA_HOME/state/agent.lock` (pid, link(2)-published like the registration lock) makes the second `agent run` on one Mac refuse with `agent_already_running` naming the pid, whatever its flags. Sessions belong to the agent process, not to the WebSocket: a reconnect keeps every session; channels open at the moment of loss are aborted (their SSE streams end; responses to their unanswered ids are retained for `Last-Event-ID` replay, and a stream that completed into a link not yet known dead keeps its events for 90 s for the same replay; the connection's server-initiated messages queue in the session buffer until the next stream). The idle rule still applies, so a cloud client that never returns releases the runtime.

`cua agent run [--http <host:port>] [--relay]`: `--http` is E1's LAN mode, `--relay` E3's (requires `relayUrl` in `device.json`, else `remote_no_relay`); both may be given; neither is a usage error. The `ws` package is imported lazily inside the relay code path only, so `cua serve` and `agent run --http` (and the plugin copy, which runs without `node_modules`) never load it.

### launchd

`cua agent install [--http <host:port>] [--surfaces <list>] [--json]` writes `~/Library/LaunchAgents/com.ssfskim.cua.agent.plist`: `ProgramArguments` = the resolved `node` and `bin/cua.mjs agent run`, followed by `--relay` when `device.json` has a `relayUrl` and `--http <host:port>` when given; `install` with neither (no relay enrolled, no `--http`) refuses with `agent_nothing_to_serve`. `KeepAlive` `{SuccessfulExit: false}` (launchd restarts a crash or a refusal such as `agent_already_running`, which then takes over once a terminal agent stops, but not the agent's deliberate stops: a signal shutdown or close code 4001/4003), `RunAtLoad` true, `StandardOutPath`/`StandardErrorPath` = `$CUA_HOME/state/agent.log`, `EnvironmentVariables` carrying `CUA_HOME` when set and `CUA_SHIM_SURFACES` from `--surfaces` (default `computer,browser`, since remote use is for the browser as much as the desktop). Paths are XML-escaped in the plist; the resolved `node` path is recorded in `agent status` output because a Homebrew or nvm upgrade that moves it breaks the job (the README says to re-run `install` after upgrading node). It loads with `launchctl bootstrap gui/$UID <plist>`; `uninstall` runs `launchctl bootout gui/$UID/com.ssfskim.cua.agent` then removes the plist; `status` reports the job's pid or absence from `launchctl print gui/$UID/com.ssfskim.cua.agent`. A GUI-session job is the point: `docs/evidence/second-mac-acceptance.md` records that TCC prompts and Keychain access need the console session, and `launchctl bootstrap gui/` is how a process gets one without a terminal.

`cua doctor` gains four rows: `agent.installed` (plist present and parseable by cua's own reader, naming its program path and node path), `agent.running` (launchd reports a pid), `agent.enrolled` (`remote/device.json` present, mode 0600, naming the relay URL or "local only"), and `agent.console` (the user's session is the console session and the screen is not locked, read from `CGSessionCopyCurrentDictionary` through a tiny Swift or `osascript`-free helper already available to doctor: `kCGSSessionOnConsoleKey` and `CGSSessionScreenIsLocked`). Doctor gains a fourth status, **`skip`**: "not applicable here"; it is neither a failure for `ok` nor counted by `summarize` as blocked, and the CLI prints it like the others. All four `agent.*` rows read `skip` on a Mac that never enrolled and has no job, with the hint "run cua remote enroll / cua agent install" (a locked Mac that does no remote control is healthy); otherwise `agent.console` reads `fail` when locked or off-console, because that is exactly the state in which remote control silently does nothing. The same check backs a classified refusal: a `js` or `js_reset` call arriving over HTTP while the console is locked or the session is not on the console is answered with a tool error `console_locked` ("the Mac's screen is locked or the session is not on the console; unlock it and retry") instead of the vendor's confusing failure.

### What Phase E does not do

No TLS termination in the relay (it sits behind a reverse proxy); no accounts, device lists or credential rotation beyond `enroll --rotate`; no per-client credentials; no change to the vendor runtime, the host notes' content (except the one README paragraph on remote use), the profile registry or secrets. Secrets work remotely exactly as locally, because substitution happens in the agent process on the user's Mac, under the same requirement that the console be unlocked (the login Keychain is locked with the screen).

## Phase F design: a Linux pin

Spike #12 established the facts (evidence doc, sections (a)–(e)); the arm64 deb was inspected afterwards and matches the amd64 one in layout (same `@oai/*` files by hash, aarch64 binaries in the same places). The design is the set of decisions on top of them.

**Source and trust.** Two Linux pins, `runtime/releases/26.928.40906-linux-x64.json` and `26.928.40906-linux-arm64.json`, from the vendor's public APT pool. **Pin schema.** `parsePin` branches on `platform`: `darwin` keeps schema 1 as is; `linux` requires `archive.format: "deb"`, `components` (each may be a directory or a file; `install.mjs`'s "component directory" check becomes "component exists"), `layout` with the keys above (`LAYOUT_KEYS` becomes per-platform: no `skyServiceApp`, no `ipcClient`; `skyLinuxBin` added), no `signing`, `notes` optional, and `chromePlugin.signing: []` permitted. The Chrome plugin source is taken from `chromePlugin.from` as on darwin, not listed under `components`.

**Extraction.** `install` recognises a deb by `archive.format`: `ar` extracts the `data.tar.xz` member into staging, `tar` with `xz` unpacks it, and the components and the plugin source are taken from the paths in the pin. `install` checks for `ar`, `tar` and `xz` before download and refuses with `missing_tool` naming the tool and its package (`binutils`, `xz-utils`). The verified tree, record and pointer are unchanged.

**Home, environment, launch.** Default home on Linux: `${XDG_DATA_HOME:-$HOME/.local/share}/cua` (`defaultHome(env, host)`). `buildLaunch` on Linux passes `DISPLAY`, `XAUTHORITY`, `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `XDG_DATA_DIRS` through the ambient allowlist; when `DBUS_SESSION_BUS_ADDRESS` is unset and `XDG_RUNTIME_DIR` is set it derives `unix:path=$XDG_RUNTIME_DIR/bus` (an SSH session lacks the former and has the latter); it does not set `SKY_CUA_SERVICE_PATH`, sets `OAI_SKY_LINUX_BIN` to the pinned helper and `CODEX_CLI_PATH` to `<release>/codex`. `cua login` prints the URL when `xdg-open` is absent. Because `DISPLAY` and `XAUTHORITY` reach the runtime, a model cell on Linux can talk to X directly; the host notes and README say in one sentence that the trusted wrapper is not a boundary on Linux (nothing changes today under the allow-all policy with no Linux secrets). **Sandbox default on Linux** (revised 2026-10-06 at F2, Decision Log under Phase F): `CUA_SHIM_SANDBOX` defaults to `disabled` when the computer surface is on and to `scoped` for the browser surface alone; an explicit value wins. Under a working scoped sandbox the pinned runtime refuses every `connect(2)`, unix sockets included, so the computer-use helper cannot reach X or the session bus; and where the kernel refuses unprivileged user namespaces (Ubuntu ≥ 23.10's AppArmor restriction) the vendor's sandbox fails open, so every scoped launch on Linux first runs doctor's probe (`bwrap --ro-bind / / true`, bwrap looked up on `/usr/bin:/bin`) and, where it does not pass, is refused with `sandbox_unavailable` instead of running unconfined: a scoped connection, and the standalone profile listing behind `cua profiles list` and `bind` (always scoped). A connection's own readiness listing runs under the connection's mode, so a `disabled` connection is never probed. Doctor's `sandbox` row reads `fail` for a scoped connection in that state, and `sandbox.userns` reads `skip` only when no scoped launch can happen (the connection is not scoped and the browser surface is off, so neither a connection nor the standalone listing would probe); otherwise a refusal reads `blocked`, naming the `sandbox_unavailable` refusal of `cua profiles list`/`bind`.

**Doctor on Linux.** `helper.live` and `helper.permissions` are replaced by `display` (`DISPLAY` set and `xdpyinfo` lists `XTEST`, `Composite` and `XFIXES`; `missing_tool` names `x11-utils` when `xdpyinfo` is absent), `accessibility.bus` (the session bus answers `dbus-send --session --print-reply --dest=org.freedesktop.DBus / org.freedesktop.DBus.ListNames` and the list contains `org.a11y.Bus`; the address is derived as in launch), `sandbox.userns` (`bwrap --ro-bind / / true` exits 0; otherwise `blocked` with the stderr, naming `kernel.apparmor_restrict_unprivileged_userns` when the distro is Ubuntu ≥ 23.10); the darwin group-container socket, LaunchServices, `lsof` and `plutil` paths are never consulted; `secrets.*` reads `skip` (unsupported platform). `countLiveHosts` (`src/profiles/chrome.mjs`) matches the Linux host path (`extension-host/linux/<arch>/extension-host`) and reads processes with `ps -eo pid,args`; `profiles open` uses `google-chrome --profile-directory=<dir>` detached; `verify.mjs`'s native-socket holder step reads `skip` on Linux (the helper is a child process, not a socket holder).

**Chrome.** `browsersFor({host, env, userHome})` replaces the `BROWSERS` constant. On darwin it returns today's table unchanged. On Linux it returns, under `${CHROME_CONFIG_HOME:-${XDG_CONFIG_HOME:-~/.config}}` for Chrome's own entries and `${XDG_CONFIG_HOME:-~/.config}` for the others (`CHROME_CONFIG_HOME` is Chrome's variable, honoured by Chrome only):

The manifest goes to `<dataDir>/NativeMessagingHosts/com.openai.codexextension.json`; its body is unchanged. The vendor's table also lists `google-chrome-for-testing`; cua omits it because no user profile lives there. Keys are what `registration.json` and the backups record, so the darwin keys keep their names and the three new ones are Linux-only. The desktop-presence probe looks for `/usr/lib/chatgpt` and `~/.codex`. The README says: deb or rpm Chrome, never Flatpak or snap.

**Secrets.** No Linux secrets backend: `openSecrets({host, …})` reports `unavailable` with code `secrets_unsupported_platform`; `secrets_list` returns that; a `{{secret:…}}` reference in any input refuses before dispatch with the same code (the Linux `type_text` shape is never matched); `cua secrets set|list|remove` print it and exit 1. A libsecret backend is a later initiative.

**Surface text.** `hostNotesFor(surfaces, {platform})` returns a second constant on Linux that replaces the macOS-only sentences: apps are bound by window (`cua.getApp({windowId})`, `listWindows`), `setValue`/`selectText` do not exist, `paste` types, key names are X keysyms, there is no per-app approval (one connection can drive every window of the session; the owner's allow-all decision, no allowlist in the sky wrapper), and the trusted wrapper is not a boundary on Linux. The 2,048-character budget test covers both constants.

**What Phase F does not do.** Wayland, multi-user VMs (shared `/tmp/codex-browser-use`, spike (e)), a Linux secrets backend, Flatpak or snap Chrome, Linux support for the relay and agent (platform-neutral Node, expected to work, untested until a later initiative; done since by #58, see Progress).

## Phase G: one server, every device

Board: issue #70 (design approved by the owner 2026-10-07; it also settles #69's open question). This section is self-contained: its own purpose, design, acceptance, interfaces and milestones; the Progress list, the Decision Log and Surprises & Discoveries carry its living record beside the earlier phases'.

### Purpose

Phase E made a device reachable as its own HTTP MCP server, which a client registers per device (`claude mcp add --transport http cua_repl …`: one registration per device, a reconnect for each, the credential expanded into `~/.claude.json`). With the plugin installed, that also means two servers whose tools differ only by name (`mcp__plugin_cua_cua_repl__*` for this machine, `mcp__cua_repl__*` for the device), which agents mix up. Phase G makes **one server reach every device**: the plugin's own `cua_repl` (stdio `cua serve`) keeps its tool names and gains a per-connection **target**, `local` by default, switched with `devices_use` to any device in a local registry. Seen from the user's chair: `/secret CUA_DEVICE_<id>` and `cua devices add mini …` once (or `cua devices import ~/.config/cua-relay/mini.mcp.json`), then in any session "on the mini, open my school calendar" is `devices_list`, `devices_use mini`, the usual `js` work, `end_task`, `devices_use local`, with no registration and no reconnect. The standalone HTTP registration stays supported for clients without the plugin.

What stays as it is: `js`'s schema (no `device` argument: the target is connection state, so the vendor's tool and every prompt that teaches it stay untouched), the device side's HTTP surface (Phase E) apart from one response header, the relay, the credentials' derivation, and the per-connection runtime rule (the remote target is a session on the device owning the device's runtime; the local runtime stays owned by the local connection).

### Design

**Target and tools.** A stdio connection holds `target` (`local` or a registry name) and, for a remote target, at most one open device session. Two tools join the list on stdio connections only (the HTTP agent's sessions never list them: a device driving a third device through itself would hide a hop and a credential):

- `devices_list` (no arguments): `{status: "ok", current, devices: [{name: "local", status: "online"}, {name, deviceId, relay, status, code?}, …]}`. Each configured device is probed concurrently with a 3 s timeout and reads `online`, `offline`, `locked` or `unauthorized`, with a `code` where it says more (`credential_missing`, `relay_unreachable`, `timeout`). A probe never opens a session (an `initialize` spawns the device's runtime and, at the device's cap of 1, could evict another client's idle session): it is one authenticated `POST /mcp` of a `ping` request without `Mcp-Session-Id`. The relay answers `503` (`device offline`) when the device has no link and `401` on a credential it does not know; a device answers `401` itself on a mismatch and otherwise `400` (no session header), which reads `online`, or `locked` when the response carries `Cua-Console: locked` (the device side, G2: set on that session-less answer when the console check reports locked or off-console; an older agent never sends it, so it reads `online` and its `js` still answers `console_locked`). A network failure or a timeout reads `offline` with its code.
- `devices_use {device}` (`device`: `local` or a registry name): refused with `task_open` while a task is open on the current target (local: the task lifecycle is not `idle`; remote: a `js`/`js_reset` was sent since the session's last `end_task` answered `ended` or `noop`); naming the current target is a no-op `ok`. Switching to a device reads the registry and the credential, opens a device session (below) and answers `{status: "ok", device, previous}` with the device's own host notes (its `InitializeResult.instructions`, which then apply) in the text and, as `hostNotes`, in the structured content (Claude Code shows the model only the latter on success; G4); any failure leaves the target unchanged and answers a classified tool error. Switching away from a device ends its session (DELETE).

`js`, `js_reset`, `end_task`, `profiles_list` and `secrets_list` route to the target. With a remote target each is sent to the device session as a `tools/call` with the client's own `params` (including `timeout_ms` and `_meta`), and its result is relayed unchanged (the device already corrected images and redacted tokens), tagged `_meta["cua/device"]: <name>`; a JSON-RPC error is relayed as an error. `end_task` on a device, once answered, also ends the device session (DELETE), so the device's runtime and `run/` entry are freed for other clients the moment a task ends; the next `js` opens a fresh session lazily. Classified errors are tool errors (`statusResult`, `isError`) whose `code` is one of: `task_open`, `device_unknown`, `credential_missing`, `device_offline` (relay `503 device offline`, a `502` from its proxy, the relay unreachable, or the resume budget spent), `device_unauthorized` (`401`), `session_limit` (`503` session limit), `device_session_ended` (the device answered `404`, or ended the session, while a task was open there: its REPL state is gone; the next call opens a new session), `device_protocol` (an answer the client cannot read), `device_failed` (the device answered `500` or refused `initialize`, e.g. nothing installed there; G2). `console_locked` arrives from the device as its own tool result and passes through. A call the device certainly never received (a `404` on its own POST, or the session already gone before sending; G3 narrowed this from "any `404`", Decision Log) while no remote task is open re-opens the session once and retries the call; its result then says, in the text and as `_meta["cua/deviceSession"]: "new"`, that the device session is new and its REPL state fresh (rebind apps and tabs), so the model never assumes earlier state (the coordinator's ruling, 2026-10-07). Every call that opens a session lazily (the first `js` after `end_task`) says the same. `tools/list` is the local list plus the two tools; `profiles_list` is listed by the local surfaces, as today (the plugin enables the browser surface).

**The device session** (`src/remote/client.mjs`, an MCP Streamable HTTP client over Node's built-in `fetch`; no new dependency, so the plugin copy runs without `node_modules`). It speaks to the endpoint `<relayUrl>/d/<deviceId>/mcp` with `Authorization: Bearer <credential>` on every request, under the rules of the Phase E server it talks to:

- *Open*: `initialize` carrying **the local client's own initialize params** (protocol version, capabilities, client info), so the device's runtime sees an elicitation-capable client and the turn metadata names the real client; then `notifications/initialized`; every later request carries `Mcp-Session-Id` and `MCP-Protocol-Version` (the negotiated version). Once open it holds the standing `GET`, as Claude Code's own client does (it keeps the session from reading Idle-for-eviction 60 s into a task, the Phase E rule), reopened with the backoff below while the session lives.
- *Requests*: proxy-owned ids from the session's own counter (the local client's ids never reach the device). The answer is a JSON body or an SSE stream, parsed per the SSE format (`id:`, `event:`, `data:` lines, comments ignored, the named `priming` event recorded for its id and otherwise ignored). The response settles its request; server-initiated messages on any stream (POST or GET) go to `onMessage`.
- *Resumption*: when a POST stream ends or errors before its response, the client `GET`s with `Last-Event-ID: <the last id seen on that stream>` and reads on until the response arrives; a failed attempt retries after 1 s doubling to 15 s within a 90 s budget (the device keeps a dropped stream's events that long, `streamGraceMs`), across a `502` from the TLS proxy and `503 device offline` while the relay or the agent reconnects. A spent budget answers `device_offline`. A POST that fails before carrying any event id (the device sends the priming event first, so the request may not have reached it) is answered `device_offline` and never resent: a `js` cell must not run twice.
- *Cancellation*: a local `notifications/cancelled` for a routed request becomes the device's `notifications/cancelled` with the proxy id.
- *Server requests*: an `elicitation/create` (or any other request) from the device is written to the local client under a fresh id `cua-device-<n>`; the local client's answer is mapped back to the device's id and POSTed (`202`). The local `persist` rewrite does not apply (the device's own server applies its persist mode). Notifications pass unchanged.
- *Close*: `DELETE` with a 2 s bound on `end_task`, on switching away, and at the local connection's close (before `closed` settles); a failed DELETE is logged, never fatal (the device's idle rule frees the session).
- Nothing the client logs or returns carries the credential or any request header value; diagnostics name the device and status codes only.

**Registry** (`src/remote/devices.mjs`): `$HOME/.config/cua/devices.json`, mode 0600 in a 0700 directory, exactly the ticket's shape `{"<name>": {"deviceId": "…", "relayUrl": "https://<relay origin>"}}`. Names match `^[a-z0-9][a-z0-9_-]{0,31}$`; `local` is reserved. `relayUrl` is stored as the relay's origin; `add` also accepts the enrolment's `wss://<relay>/ws` (and `ws`/`http` for a LAN relay) and normalises it. The credential is **not** in the registry: it is the secret store's `CUA_DEVICE_<deviceId with - as _>` (`clientSecretKey`, `src/remote/device.mjs`), read by the server process (the store's `read`) at each session open and probe, never by the model's cells. The registry and the credential are read at every `devices_list`/`devices_use`, so `cua devices add` takes effect without a reconnect.

CLI: `cua devices add <name> --relay <url> --device <id> [--replace] [--json]` (refuses an existing name without `--replace`; warns, without failing, when the credential key is absent, naming the `/secret` step); `devices remove <name> [--json]` (the registry entry only; the stored credential is the owner's to remove with `cua secrets remove`); `devices list [--json]` (name, device id, relay, whether the credential is stored; never probes, never a value); `devices import <file> [--name <name>] [--replace] [--json]`, which reads a client config of today's shape (`{"mcpServers": {"cua_repl": {"type": "http", "url": "https://<relay>/d/<id>/mcp", "headers": {"Authorization": "Bearer <credential>"}}}}`, or the one server entry when there is a single one), derives the device id and relay from the URL, writes the credential to the store under its key (reporting `stored`, `unchanged` or `replaced`, never the value), and adds the registry entry under `--name` or the file's basename less `.mcp.json`. `remote enroll --json` and `remote show --json` gain `devicesAddCommand` (the `cua devices add` line for a client) beside `clientRegisterCommand`.

**The reserved prefix** (closes #69). Keys starting `CUA_DEVICE_`, in any letter case (macOS's default file system would open `CUA_DEVICE_x` for `cua_device_x`; G1 review, 2026-10-07), are device credentials: the model-facing `secrets_list` omits them (in `connectionSecrets`, so local and device sessions both), and a `{{secret:CUA_DEVICE_…}}` reference is refused in both trusted services (`sky`, `browser`) before the store is read, with the code `secret_reserved` and nothing entered. `cua secrets list` (the owner's terminal) still shows them. A device enforces this once it runs this version; the client side, where the credential lives, enforces it at once.

**Host notes.** One rule joins the stdio notes (only where the device tools exist), within the 2,048-character budget the test measures with the vendor's 63-character first line, in substance: `devices_use` switches every tool to that machine, whose notes (in its result) then apply; `end_task` before switching. The macOS notes for `computer,browser` are at 1,980 characters today, so the rule's room comes from tightening existing lines without dropping any rule the tests name.

**Skill and README.** `cua-remote` Part B collapses to: the owner stores the credential (`/secret <clientSecretKey>`), `cua devices add` (or `import`), then `devices_list` / `devices_use <name>` in any session; the standalone registration stays as the route for a client without the plugin. README's remote section leads with the plugin route and keeps the standalone one second.

## Surprises & Discoveries

- 2026-10-06 (acceptance 6 through ngrok): the tunnel's edge re-serialises SSE. Bytes leaving the relay on loopback were `retry: 15000\nid: 2-0\ndata: \n\n`; the same stream through `*.ngrok-free.dev` arrived as `id: 3-0\nretry: 15000\n\n`, the empty `data:` line dropped and fields reordered (response events arrive as `data: …\nid: …`). An event with no `data` line is never dispatched by an SSE parser (WHATWG: empty data buffer, return), so Claude Code never saw the priming id, did not resume the `js` call whose stream the relay restart cut, and hung on it (ngrok's request log: the POST cut at 13.6 s, then only the standing GET reconnecting, with no `Last-Event-ID`). Keepalive comments are likely dropped the same way; they still keep the proxy's upstream leg busy.
- 2026-10-06 (E2 acceptance 5): the launchd-started agent on the mini reached Accessibility, Screen Recording and Chrome with no prompt (E2's delegated unknown: no dialog appeared; nothing was answered). The locked-screen clause was proven on the MacBook, which the owner's absence had locked (`IOConsoleLocked` true on `Root`, `CGSSessionScreenIsLocked` true in the session): doctor `agent.console fail` and a `js` answered `console_locked`, from a temp-home agent on loopback. The mini was not locked on purpose, because nobody could unlock it for E3 and E4.

- 2026-10-06 (E1 LAN proof): the mini's application firewall is on ("allow signed software" both enabled) and lists only nvm's `node` v24.18.0 as allowed for incoming connections; Homebrew's `node` 26.4.0 (the one on `PATH`) is not listed, so an `--http` listener under it would raise the "accept incoming connections?" dialog at the console.
