# Own-browser-service benchmark controller

You are running the **agent-level benchmark**, not the deterministic parity corpus. Its question is whether cua's replacement browser service preserves task outcomes and latency through the same plugin/device route. Source contract: `docs/doperpowers/specs/2026-10-13-own-browser-service-design.md`, “Benchmark baseline and comparison” and M0/M5.

## Inputs and route

The dispatcher supplies `service` (`vendor` or `cua`), `profile` (the mini's prepared key, normally `ssfs`), resident checkout commit, runtime release, and an evidence directory on this Mac. Do three consecutive runs, serial and unattended, with the same model and profile. The owner/session must first make that mini profile ready on **cua's extension route**. If readiness or service attestation disagrees, stop and report it; a run through the old ChatGPT extension is not this baseline (spec's execution pre-flight discovery).

Use the cua plugin: finish any open task, `devices_use mini`, `profiles_list`, select exactly the supplied key's `extensionInstanceId` with `cua.getBrowser`. Only tabs you create are yours to close. Call `end_task` between runs and at completion. The resident agent serves vendor until the session updates its checkout/agent at M5; setting a shell variable in your client does not switch it. Record the supplied resident commit and the selected browser's documentation header/marker as the attestation. Vendor has no `cua browser service <version>` marker; cua requires it. Never restart/reconfigure the resident agent to make a benchmark run.

## Recorder and consistent timing

On this Mac, read `test/browser-parity/bench-recorder.js` from the repository. Evaluate its complete contents unchanged in the first `cua_repl.js` cell of each run, after selecting the mini device and before any browser API calls. It defines persistent `globalThis.bench` without filesystem access. After ending a completed run, reset your own REPL with `js_reset` before initializing the next run's recorder; reinitializing an existing recorder refuses to erase its data.

Call `bench.start(taskId)` before a task. Wrap **every browser API call** in `await bench.call(toolName, kind, () => browserCall(), note)`, including selection, navigation, reads, screenshots and actions. The recorder captures the task ID, call-start ISO timestamp and `performance.now()` duration around that exact awaited call. A rejected call is recorded with its duration and error message, then rethrown; catch it only to decide the task's outcome. Do not time judged calls in the shell or time a whole REPL cell containing several calls.

For example, after `bench.start('T1')`, use `await bench.call('tab.goto', 'action', () => tab.goto(url), 'open fixture')`, then separately record each read. Finish with `bench.done(answer, ok)`. For fixture tasks awaiting ground-truth review, use `bench.done(answer, null)` at their actual completion; after T8 read the ground-truth section and call `bench.score(taskId, boolean)` for T1–T8. Scoring changes only correctness, preserving the original completion timestamps. MiniWoB answers can be objects carrying raw/discounted rewards and the reason; score immediately from the observed completion and raw reward.

`profiles_list` and `end_task` are MCP tools outside JS. Measure each externally with shell-side start/end clocks and import that measurement through `bench.recordExternal(toolName, kind, {t, ms, ok, note})` while T0 or T9 is active. For T0, retain the measured `profiles_list` result until the first JS cell has loaded the recorder, then start T0 and import it. These externally timed rows cannot enter judged tasks. T9's final dump can use a JS cell after `end_task`; finish that export-only task with another `end_task` outside the benchmark.

Call `bench.dump()` after the fixture block has been scored, after the MiniWoB block, and after T9. It returns `{calls, outcomes}`: `calls` is complete cumulative JSONL text and `outcomes` is the matching object. Transfer each snapshot to this Mac and write `calls.jsonl` exactly from `calls` and `outcomes.json` by JSON-encoding `outcomes`; later complete snapshots replace earlier files. **Never write, relabel, reconstruct or edit rows by hand.** If tool output truncates a dump, export fixed slices of `JSON.stringify(bench.dump())` and concatenate them unchanged rather than guessing missing rows. The block snapshots bound how much an interrupted session can lose.

## Evidence contract

For each run write `<evidence>/<service>/run-<1|2|3>/`:

- `meta.json`: `{service, commit, profile, model, runtime, started, finished, attestation}`. Times are ISO timestamps. Model/runtime/profile stay identical across both service groups; commit pins each group's implementation. `attestation` contains `{route:'resident-agent', residentCommit, selectedBrowserHeader, marker}`; vendor marker is null.
- `calls.jsonl`: write the recorder's `calls` string verbatim; its call rows are `{t,task,tool,kind,ok,ms,note}` (failed calls also carry `error`). `t` is call **start**, `ms` measured elapsed; `kind` is `action|observe|wait|other`. The recorder adds exactly one `{task,done,answer,ok}` completion row per task, including failures. Preserve actual timestamps: reasoning gaps are part of reported wall time, not judged tool time. Every call in T1–T8 and the MiniWoB tasks needs a finite, nonnegative `ms`; unmeasured calls invalidate judged timing. T0/T9 may have unmeasured durations because their timing is diagnostic only. Finalize fixture correctness through `bench.score` after T8; do not alter timestamps.
- `outcomes.json`: write the recorder's `outcomes` object, keyed by identical task IDs across runs, each `{ok:boolean, answer}`. Structured answers can contain `rawReward`, `discountedReward` and `reason`. Deferred `ok:null` values must be scored before final export; the recorder keeps `ok` identical to the done row. Failed/blocked tasks remain in both files, not silently omitted.

Keep notes about fixture data and observed errors, not unrelated tabs, credentials or approval content. Do not read secret stores, auth files, tokens or Chrome profile files to solve setup friction.

After run 3, run `node scripts/bench-summary.mjs <evidence>` on this Mac and return its output plus the evidence directory. With fewer than three runs in a present service group, the summarizer prints per-run measurements and `incomplete: <service> has N of 3 runs`, exits 1, and gives no verdict. Three vendor runs without cua end `cua runs: none`, not a parity verdict. With all six runs, judged timing is each task's tool-call time: sum the `ms` of its call rows, then compare medians over three runs. A task passes when cua's tool-time median is no more than vendor's plus `max(10%, 500 ms)` and cua's success count over its three runs is at least vendor's over its three. Wall time (first call to done mark) is printed beside tool time but not judged because it includes the controller's thinking. T0 setup and T9 cleanup are excluded from judged timing and call-duration validation; their outcomes still count. Success is the scored `ok` flag: fixture answers are scored against ground truth; MiniWoB uses completion with raw reward 1. Answers and rewards are recorded and printed, never compared: answer wording may vary, and discounted reward is time-dependent. One task outside that boundary yields `regression`. The summarizer rejects invalid or incomparable measurements rather than inferring absent data.
