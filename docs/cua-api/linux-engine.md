On Linux, some calls can answer in ways the document above does not list. Each such answer says what happened; do what it says before you act again.

If a call answers `<App> does not accept background input; use a dedicated desktop or activate the window first`, this desktop is shared (a person may be using it), the app ignores that kind of input while its window is in the background, and nothing was sent. A click on an element by its index is not refused this way, so it may still do what you need. Unless the user asked you to work in that window in front, say what you could not do instead of activating it.

If a drag answers with a sentence that begins `<App> began a drag and drop, which changes the desktop`, the drag started a drag and drop in a background window. The rest of the sentence says whether it was cancelled before the drop, or whether the drop may have happened anyway; read the window before you act again.

In a drag that starts in a Chrome or Electron window, the mouse button is not released until 450 ms after its press, however short the path, unless the page starts a drag and drop before then: a page that starts one after the button is up loses it. So a short drag there takes about 450 ms. If Chrome or Chromium is still busy at 450 ms, as it is while it starts a drag and drop, the button stays down for up to 650 ms after the press, and if no drag and drop has started by then, the drag answers with `the page may have started a drag that did not complete`: what you dragged may not have moved, so read the window before you go on. A page whose own code takes longer than about 450 ms to start its drag can still lose it while the drag answers with no such notice; when that matters, read the window after the drag. If the page starts a drag and drop after the button is up and the engine sees it while it still watches, for 700 ms after the release, the next reply says `Pending from your last drag, a late drag and drop:`, and your next input request is not run.

A drag and drop in Chrome ends with a short rest: before the button goes up, the pointer stays on the path's last point and is moved there twice more, 8 ms apart. A drag whose path goes on for more than about 350 ms after the page starts its drag and drop takes about 25 ms longer for it; a shorter one takes no longer. Without the rest, under heavy load, Chrome could drop the drag where the pointer was a moment before the end, on a target the path had already left, and still report the drop as made. The rest makes that rare, not impossible: when it matters where a drag dropped, read the page after it.

Under heavy load an Electron app's page can miss the last position of a drag and drop, so a drop that Electron reports as made, and the drag answers as done, may have landed where the pointer was just before the end, or nowhere on the page. When you need to be certain, check the target before you go on.

A failure that says nothing was sent sent no input: fix what it names, then you may send the request again. A failure that says a focusing click already reached the window may have moved its focus or caret: read the window before trying again. `Paste was sent once and could not be confirmed; read the field before retrying`, from `typeText` or `paste`, means the text may have arrived, now or a little later: read the field with `getAXState()`, and send the text again only if it is not there.

When `listWindows()` lists a window with `minimized: true`, it is minimized or on another desktop. `getAXState()` can still read its tree; a screenshot of it answers `Screenshot unavailable for window <id>.`, and input to it answers `Window <id> is minimized; activate it first`, with nothing sent. Unless the user asked you to work in that window, say that it is minimized instead of restoring it.

If a call answers `Window <id> matches several accessibility windows; close or retitle the duplicates`, windows of one app with one title and one size cannot be told apart, and that call was refused. Ask the user to close or retitle the duplicates; do not close their windows yourself.

If a call answers `showContextMenu was sent and no menu was seen within 1 s; the application may have shown its own menu or ignored the request; read the window before retrying`, the menu request went out and no menu was seen: take a screenshot to see whether a menu opened before you request it again. Only a request that runs an element's `showContextMenu` action checks for the menu, and a right click on an element with no visible point runs it; a right click at an element's visible point answers once it is sent, so take a screenshot before you choose a menu item.

A window state whose first line begins `Pending from your last drag,` says that your last drag may not have ended as it answered: a drag and drop may have started late, a drop may not have landed, its watch may have failed, or an idle drag handle was released where the pointer was; the sentence names which, and what may have changed. When it says the app `did not answer in time for its drop to be confirmed`, the engine could not confirm the drop, so it may or may not have landed where the drag ended. Read the window before sending input again; the next input request after it is not run, and its answer says so.

An accessibility tree that ends with `Accessibility tree truncated: at least <n> elements not shown (<reason>)` lists only part of the window: the reason says whether the element limit, the depth limit or elements that could not be read cut it, and the elements under each cut are missing. Act on what it lists, use a screenshot and coordinates for what it does not, or narrow what the window shows, by closing a panel or opening only the part you need, and call `getAXState()` again.
