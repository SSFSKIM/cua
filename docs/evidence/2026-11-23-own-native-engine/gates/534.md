# Gate #534: a web button pressed by element reaches its pointerdown handler

- **Ticket:** [#534](https://github.com/SSFSKIM/cua/issues/534), ruling 1168. Gate of #506 (the M5 sittings), task 10 of
  wave 1.
- **State:** the cell is built into the native matrix and unit-proven. Sitting C reads it. No engine change. **Open.**

## Ruling 1168: the pointerdown-only cell

**Why it exists.** Web UI kits often open menus and popovers on `pointerdown`, not `click`; Radix-style triggers are
the common case. After #258, cua still presses a web button by AXPress. The vendor posts a real click when the button's
point lands on its nested content (`F-helper-logic.md` §5, item 1). If Chromium's AXPress dispatches no pointer event,
cua misses these handlers where the vendor reaches them. Ruling 1153's principle applies: a known suspect gets a cell
that would catch it.

**The cells.**

- `chrome/frontmost/click.pointerdown`, on Chrome for Testing's scene page.
- `electron/frontmost/click.pointerdown`, on the Electron fixture.

Both are method cases in `scripts/native-matrix/plan.mjs` (`pointerdownCase`), each the last case of its target, so
every earlier row starts from the state it started from before. Each also gets its timing row
(`<scene>/method.click.pointerdown`).

1. **Prepare.** Find the button `Pointer target` by name and read the count in the status `Pointer status`
   ("Pointer downs: N"). If either is missing, the row is invalid and nothing is sent: the scene is not the matrix's
   variant.
2. **Act.** One element click by index, `__app.click(index)`, on both engines.
3. **Check.** Read the count again. The row passes when it rose by exactly one. The outcome records
   `{pointerDownOnce, rose}`.

**The page change.** Each scene gets one more line below every control: a button whose only handler is `pointerdown`
(no `click` handler), and beside it a `role="status"` span counting the pointer downs.

- Chrome: the page variant `pointerdown` (`scripts/native-matrix/fixtures/scene-page.mjs`, `POINTERDOWN_PAGE_HTML`).
  It is the shared page with the line after the status line and one more script. Its CSP adds only that script's hash.
- Electron: `renderer.js` adds the same line when the page's URL carries `?page=pointerdown`. `main.js` loads it so
  only when launched with `--cua-fixture-page=pointerdown`. `index.html` is unchanged.

The line sits below the status line, so it is outside both drag paths and every coordinate cell's point. Chrome's drag
points and `ELECTRON_FIELD_LAYOUT` lie in the text fields at the top. Neither moved.

**The gating.** The buttons appear only in the matrix's trees.

- `./run.mjs` brings the two scenes up with `MATRIX_SCENE_ARGS`: `--page pointerdown` for Chrome, and
  `--electron-arg --cua-fixture-page=pointerdown` for Electron.
- Nothing else passes them. The renderer goldens' recorder, sitting B's native-mac suite, the live hold, the cursor
  sitting and the spike bring up the shared page and the plain fixture.
- The shared page stays byte-identical (its hash is pinned in `test/scenes-counters-page.test.mjs`).
- Without the flag, the fixture's DOM is `index.html`'s alone.
- The scenes' targets (`PAGE_CONTROLS`, `FIXTURE_CONTROLS`) do not name the new controls. The finding cells and the
  fixed-state checks are unchanged.
- `test/native-goldens/` and the repl-parity tests are untouched.
- Changing the fixture's source changes its build directory (`44.9.0-<source hash>`), as any source change does. Both
  lanes of a run share one build.

**The judgement.** The rows are frontmost method rows, judged against the vendor's sample of the same run (the
`'reference'` mode, ruling 1116's pairing):

| vendor's count | cua's count | verdict |
|---|---|---|
| rose by 1 | rose by 1 | equal |
| rose by 1 | unchanged | **worse**: sitting C FAILs |
| rose by 1 | rose by 2 | **worse** |
| unchanged | unchanged | equal (the same failure) |
| unchanged | rose by 1 | better |

- **No departure may name either row** (`departures.mjs`, ruling 1168). A press that misses a pointer handler the
  vendor's click reaches is fixed, never declared.
- Each act is an element click, so it is a pointer cell. It goes through `steps.mjs` `guardLane` like every other, and
  is refused unsent when an alert overlaps the scene's window or holds the front or key
  (`test/native-matrix/alert-guard.test.mjs` lists both acts).

**Frontmost only.** These cells follow #258's and #259's choice: they do not run in the background. A background row is
judged against ground truth alone. It would ask cua to deliver a pointer into a background page, which nobody has
measured the vendor doing.

## Closing condition (open)

- **Both pass.** In sitting C's full run, both `chrome/frontmost/click.pointerdown` and
  `electron/frontmost/click.pointerdown` judge `equal` and qualify, every sample's count rising by one on both
  engines. Then Chromium's AXPress reaches pointerdown handlers. Record the run's URL here and close #534, citing the
  cells.
- **cua FAILs, the vendor passes.** cua's count is unchanged where the vendor's rose. This blocks #506 and goes to the
  design session: how cua presses a web control (for example a posted click where the vendor posts one) is a design
  call, not a harness one. The cell is then run again.
- **Both unchanged.** The rows are equal (no gap against the vendor), but neither engine reaches the handler. This
  does not block #506. It goes to the design session as a shared limit.
- **No verdict.** The gate stays open.
