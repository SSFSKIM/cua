# cua's own macOS native engine (#117; child 4 of #114)

## Purpose

On macOS, cua's computer surface (`cua.getApp(...)`, `getAXState`, `click`, `typeText` and the rest of the window API the model learns from `docs/cua-api/core.md`) is answered by OpenAI's native helper, `Codex Computer Use.app` from the pinned `@oai/sky` package: it reads the accessibility tree, numbers the elements, delivers input, captures the window, and holds the Accessibility and Screen Recording permissions the user granted. Because that helper accepts only the vendor's `node_repl` as a socket peer, macOS computer sessions are also the last sessions still served by the vendor's REPL host instead of cua's own (#116). After this work, cua's own engine, `cua Engine.app`, answers the same API behind the same contract, cua's own host serves every session on every platform, and `cua install` on macOS stops downloading the vendor runtime archive altogether.

Three things become observable that are not today:

- **Nothing of the vendor runs.** `ps` during a session shows `cua-engine`, cua's Node and no `SkyComputerUseService`, `node_repl` or vendor Node started by cua. `cua doctor` shows cua's engine, its build and signature, and the permissions granted to it.
- **A driven app stays where it is.** Clicking a button in a background app does not bring that app's window to the front or take the keyboard focus from the window the user is working in, and the user typing in their own window does not stop the agent. Today the vendor's click path activates the app, which the owner experiences as windows jumping forward (#162's investigation).
- **The same speed or better, measured.** Every operation of the native baseline (`docs/evidence/2026-10-14-native-baseline/`) is answered within the no-regression rule, and the three points the owner named (speed, finding elements, not interfering) are recorded against the vendor's engine on the same machine before the default changes.

How to see it: on the mini, with the plugin at the release this work ships, run a session that binds TextEdit, keep a Finder window in front, and ask for a click in the TextEdit document. The Finder window stays in front and keeps the keyboard, the click lands, and `cua doctor` names `cua Engine.app` as the engine. The vendor engine stays selectable with `CUA_NATIVE_ENGINE=vendor` until M6 retires it.

What is in scope: the macOS engine, its JS service, the switch of macOS computer sessions to cua's own host, the engine selection and attestation, the verification system, install and signing, the retirement of the vendor runtime on macOS including cua's own module tree for cells, and approvals on both platforms through one policy module. What is not: the Linux engine (`sky_linux` stays pinned and served by cua's own host until #171), the Windows target (cua drops it), audio recording (dormant in cua), the vendor's Skysight, Messages, Calendar, picture-in-picture, lock-screen auto-unlock, analytics and app-server features, a cursor overlay, and per-app instruction texts (the vendor ships its own; cua writes none in this work).

Terms used below:

- **Engine**: the native process that touches the Accessibility API, input and capture. The vendor's is `SkyComputerUseService` inside `Codex Computer Use.app`; cua's is `cua-engine` inside `cua Engine.app`.
- **Service**: the JavaScript that runs in the trusted worker of the REPL host and talks to the engine. The vendor's is `@oai/sky`'s `service.js` and `targets/mac/*`; cua's is `src/services/engine/`. cua's existing trusted wrapper `src/services/sky.mjs` (secret substitution) sits in front of either.
- **Facade**: the model-facing API in `src/cua-api/` (a port of `@oai/cua`'s `tinysky_alt`), which calls `nodeRepl.rpc("sky", {type: "setup" | "execute", ...})`. Unchanged by this work.
- **Skyshot**: the vendor's name for one observation of an app: its key window's accessibility text, optionally a screenshot. Kept as the name of the engine's observation result.
- **Scene**: one harness-owned window in one app family, used by the verification system (defined under "Verification system").
- **Lineage**: the engine's per-connection, per-app numbering of elements, in which an index keeps meaning across observations until the lineage ends.
- **Approved engine**: the one on-disk copy of `cua Engine.app` per Mac whose grants the owner confirmed, which every session and harness on that Mac serves in place (defined under "Install, signing and permissions").

## Design

### The contract kept, and what changes behind it

The facade's contract with the service does not change: `setup` returns `{target: "mac", methods: [the 11 names]}` and `execute {method, args}` returns what each method returns today (`R/A-contract.md` §1.2–1.4). The trusted wrapper `src/services/sky.mjs` keeps its pinned eligible shapes for secret substitution and its value-free error classification; the vendor module it delegates to is replaced by cua's service, selected by the launcher through the one slot it already reads (`CUA_SKY_SERVICE`, M1a's rename of `CUA_SKY_VENDOR_SERVICE`; `skyServiceFromEnv` and the `sky_not_configured` sentence name it), and cua's service raises errors of the same class names and `errorName` values (`SkyComputerUseError`, `SkyComputerUseTransportError`) so the wrapper's classification needs no change. Error sentences the model sees are kept where cua's harnesses, acceptance scripts or the first-call document depend on them (`noWindowsAvailable`, `timeoutReached`, the `userIntervened` and `screenLocked` sentences, `The element ID is no longer valid…`, `<n> is an invalid element ID`, the select and set-value refusals, `Computer Use was not approved to use <app>`, the forbidden-app sentence); elsewhere they are cua's own and bounded.

What changes behind it: the engine process, the socket it listens on, who may connect, where approval memory lives, and which REPL host runs the session.

### The engine: `cua Engine.app`

**One Swift program, Apple frameworks only.** `native/engine/` is a Swift 6 package (`swift build -c release --scratch-path <outside the package>`) producing the executable `cua-engine`, assembled into `cua Engine.app` (`LSUIElement`, hardened runtime, bundle id `io.github.ssfskim.cua.engine`, minimum macOS 14). It links ApplicationServices (the Accessibility API), CoreGraphics (events, window lists), ScreenCaptureKit (capture), AppKit (`NSWorkspace`, `NSRunningApplication`, `NSPasteboard`), Carbon's Text Input Sources (`TISCopyCurrentKeyboardInputSource`) and Foundation. No package dependencies: the owner's ruling bars unvetted third-party code, and Swift against Apple's frameworks needs none, where Rust would need binding crates. Apple SPI (private functions of SkyLight or CoreGraphics), where "Input" below needs it, is resolved with `dlsym` at run time and feature-detected, never a dependency. `engineVersion` is the package's version and `build` is the hash of the `native/engine/` source tree plus the assembling script, so two bundles with the same `build` are the same program. The executable also has a `--probe` mode for the harnesses (Interfaces, `UserProbe`).

**Process model: one engine per Mac, launched on demand, resident.** The service launches the approved engine through the own host's existing `nodeRepl.launchServices.openApplication({applicationPath})` relay (`src/repl-host/launch-services.mjs`), which M1a changes to run `/usr/bin/open -n -g -a <path>` (`-g`: launch in the background, so the engine's own launch never takes the user's focus; `-n`: a new instance even when another copy of the same bundle id is running, because LaunchServices otherwise reuses the running instance and launches nothing; M0 probes both). Before it unlinks or binds the socket, an engine takes `flock` on `engine.lock` beside it; the loser of that lock exits at once, so two services launching in the same instant (two checkouts whose connects failed together) never leave an engine listening on a replaced socket inode, and `-n` never produces a duplicate. On the vendor host (comparison A's lane) the vendor relay runs plain `open -a`; if M0's probe (c) shows that `open` without `-g` activates the engine, that lane pre-launches the engine from the harness with `open -g` before the run, which the "engine stopped at the start of a run" rule below permits as the run's own launch. LaunchServices is then the engine's parent and TCC attributes the Accessibility and Screen Recording grants to the bundle, not to Node (the vendor's arrangement; Apple's guidance on responsible processes in `C-macos-prior-art.md` §6). The engine stays resident across sessions, as the vendor's does, and exits on a `shutdown` request or when the login session ends. `shutdown` is sent by `buildEngine` before it moves a new build into the approved location and by `cua engine stop`; the engine refuses it while another connection is open (`{error: "busy", connections: n}`), and `buildEngine` then fails visibly with the approved bundle and the running engine untouched, rather than leaving a stale process serving a new bundle's socket. **A service never shuts down an engine it did not launch**: on a version or build mismatch between the `ping` answer and the bundle it was given, the service fails the connection with a diagnostic naming `cua install --engine`. The reason is the mini, where several checkouts and harness homes meet one Mac: a service that "fixed" a mismatch by shutting another's engine down would restart that session's lineages mid-task. The alternative process model, one engine per connection as a child of the trusted worker, would give peer authentication for free but makes TCC attribution depend on the process tree and re-prompts after rebuilds and relaunch heuristics; rejected.

**Socket and peer check.** The engine listens on `engine.sock` beside its own bundle: the engine derives the path from `Bundle.main.bundlePath`, the service from `CUA_ENGINE_APP`, so no argument crosses the LaunchServices launch (the own host's relay runs `open` with `PATH` only, the vendor relay passes `node_repl`'s environment, and the design relies on neither; an already-running instance gets no new arguments). The directory is created with mode 0700. `CUA_ENGINE_SOCKET` overrides the path only when a harness runs the engine executable directly rather than through the relay. On accept the engine reads the peer's uid with `getpeereid(2)` and closes any connection from another uid; the kernel's seatbelt profile denies the engine directory's sockets to cells (the unix-socket deny pattern that already exists in `src/sandbox/seatbelt.mjs`), so under the scoped sandbox only the trusted worker reaches the engine; and the engine itself refuses the forbidden list (system security processes and password managers, "The service" below) on `resolve_app` and every app-scoped request, whoever the client is. That is the whole peer policy. The threat model is the owner's own account, where an unsigned Node cannot carry a code-signing requirement anyway (`C-macos-prior-art.md` §6, "Authenticating a local Node client"); the vendor's ancestry check is what forced the vendor host on cua and is not reproduced. What remains exposed: any process of the owner's uid outside the sandbox, including a cell under `CUA_SHIM_SANDBOX=disabled` or the agent's own shell, can connect and observe or drive any non-forbidden app without an approval. That exposure is recorded in the Decision Log and was accepted by the owner on 2026-10-18.

**Protocol: the facade's vocabulary, one layer down.** JSON-RPC 2.0, each frame a 4-byte little-endian length then UTF-8 JSON, 8 MiB maximum each way, one request in flight per connection, as the vendor's transport (`R/A-contract.md` §2.2). Methods: `ping {clientApiVersion}` → `{serverApiVersion, engineVersion, build}` with `serverApiVersion = "cua-engine-1"`; `execute {method, args, deadlineUnixMilliseconds, lineage?}` → the method's result or a JSON-RPC error `{code, message}` using the vendor's code numbers for the conditions cua maps (`R/A-contract.md` §1.5) and `-10005` with a bounded sentence otherwise; `status` → the engine's permissions and identity; `approve` → the grant prompts and the one discarded capture of the approve step; `shutdown`. `execute.method` is one of the facade's 11 snake_case methods with the facade's argument shapes (`R/A-contract.md` §1.4, input column) plus two engine-only methods, `resolve_app {app | pid}` and `get_app_state` returning a `Skyshot` tree instead of text. So the service translates nothing: it adds policy, approval, rendering and diffing around a request it otherwise forwards. The vendor's own IPC vocabulary (`ComputerUseIPC*Request`, the `{_0: …}` enum encodings) is not adopted: the earlier reason for it, one JS client for both engines, was false, since cua's client can never reach the vendor helper (its peer check), and the vendor client would have to be impersonated to reach cua's (Decision Log entry 2).

**Observation (skyshot).** `get_app_state {app, disableDiff?, includeScreenshot?, outputDirectory}` observes the app's primary window (`AXFocusedWindow`, else `AXMainWindow`, else the last of `AXWindows`, the vendor's three-step fallback, `R/F-helper-logic.md` §1.7; none → error `noWindowsAvailable`). The engine walks that window's accessibility tree depth-first in preorder (the order the text prints), plus the menu bar's top-level items as the vendor adds them, fetching the vendor's 20-attribute set (`R/F-helper-logic.md` §1.2: role, subrole, role description, title, description, value, value description, placeholder, number of characters, help, identifier, selected, focused, enabled, disclosing, URL, traits, serves-as-title, row and column index ranges) plus position and size, through one of two routes M0 prices against each other: the public `AXUIElementCopyMultipleAttributeValues` per element, or the private batched `_AXUIElementCopyHierarchy` the vendor prefetches with (recovered by name with its four option keys in `R/F-helper-logic.md` §11 and §1.1; `dlsym` with feature detection, the public route as the fallback), then `AXUIElementCopyActionNames` per element; the owning process (`AXUIElementGetPid`, the vendor's `_AXUIElementGetActualPid` at input time, §5.7) is read for the elements an action targets, because sheets, open and save panels and some menus are served by another process (TextEdit's Open panel is; the baseline's `setup.newDocument` clicks its button) and input must be posted to the element's owner, not the app. The messaging timeout is set to 1 s on every element it touches (timeouts set on the application element do not reach its descendants), and a whole observation has its own 10 s traversal deadline apart from the request's 120 s: a hung app yields a truncated tree with the marker, not a stall (both cua's additions; the vendor has neither, §1.6). Enablement follows the vendor (§1.9), confined to web-shaped apps (the Settle paragraph's detection) and the bundles the vendor names (`com.apple.iWork*`, `com.spotify.client`), so an AppKit app such as Finder is never left with `AXEnhancedUserInterface` set, which changes its window behaviour for as long as it stays set (cua's departure; the matrix carries one iWork app and Spotify as the parity check): an application element that lists `AXManualAccessibility` gets it set (Electron, Chromium), else one that lists `AXEnhancedUserInterface` gets that, never both, once per process, and the first observation after enabling, or of any Chromium window, waits 100 ms and then up to 1 s for an `AXWebArea` to appear (without it a browser page is a single group); once a web area has been seen in a process, later observations of that process skip the wait (cua's departure: the vendor waits on every Chromium observation, which the MacBook shakedown priced at about 145 ms per observation, and a process whose web content is already exposed gains nothing from it; a window whose web area has gone, a new tab or a navigation, is caught by the settle's busy veto on an unloaded `AXWebArea`). The vendor's global VoiceOver preference is flipped only for Excel, Music, Atlas, Arc and Dia; cua never touches it, since it is visible to every app on the machine, so those five may expose less under cua until the owner decides otherwise at M5's sitting. Caps: the vendor's width rule is kept (100 children per element, then the visible subset, children omitted above 499, rendered as `(showing … of N items)`, §1.5), depth is the vendor's 200 levels (it drops the subtree silently; cua marks it), and cua adds what the vendor lacks, each with a marker in the text: a node budget of 4,000 after which remaining subtrees are omitted and counted in `truncated`, 10,000 characters per value, cut with a `[truncated]` suffix, and a total budget of 6 MiB for the serialized `Skyshot`, enforced during the walk so that a text-heavy window (a long article, a log view) yields a truncated tree rather than the relay's frame-too-large error (the vendor's hierarchy call truncates strings at a length the SPI chooses; its 4,000 is the URL-character budget per tree, which the renderer keeps, §2.5). The method matrix includes one scene state large enough to hit the budget. `valueMarkdown`, the Markdown rendering of an attributed value (headings, emphasis; the vendor renders them so `selectText` can quote them), is fetched only for text elements whose plain value is at most 2,000 characters, because the parameterized attributed-string fetch is the likely cost centre; M0 measures it. The result is a JSON tree (`Skyshot` in Interfaces), not text: **rendering to the model's text happens in the service.** The split is the point of the design: element handles (`AXUIElementRef`) cannot leave the process, so index assignment and re-resolution must live in the engine, while the grammar, pruning and diffing are pure functions that the service can run against recorded trees and the vendor's recorded text, which is how the grammar is pinned (goldens, under "Verification system"). Linux already renders client-side (`src/cua-api/linux-accessibility-tree.mjs`), so both platforms end up with the renderer where it can be tested. **Open for critique (Decision Log entry 1):** today the engine assigns the indexes but the service prunes and transforms the tree, so the model would see the engine's non-contiguous numbering over nodes the service later drops, not the vendor's contiguous post-transform numbering (`R/sky-behaviour.md` §23.1). The candidate, the debate's first topic, is that the engine emits a stable per-lineage handle token per node (equal exactly when two observations' handles are `CFEqual`) and the service does the transformations, the numbering, the grammar and the diff as pure code, with the handles never leaving the engine; the lineage's index-to-handle table would then be keyed by token. This moves index assignment out of the engine, which the current "Indexes and handles" paragraph puts in it, so it is held for the debate rather than folded.

**Indexes and handles.** Per (connection, app) the engine keeps a lineage: an id, the previous revision's rendered tree with its handles, and a table from index to element handle plus the eleven attributes the vendor matches on (role, subrole, role description, title, value, value description, description, placeholder, help, identifier, URL; `R/F-helper-logic.md` §3.6) and the owning pid. Indexes are 0-based in preorder over the nodes the engine emits for a fresh lineage, as the vendor numbers its rendered nodes (§3.1; the engine does not render, so the goldens compare modulo renumbering, part 3). On every observation an element keeps its index when its handle is `CFEqual` to the previous revision's at a matched position (sibling list against sibling list under matched parents, the vendor's rule, §3.2); a new element takes the next unused index; a vanished element's index is retired and **never reused in that lineage**, where the vendor reuses indexes above the surviving maximum (§3.3), a defect cua does not copy because a stale index would then resolve silently to another element. An action naming an index resolves the handle; the engine re-fetches only after a `layoutChanged` or `uiElementDestroyed` notification since the observation (the vendor's invalidation monitor, §3.5), else validates the handle with one `AXRole` read; a re-fetch walks the current tree for the one element matching the stored attributes, returning `The element ID is no longer valid. Try to get the on-screen content again…` when none matches and the vendor's before/after ambiguity sentences when several do. Every `Skyshot` carries its `lineage` id and every action names the lineage its index came from; the service keeps the lineage of the last observation per app and refuses, with the same "no longer valid" sentence, an index from another lineage (cua's addition; the vendor has no lineage check on actions), so a reconnect or a relaunched engine can never resolve a stale index to a different element. `disableDiff` starts a new lineage renumbered from 0 and returns the full tree, as the vendor does (§3.4). The sentences and their trigger order are the vendor's (`R/A-contract.md` §3.3), which the first-call document and the model's habits rely on.

**Screenshot.** When asked, a JPEG of the key window through ScreenCaptureKit (`SCContentFilter(desktopIndependentWindow:)`, `SCScreenshotManager.captureImage`), scaled to points (the baseline's 1172 × 976 for a window on a 2× display), quality 0.8, written with mode 0600 into `outputDirectory` (the session's run directory, which the kernel's sandbox lets the cell read) and returned as a `file:` URL, as the vendor returns it (`R/A-contract.md` §3.7). `CGWindowListCreateImage` is deprecated since macOS 15 and is not a fallback. Screen Recording's periodic re-confirmation on macOS 15 and later applies to any app without Apple's capture entitlement; the vendor's helper has none either, so this is parity, not a regression. What is not parity-neutral is the first capture of each new on-disk copy, which raises a confirmation only the owner can answer (the sibling spec's evidence; "Install, signing and permissions" below handles it with the approved engine).

**App resolution and launch.** `resolve_app {app}` and every app-scoped method accept, in the one `app` string the facade binds and sends on every later call, a bundle id, a display name or a path. A bundle id, name or path that matches more than one running instance is `ambiguousApp` with the vendor's sentence, never a silent pick; that is why the harnesses' scene processes carry bundle ids and paths no owner process uses (part 2 of the verification system), so a path names exactly one process on either engine. Running regular apps match first; otherwise LaunchServices (`NSWorkspace.urlForApplication(withBundleIdentifier:)`, and for a name the `.app` of that name or localized name in `/Applications`, `/System/Applications`, `~/Applications` and `/System/Library/CoreServices`), with `ambiguousApp` when more than one matches and `invalidApp` when none. An app that is not running is launched without activation (`NSWorkspace.openApplication(at:configuration:)` with `activates = false`) and the observation waits up to 5 s for a window, then fails `timeoutReached` as the vendor does; the baseline's `bind.getApp.retry` row exists for exactly that path. `list_apps` returns every running regular app plus the apps this engine has resolved before, from its own usage store (`<approved engine directory>/usage.json`: bundle id, last used, use count), so the vendor's `lastUsedDate` and `useCount` fields have cua's meaning; the bound identity returned to the facade is the app's path, as the vendor binds (`R/A-contract.md` §7).

### Input

Every input request names the app and either an element index or window coordinates. The rule that produces "not interfering": **the engine never activates an app on its own**, and input is posted to the process that owns the target element (`AXUIElementGetPid`), which for a sheet or an open panel is not the app. The routes, in order of preference:

1. **Accessibility actions** for element-targeted requests when the element advertises the action: `AXPick` when advertised, else `AXPress`, for a plain single left click (the vendor's choice, `R/F-helper-logic.md` §5.1; `AXShowMenu` is never used and right clicks are synthesized), `AXIncrement`/`AXDecrement`, the element's own secondary actions for `performSecondaryAction`, `AXValue` for `setValue` when settable, `AXSelectedTextRange` for `selectText`. These reach the element without events and need no focus.
2. **Synthesized events posted to the owning process with the vendor's recipe** (`R/F-helper-logic.md` §5.3–5.4, §6.2) for everything else: coordinate clicks, multi-clicks, right clicks, drags, scroll wheel, key presses and typed text. Mouse events are made through AppKit (`NSEvent.mouseEvent(...)` taken as a `CGEvent`, no event source), carry the global point as their location and the window-local point through the private `CGEventSetWindowLocation` (recovered by name; `dlsym`), the button in field 3, mouse subtype 3 in field 7 and the window id in fields 91 and 92, and are posted back-to-back with `CGEventPostToPid`, down and up per click; **when the target app is not active the ⌘ flag (0x100000) is added**, which AppKit treats as a click to deliver to an inactive window without activating it. That, not SPI, is how the vendor clicks in the background. Keyboard, scroll and modifier events come from an HID-system event source (`CGEventSourceCreate(.hidSystemState)`), as the vendor's do, because the Text Services Manager and some apps ignore other source states; what that costs the intervention rule is probe (d)'s question. The real pointer is never moved.
3. **Fake activation**, for the cases the vendor reserves it for (held keys or non-zero flags, elements inside a web view, `clickingMayCauseSelection`, Catalyst apps, keyboard actions into an app that does not believe it has focus, menu-bar items): post to the pid an AppKit-defined event of subtype 1 (application activated; modifier flags 0xC0000, the window number set) plus a left mouse down and up at the window's `AXActivationPoint`, so the app believes it is active while the user's app stays frontmost; the vendor wraps it in `SLSDisableUpdate`/`SLSReenableUpdate`, polls every 10 ms up to 1 s that the user's app is still frontmost (answering a window that ordered above the user's with `AXRaise` on the user's window), re-activates the user's original app with `activateWithOptions: 0` if it lost frontmost, and posts the matching deactivation subtype when done (`SyntheticAppFocusEnforcer`, §5.5); its `SystemFocusStealPreventer` (§5.6) watches process-level focus notifications and hands stolen key focus back through `CPSReleaseKeyFocusWithID`. The event posting is public API; the SLS and CPS calls are private, resolved by `dlsym` with feature detection and skipped when absent. The earlier inference that this needed a SkyLight posting function with a window-local authentication field was wrong: no such function is in the binary (§11). Route 3 is probed in M0 for keyboard actions into a background app and for the web-view click case; failure → route 4.
4. **Foreground assist**, bounded and reported: activate the app, post, then restore the previously frontmost app and its key window. The result's meta (`cua/inputRoute: 4`) lets the harness count it, and the non-interference metric counts it as a failure for that action, except for a family whose route 4 the owner accepted in M0 (Decision Log). It exists so a canvas app still works; it is not a route the engine chooses silently.

Which route each scene family lands on is decided by measurement in M0, not assumed. The baseline's `super+w` and `super+n` prove nothing about background delivery: the harness sent them while TextEdit was frontmost (the #162 key guard). Every result carries `cua/inputRoute` (1–4, or `"paste"` for the text fallback below) so the matrices can see what carried each action.

**Keys** (`pressKey`): the vendor's xdotool-style names, exact and case-sensitive, from its fixed ANSI key table (`R/F-helper-logic.md` §6.4: `super`/`cmd`/`command`, `ctrl`, `alt`, `shift`, `Return`, `KP_0`, …; no `Control`, `Ctrl`, `Alt`, `Shift`, `Enter` or `Esc` exists, whatever the vendor's documentation says), sequences split on space and combos on `+`, each combo one key press with the vendor's four events (a flags-changed with the mask, key down, key up, a flags-changed restoring the session's real modifier state), no gap between events; cua accepts exactly the vendor's names in this work (aliases would be an extension recorded in the first-call document) and corrects the vendor's `equal` defect, which types `+`.

**Text** (`typeText`): the engine reads the active input source (`TISCopyCurrentKeyboardInputSource`) and routes by it. With a Latin source active, every character the layout can produce is keyed as the vendor keys it (`R/F-helper-logic.md` §6.2): one key press per UTF-16 unit, four events each (flags, key down, key up, flags restored), 250 µs apart, whose virtual key code and modifier flags come from a reverse map of the layout (`UCKeyTranslate` with `kUCKeyActionDisplay` over key codes 0–127 under the vendor's eight shift/option/control masks, never ⌘, built once per layout and rebuilt on `kTISNotifySelectedKeyboardInputSourceChanged`; the engine also compares the current source's id (`TISCopyCurrentKeyboardInputSource`, read directly rather than through a notification flag, since the notification would wait for the run loop the request occupies) before every event and after the last, so a source switch during a keyed request, the user switching to Hangul for their own window mid-action, stops the request with the error name `inputSourceChanged` and a bounded sentence naming how many characters (UTF-16 units) were entered, rather than letting the Hangul input method compose the remaining Latin keys; the wrapper's value-free classification admits that name, and for a concealed request renders its "may have been partly entered" sentence) and whose Unicode string (`CGEventKeyboardSetUnicodeString`) is the character, so an app that reads virtual key codes and an app that reads the event's characters both receive it; a character the layout cannot key (an emoji, CJK, a combining sequence) goes as a Unicode-string event with key code 0, in chunks of at most 20 UTF-16 units that never split a surrogate pair or a combining sequence (cua's departure: the vendor logs and drops such characters, `R/F-helper-logic.md` §6.2, which is what the Korean and Unicode matrix must beat). Events are posted to the owning process; a newline is a real Return key event; an app that does not believe it has focus gets route 3's fake activation first, as the vendor does for every keyboard action (§6.1). With the Korean source active, the Text Services Manager interprets key events by key code and composition state, so neither form is trusted: the engine takes the paste route for the text and sends Return as key events. One more case makes the session-wide reading unreliable: macOS can hold an input source per app (Keyboard → Input Sources → "Automatically switch to a document's input source", the per-context input preference in `com.apple.HIToolbox`), and when it is on, a background driven app may sit in its own Hangul context while the session's source reads Latin; the engine reads that preference and, when it is on and the driven app is not frontmost, treats the source as unknown and takes the paste route. M0 probe (e) checks whether keyed Latin events are transliterated to jamo by the Hangul input method in that state. Every paste fallback is reported (`cua/inputRoute: "paste"`). There is no per-app fallback list: the matrix proves the keyed form on its scenes, and the ruling is any ordinary app. **Secrets never take the paste route.** The vendor's typeText keyed through the layout and never touched the pasteboard, which clipboard managers poll and keep; so `src/services/sky.mjs` marks the request copy it substitutes into with `concealed: true`, and for a concealed `type_text` the engine keys the text under a Latin source whose reading is reliable (the per-context preference off, or the driven app frontmost) and otherwise fails closed before anything is entered with the error name `concealedInputUnavailable`; a concealed `paste` is refused with the same name. The wrapper's value-free classification (`src/services/sky.mjs`, `secret-input.mjs`) admits that name and renders it as its own fixed sentence, which says that nothing was entered, names the active input source, and names `setValue` as the alternative (a settable field takes the value through `AXValue`, no keystrokes and no pasteboard); the wrapper's generic "may have been partly entered" sentence is reserved for every other failure after substitution. Never the value. The vendor keys through the layout and drops what it cannot key; `src/mcp/surface.mjs`'s "paste emoji" rule and its secrets rule are revised in M4 once the matrix shows what cua carries.

**Paste** (`paste {text, format: text|md|html}`): declare the pasteboard contents through a lazy data provider (an `NSPasteboardItem` whose data is supplied when an app asks for it; the vendor's representations, `R/F-helper-logic.md` §7.2: `text` → plain only; `html` and `md` (Markdown converted to HTML first) → `public.html` as the source, `public.rtf`, and plain as the rendered text), with `NSPasteboardContentsCurrentHostOnly` so the paste stays off Universal Clipboard, and in addition, cua's own, the `org.nspasteboard.ConcealedType` and `org.nspasteboard.TransientType` marker types that clipboard managers honour by not recording the item (the vendor writes no markers); snapshot the previous contents; give the app route 3's fake activation when it does not believe it has focus, as the vendor does before ⌘V (§7.1, 7.3); post ⌘V to the owning process; treat the provider's callback as the evidence that the app read the pasteboard (bounded at 2 s), then wait up to 2 s, polling every 25 ms, for an effect (a `valueChanged` or `selectedTextChanged` notification, or a change of the focused element's selected range or character count against the snapshot taken before the paste), both waits failing with `Timed out waiting for the application to read the clipboard` as the vendor's do (§7.4–7.5); then restore the previous pasteboard contents on every path, success or error, only if the change count is still the engine's own (a human's newer clipboard is never overwritten; the vendor's "The user may have conflicted with your paste operation" sentence covers that case, §7.6). Secret substitution is unaffected: the wrapper places the value into the request before the service runs, whichever route delivers it. **Open for critique (Decision Log entry 1):** the vendor serializes pastes process-wide, while cua's one-in-flight rule is per connection, so two connections pasting at once could clobber the pasteboard and each other's restore (`R/sky-behaviour.md` §23.5); the candidate is an engine-wide paste lock held across the write, the ⌘V and the restore.

**Scroll**: scroll-wheel events in lines, `pages` × the scroll area's visible lines, at the element's centre or the point. **Drag**: down, interpolated moves, up, posted to the owning process.

**Settle.** The vendor's rule, read in full (`R/F-helper-logic.md` §8): after an action, before the next observation on that app, the engine waits for quiet. An `AXObserver` on the application, created for the wait, listens for ten notifications: `titleChanged` (ignored when the title is unchanged), `layoutChanged`, `focusedWindowChanged`, `focusedUIElementChanged`, `elementBusyChanged`, `menuOpened`, `sheetCreated`, `windowCreated`, `created` and `uiElementDestroyed` (not `valueChanged`). Sampling every 100 ms (250 ms for a web-shaped app: the bundle's URL types include `http`, or its principal class is Electron's `AtomApplication` or Chromium's `BrowserCrApplication`), the engine returns once 250 ms have passed since the last notification, or since the wait began when none arrives, so a native app with nothing posted returns at about 300 ms (there is no 1 s floor; the earlier reading of one was wrong); it keeps waiting while the primary window's tree shows a busy sign (`AXBusyIndicator`, an `AXWebArea` with `AXLoaded` false, `AXElementBusy`, or the DOM class `macos-mac-parity-spinner`; a progress indicator is not one), and gives up at 5 s whatever keeps arriving (a browser page's animations and live regions post layout changes continuously), which the vendor does silently and cua reports as `cua/settle: "capped"` so the settle cell can tell it from slowness; M0 measures notification rates per scene. Because the vendor's IPC path defers the settle to the next `get_app_state` rather than running it inside the action (§8.6), cua does the same: an action returns when its events are posted, and the next observation on that app settles first, reusing the tree the busy walk fetched. The cell's time budget is suspended around launch wait, action and settle through `nodeRepl.withSuspendedTimeout`, which the own host honours by pausing the budget on the worker's `suspend_timeout` (`src/repl-host/supervisor.mjs`).

**User intervention.** The vendor's mechanism, read in full (`R/F-helper-logic.md` §9), is a listen-only event tap at the annotated session level on five event types (left, right and other mouse down, scroll wheel, key down), excluding only events whose source pid is the helper's own, attributing each event to an app by the owner of the window under it (private field 51) or else by the event's target pid, with no frontmost test; an event attributed to a driven app renews a 5 s debounce and sets a sticky re-query flag that only a successful `get_app_state` clears. cua keeps that mechanism and attribution: a click or scroll on the driven app's window counts, a keystroke counts when the driven app is the event's target, and the user typing or clicking in their own window never counts, which is the promise of the purpose section without any frontmost heuristic. The tap exists only so the engine yields to the human: its callback reads the event type, the source pid, the target pid and the window id and nothing else, never a key code, never characters, never a location it stores, and it is torn down when the last connection closes (a unit test pins the fields the callback touches). The engine's own events are excluded by source pid, as the vendor's are, and by `CGEventPostToPid`'s delivery, which does not pass a session tap (a run-time question probe (d) settles, with whether the tap can be created with Accessibility alone, since the vendor's helper runs it with the same two grants cua's engine will hold and no Input Monitoring; should either fail, the fallback is private-source key events, if probe (d) shows they land, with the machine-wide HID idle time plus a driven-app-frontmost test as the evidence). What cua does with the evidence differs from the vendor in two bounded ways, both recorded as expected differences: an in-flight sequence **stops** at the first attributed event and fails with `userIntervened` and the vendor's "The user changed '<app>'…" sentence (the vendor never stops an action in flight and reports the intervention only at the next request, §9.5); and the pre-action guard refuses at once, for every input kind, with the vendor's "The user is still interacting with '<app>'. Wait 5 seconds and retry." sentence while the debounce is live (the vendor waits out the debounce for up to 100 s before proceeding or refusing, which stalls the model for the whole time the user keeps working in the app). After an intervention the engine refuses further actions on that app until a fresh `get_app_state` has been taken, as the vendor does and as its sentence tells the model. **Open for critique (Decision Log entry 1):** what a `get_app_state` during the live debounce does is unspecified for cua (`R/sky-behaviour.md` §23.4); the candidate is to observe at once and clear the re-query flag, so the model's own re-query after a refusal is not itself refused. The engine's own `super+n`, its click on a sheet button, the window it opens or closes, and a route-4 activation it performs itself are never interventions, since none of them is a tapped user event attributed to the app. `cua/hidIdleMs` on results and refusals reports the milliseconds since the last user event the engine attributed to the driven app (or the HID idle time under the fallback). Input through Screen Sharing counts as the user's (it enters at the HID level like a local user's); the spike confirms both halves on the mini with a keystroke the owner sends over Screen Sharing during an action.

**Lock screen.** `CGSessionCopyCurrentDictionary`'s `CGSSessionScreenIsLocked` true → every request fails `screenLocked` (−10020) with the vendor's first sentence. No auto-unlock, no guardian.

### The service: `src/services/engine/`

The service replaces `@oai/sky`'s macOS target behind `src/services/sky.mjs`. On the vendor host (comparison A) it loads in the vendor trusted worker through the same slot, so `src/services/engine/` joins `NODE_REPL_TRUSTED_CODE_PATHS` in the launcher. Its parts:

- **Client** (`client.mjs`): connects through `nodeRepl.nativePipe.createConnection(path)` (the own host's relay, `src/repl-host/native-pipe.mjs`, opens the socket outside the sandbox; the vendor host's relay does the same), pings with `cua-engine-1` and checks both `engineVersion` and `build` against the bundle it was given, launches the bundle through `launchServices.openApplication` when the connect fails, reconnects for up to 5 s, fails with the `cua install --engine` diagnostic on a mismatch, chains one request at a time with the 120 s default deadline, wraps launch wait, action and settle in `nodeRepl.withSuspendedTimeout`, and raises `SkyComputerUseError` / `SkyComputerUseTransportError` with the vendor's `errorName` values so `src/services/sky.mjs` classifies them unchanged.
- **Renderer** (`render.mjs`): `Skyshot` JSON → the vendor's text grammar (`R/A-contract.md` §3.2, the literal set in `R/E-helper-catalogue.md` §5, the composition rules `R/sky-behaviour.md` establishes): the `Window: "<title>", App: <name>.` header (no `App=` line: `R/F-helper-logic.md` §2.6 shows neither producer of the IPC text emits one; the TextEdit test double's first line is corrected in M1a), one line per element, `<id> <roleWord> (<flags>) <parts>` with tabs per depth: the role word is the localized role description with the vendor's overrides (`row`, `element`, `container`, nothing for menu-bar items, menu items and radio groups), the flags in the vendor's order (`selectable`, `selected`, `disabled`, `expanded`/`collapsed`, `settable` or `settable, <type>`), then the parts in the vendor's order, title bare, `Description`, `Rows`, `Columns`, `URL` (shortened under the 4,000-character budget), `Help`, `Value`, `Details`, `Placeholder`, `ID` (dropped entirely when it starts with `_` or `NS`) and `Secondary Actions`, a part whose value repeats an earlier part skipped, long parts moved last, a lone part printed without its label (§2.4); partial arrays rendered as `(showing … of N items)`; links rendered as Markdown; the trailer with the vendor's precedence, selected text, else selected elements, else the focused element (§2.6); the truncation markers. The nine tree transformations and four Mac-only ones the vendor applies before rendering are named in E, their predicates recovered in F §2.1–2.3, and decided in `sky-behaviour.md` from F and the captures.
- **Diff** (`diff.mjs`): per (connection, app), the default mode diffs against the previous rendered tree, keyed on element id, with the vendor's one live header (`The following is a diff from the previous accessibility tree for Window: "<title>" …` with the removed-ID-ranges legend, the flag that chooses the legend defaulting to true; the cumulative header is dead code, `R/F-helper-logic.md` §4.1–4.2), `~`/`+`/`-` marks before the tabs, inserted and removed subtrees in full, no context lines, changes in depth-first order, the `Removed element IDs:` ranges line first, the no-change sentence when nothing changed, and the full tree instead of the diff when the diff's lines would exceed the full tree's node count (the vendor's budget, ratio 1.0, §4.3); `disableDiff` returns the full text on a fresh lineage; every observation advances the baseline, including one whose text the facade discards for a screenshot (the first-call document says so; the vendor has no screenshot-only mode, §4.8).
- **Policy and approvals** (`policy.mjs`): before every app-scoped method, resolve the app (`resolve_app`), refuse the forbidden list (password managers and system security UI, the vendor's list from `R/E-helper-catalogue.md` §6, also enforced in the engine) with the vendor's sentence, classify risk (terminals and browsers high, with the subtitle), then ask on every call through `nodeRepl.createElicitation` with the exact message and meta shape the harness matcher expects (`scripts/accept/lib.mjs`; `R/A-contract.md` §2.6), as the vendor's JS does, and fail `Computer Use was not approved to use <app>` on anything but accept. The once-per-connection memory lives in the REPL host's supervisor (`src/repl-host/supervisor.mjs`), which already brokers every elicitation between worker and client: it answers a repeat of a `connector_id: computer-use` elicitation for the same `tool_params.app` from memory for the connection's lifetime, accepts and declines alike, as the vendor's Rust host did (its store held `allowed` and `denied`), so a model retrying a declined app is not re-prompted on every call. The memory is not in the worker because the supervisor replaces the worker on a sandbox-policy change, a start timeout or its death, and an approval that vanished mid-connection would ask again. No session file (the vendor wrote `$CODEX_HOME/computer-use/sessions/<id>.toml`, which cua deleted at close; `scripts/accept/textedit.mjs` checked that file and changes in M3 to observe the behaviour instead: a second bind in the same connection asks nothing, a new connection asks again). `persist: ["session"]` only; `CUA_SHIM_PERSIST=always` is refused at `cua serve` from M3 with a sentence naming the hook, rather than accepted as a silent no-op, by the owner's ruling that the plugin's Elicitation hook (`hooks/cua-approve.sh`) is where friction is removed and a stricter hook is where a veto lives. The policy lands in M1a, before the first app-scoped method, so no release ever carries a selectable engine without it. **Linux** goes through the same module from M3: the window-bound methods (`get_window_state`, `click`, `press_key`, `type_text`, `scroll`, `drag`, `drag_handle`, `move`, `move_relative`, `perform_secondary_action`, `activate_window`, `key_down`, `key_up`) keyed by the window's `app` name, and `launch_app` by its app id; `list_apps`, `list_windows`, `get_screenshot` (the whole desktop) and the clipboard methods are not app-scoped and ask nothing, which `src/mcp/surface.mjs`'s Linux rule states from M3 instead of today's "no app asks for approval".
- **Result meta**: `codex/toolSurface` per call as today, plus `cua/nativeEngine {engine, version, build}` on every result, `cua/inputRoute` on every input result, `cua/settle` on the `get_app_state` result when the settle that preceded that observation was capped (not on the input result, since the settle runs at the next observation, not inside the action; `R/sky-behaviour.md` §23), `cua/actionInterval {startedAt, endedAt}` (Unix ms from the engine's clock, which is the probe's clock too) on every input result and on a `userIntervened` error so the matrix can place a probe's post inside an action, and `cua/serviceMs`, measured by the wrapper `src/services/sky.mjs` around `handleRpc` on both lanes (service, policy, approval and engine together: the vendor's policy runs inside its own `service.js`, so no finer split is measurable on that lane), which separates the host's transport from everything below the wrapper on single-call rows (response meta merges by key per execution, so a multi-call cell such as `task.total` carries its last call's value only, and the separation is read on the single-call rows); cua's lane adds `cua/engineMs`, the client's time around the socket round trip, so its service's own overhead is `serviceMs − engineMs`; every input result and every input refusal also carries `cua/receivedAt` and `cua/hidIdleMs` from the engine, set on the execution's meta before an error propagates; the MCP proxy surfaces `cua/nativeEngine` in each `js` result's `_meta` next to `cua/replHost`, which is the attestation the harnesses validate.

### Install, signing and permissions

**The approved engine.** macOS raises a screen-capture confirmation, which only the owner can answer and which stops the mini's CI runner, the first time each new on-disk copy of a capturing app captures (the sibling spec's evidence on the vendor helper, 2026-10-17; `scripts/native-baseline/prepare.mjs` exists because of it). So there is exactly one engine location per Mac, outside every `CUA_HOME`: `~/Library/Application Support/cua/engine/cua Engine.app`, with `engine.sock`, `engine.lock`, `usage.json`, `pending.json` and `approved.json` beside it (no version segment in the path: the bundle carries its version, and a versioned directory would let an older version's resident engine keep running with its grants beside the new one, outside `cua engine stop`'s reach). `buildEngine` writes `pending.json {build, identity, builtAt}` when it assembles a bundle; nothing can observe the owner's confirmation, so the confirmation is proven by its effect: `cua engine approve`, run with the owner at the console, refuses while `status.connections > 0` (connections other than its own), then sends the engine `approve`, which requests the Accessibility and Screen Recording grants with their prompts and returns their state as the engine sees them; because a Screen Recording grant applies only to a relaunched process, and whether the running engine can even observe it is probe (f)'s question, the command then waits for the operator's confirmation at the console that both were granted (a keypress; `approve`'s answer is advisory), sends `shutdown`, relaunches the engine with `open -n -g -a`, polls `status` until it answers, and sends `approve` again, which now takes one display capture that it discards, raising the confirmation; on `captured: true` the command writes `approved.json {build, identity, approvedAt}`. No app is bound for it, so the step needs no scene. Harnesses, `doctor` and the selection table's "installed" column read `approved.json` only: a bundle whose `build` or `identity` differs from `approved.json`'s is pending, not installed. Every session and every harness home on that Mac serves the approved engine in place; a harness never installs its own copy, and `--approved-engine` on the harnesses is the analogue of `--approved-runtime`. Replacing it (a new `build`, or a signature that no longer matches the configured identity, which is the second reinstall trigger) is done only by `buildEngine`, and the harnesses refuse capture cells against a pending build. M0's probe (f) measures what exactly re-raises the confirmation (a staged rebuild at the same path, a copy at a new path) and whether the Accessibility grant survives both; the install text below is revised from it.

`cua install` builds the engine when the engine is selected (`CUA_NATIVE_ENGINE=cua`, or the default once M5 flips it) or when asked with `--engine`; otherwise it leaves the engine alone and `doctor` shows an `engine` row saying so, which keeps today's gates (`scripts/sandbox-probe/hosted-gate.sh`, `scripts/native-baseline/prepare.mjs`) running unchanged until they opt in. A build failure (no identity, no Xcode) fails `cua install` only when `--engine` was explicit; under the default it leaves the rest of the install done and prints the engine row's sentence. Building means `swift build -c release --scratch-path ~/Library/Application Support/cua/engine/build` in `native/engine/`, assembling and signing `cua Engine.app` in a staging directory beside the approved location (`<engine directory>/staging/`) with the identity named by `CUA_SIGNING_IDENTITY` or `~/.config/cua/engine.json`'s `signingIdentity` (a common name or SHA-1 from `security find-identity -v -p codesigning`), hardened runtime, no entitlements, and then, if a bundle with another `build` is at the location, sending its engine `shutdown` and only on success moving the old bundle aside and the staged one into place (two renames; the engine is stopped by then, so nothing serves in the gap) and writing `pending.json`. A `busy` answer fails the build visibly, naming the connections, with the approved bundle, `approved.json` and the running engine untouched and the staged bundle discarded. The order matters: assembling in place first would leave the resident engine, which exits only on `shutdown` or logout, serving the socket beside a bundle every new client rejects on its `build` check and that `cua engine approve` could never approve (the ordinary outcome of an update on the mini, where a session usually holds a connection), and rewriting a running executable's signed pages kills it mid-session. A bundle whose `build` already matches is left as it is (reinstall changes nothing). `cua engine build [--sign adhoc]` is the command form of `buildEngine` (M1b); `cua install --engine` (M4) calls the same function. The identity is the owner's Apple Development certificate (ruling 2026-10-18): its designated requirement names the certificate's subject, so a rebuild signed by the same certificate keeps the Accessibility grant, and the subject is the same string on every Mac the owner's Apple ID issues a certificate to, so each Mac may hold its own certificate. Without a configured identity a build refuses with the sentence that names the setting; ad-hoc signing (`cua engine build --sign adhoc`, `cua install --engine-sign adhoc`) exists for the hosted CI runner, where no permission is granted anyway, and is never a default: ad-hoc signatures change with every build and would lose the grants on each rebuild. The repository carries no certificate name. Signing over SSH (every harness build on the mini runs over SSH) needs the key's keychain partition list to admit `codesign` and the keychain to be unlocked; that is a one-time owner step on the mini, done before M1b's first live run (M1b's prerequisites name it, with the Swift toolchain and the certificate) and recorded in `docs/onboarding-new-mac.md` by M4 with the exact `security set-key-partition-list` command the owner runs with their password, which automation never enters.

Permissions are requested where they are first needed and reported, never clicked: the first observation calls `AXIsProcessTrustedWithOptions` with the prompt option and fails `permissionsPending` (−10014) with a sentence naming "cua Engine" in System Settings → Privacy & Security → Accessibility; the first screenshot calls `CGRequestScreenCaptureAccess` the same way. Because macOS applies a Screen Recording grant only to a relaunched process, and whether a running process can observe its own grant (`CGPreflightScreenCaptureAccess` after the fact) is M0 probe (f)'s question, neither flow depends on observing it: after a screenshot has failed `permissionsPending`, the service, on the next screenshot request, sends `shutdown` to the engine (a `busy` answer, another connection open, leaves it running and the request fails again with the sentence), relaunches it through the relay and retries the screenshot once; until a relaunch has happened screenshots keep failing with the `permissionsPending` sentence, which says a relaunch is pending. On the mini the owner grants both at the GUI console over Screen Sharing, once per signing identity, plus the capture confirmation per approved build. `cua doctor` reports both grants from the engine's `status` request, the signing identity, whether the socket's owner is the approved bundle, and the probe mode's ability.

### Verification system

The owner's core requirement: no regression across the replacement, proven, before any default changes. The system has seven parts, built in the milestones that first need them and run in full at M5. Every live run begins and ends with `cua engine stop` (the `shutdown` request to the approved engine, never a signal; a `busy` answer, or `status.connections > 0` at preparation, refuses the run naming the connections, which is the hold discipline's job to prevent) under `prepare.mjs`'s admission lock, and with the vendor helper stopped as `prepare.mjs` does today, so a cold row is "first launch by this run" on both sides. Harnesses never call `buildEngine`: the sitting's operator builds and approves with the owner present, and every run computes `build` from its own checkout and refuses unless it equals both the attested and the approved `build`, so a sitting can never attest an engine built from older source.

1. **Three comparisons on the native baseline harness.** The vendor engine accepts only the vendor host, so "same host, different engine" is possible only on the vendor host, where cua's service runs inside the vendor trusted worker (loaded through `CUA_SKY_SERVICE`; the vendor relay connects to any absolute socket path). `scripts/native-baseline.mjs run` takes `--host` and `--engine` independently (`--host vendor --engine cua` is the loaded-service lane) and records the engine attestation from `_meta['cua/nativeEngine']`, with the helper attestation classifying both `SkyComputerUseService` and `cua-engine` processes.    A fresh vendor triple is taken in the same sitting as each candidate triple; the 2026-10-14 runs remain a reference, not a side. Scenes pair for the non-interference cells: the user window of a cell is the scene window of another family (TextEdit ↔ Finder, Chrome ↔ TextEdit, Electron ↔ Finder), so the driven app and the user's app are never the same process; the concurrent-use cell uses TextEdit as the user window with Finder and Chrome for Testing as the driven apps, and its sheet variant, which needs a driven app that opens a sheet on `super+w`, drives TextEdit with the Electron fixture's text field as the user window; the user window's value is read back through the probe mode's `focus` command (its `valueHash`), never through either engine. 5. **The three points, defined.** *Speed*: on every scene, in-cell medians of `getAXState`, `getScreenshot`, `listApps` and each method cell, from the matrix runs, lower than the vendor's by at least 10% with p95 not worse, three runs per side; the no-regression gate of part 1 stays the inherited rule, this is the stricter "beat", and a missed beat on a scene is an owner fork at M5 (accept parity there, or continue). *Finding elements*: per scene a fixed list of ten targets drawn from the fixtures' ground truth before either engine's text is seen (every control the harness put into the Electron fixture and the loopback page; a fixed set of Finder and TextEdit controls named from the fixture definitions), each to be resolved by name through the model's path (`getAXState` text search → index → action), plus the share of element lines with a non-empty title or label and the `ID:` count; the vendor's misses are then a result, not the sampling frame. Where cua resolves what the vendor misses, its text carries lines the vendor's lacks; the Chrome and Electron scenes are therefore expected to exceed part 3's 10% added-line cap, and the Decision Log entry that cap requires is written when the first such golden is recorded, not discovered at M5. *Not interfering*: for each paired scene cell (a background-regime cell of part 4) the harness activates the user window, drives the scene's app, and requires the cell's outcome under part 4's rule and three things more: after every action, read from the device side and independently of either engine, the frontmost application (`lsappinfo front`, the existing `FRONTMOST_SCRIPT` in `scripts/accept/key-guard.mjs`) and the topmost on-screen window's owner pid and bounds (`CGWindowListCopyWindowInfo` through a Swift script, which needs no permission when names are not read) are unchanged; during the whole cell, a resident device-side watcher (the probe mode's `watch-activations`, subscribed to `NSWorkspace.didActivateApplicationNotification`) recorded no activation of any app (the probe instances are launched with `-g` and their pids, which they print, are excluded by the watcher and the frontmost oracle), so a steal handed back inside an action (route 3's active-state events, the vendor's `SystemFocusStealPreventer`) is seen; and `cua/inputRoute ≠ 4` outside an owner-accepted family. Two cells test the rule's positive side after M0, since the concurrent-use cells only prove it must not fire: **intervention fires**, in which the harness activates the driven scene's window (its own), the probe, gated on that window, posts one keystroke into it during a driven action, and the result must be `userIntervened` with the next action on that app refused until a `get_app_state` (the `userIntervened` error carries `cua/actionInterval` as a result would, and a sample whose post falls outside the interval is invalid, as in the concurrent-use cell); and **pre-action refusal**, in which the probe posts a keystroke into the frontmost driven window and the harness requests `typeText` at once, which must be refused as `userIntervened` with the still-interacting sentence and nothing posted (the window's value equal to its value after the probe's keystroke). ## Interfaces and Dependencies

**EngineClient** (`src/services/engine/client.mjs`): `connect()`, `execute(method, args, {deadlineMs = 120_000, lineage})`, `status()`; owns the one-in-flight chain, the version-and-build check, the launch-on-failure path through `nodeRepl.launchServices.openApplication` and `nodeRepl.nativePipe`, the `withSuspendedTimeout` wrapping, and the error classes.
