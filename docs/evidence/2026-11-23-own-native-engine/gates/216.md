# Gate #216: approval lost across apps

- **Ticket:** [#216](https://github.com/SSFSKIM/cua/issues/216), "Diagnose cross-app approval loss and expose refusal
  provenance without bypassing consent" (P1). Gate of the macOS default switch (M5 pre-flight §6), task T8d; O10 is the
  owner's fallback.
- **State:** not reproduced in code. The sequence is pinned end to end in process and passes on the base as well. The
  refusal now says where its answer came from. That provenance is the connection's own, and every approval answer
  carries it as `cua/approval` result meta. The hosted twenty-cycle witness is prepared and has not run. **Open.**

## The report

From MAWS's dogfood (`plugin/cua/dogfood-feedback/l8-settings.md` §1 and its 23:08Z addendum, 2026-10-23). The driver
was a background Claude Code subagent on cua plugin 0.17.0 (main `d95261fb8`). The apps were MAWS-under-test (an
Electron dev app bound by its full `Electron.app` path), Claude Desktop, and ChatGPT/Codex.

1. MAWS and Claude were approved and driven for about 15 minutes.
2. `cua.getApp('com.openai.codex')` failed with `Computer Use was not approved to use ChatGPT`.
3. The next cell failed with `maws is not defined`. The reporter's reading was that the error had reset the kernel.
4. Binding MAWS again failed with `Computer Use was not approved to use Electron`.
5. Three end_task/new-task cycles did not help.
6. By 23:08Z, in a fresh task, `getApp` on MAWS worked again. Nothing said why.

Which engine and host served this is not on record. At 0.17.0 the macOS default was the vendor's engine on the
vendor's host. MAWS's repository sets `CUA_NATIVE_ENGINE=cua`, which selects cua's engine on cua's host. Both paths go
through the same approval memory in cua's MCP connection.

## Diagnosis

**The store and its scope.** cua keeps one approval memory per MCP connection: `src/mcp/approval-memory.mjs`, created
once in each `createServer`, `src/mcp/server.mjs`.

- **What it answers.** Only `elicitation/create` requests whose `_meta.connector_id` is `computer-use`.
- **The key.** `_meta.tool_params.app`. The policy sets it to the bundle id the engine resolved, or to the app's path
  when there is no bundle id (`src/services/engine/policy.mjs` `approvalRequest`). The key does not depend on the
  string the model passed: a path, a name and a bundle id that resolve to the same app share one key.
- **What it records.** Only a reply the host's own rule accepts as an answer (`elicitationOutcome`):
  - every decline;
  - an accept whose `_meta.persist` is `session` or `always`. That `persist` may be the client's own, or the one the
    connection adds to an accept that has no `_meta` (`surface.mjs` `persistAccepted`). `CUA_SHIM_PERSIST=none`
    suppresses only the connection's implicit `persist`. An accept that carries its own `persist` is still remembered
    under `none`, and so is every decline.

  Cancels, error replies and malformed replies are never recorded.
- **When it answers.** On a repeat for the same key it answers from memory, with `content.source:
  computer-use-persisted-state`, and the client is not asked.
- **The client's contract** (the design session's ruling on this gate): an accept that carries its own `_meta`
  without `persist` stays unremembered, and that app asks again on every bind. MAWS's shim
  (`MAWS/plugins/cua/cua-shim.mjs`) adds `_meta.persist` to every accepted app approval. Claude Code's hook path sends
  no `_meta`, so the connection adds `persist`. Remembering more would widen consent for no known client.

**Per app.** `record` writes only the key it was asked about, and `recall` reads only the key it is asked about. A
decline for one app therefore leaves every other app's entry alone. No connection-wide flag or counter exists, and no
code path clears or overwrites another app's answer.

**Per connection, task and end_task:**

| Event | What happens to the memory |
|---|---|
| end_task | Kept. end_task completes the task upstream (`turn_ended`) and closes the engine connection (`client.release`); neither reaches the memory. |
| A new task | Kept. A task is a turn ID inside the same connection. |
| `js_reset` | Kept. It resets the runtime's kernel only. |
| The idle stop | Kept. It replaces the runtime under the connection, and the memory lives in the connection, outside the runtime. A late answer to a stopped runtime is recorded for its own app and never forwarded (`generation`). |
| A worker replaced | Kept, for the same reason. |
| A new MCP connection (a new `cua serve`) | Starts empty and asks again. This is by design (spec, Policy and approvals; M3.1 ruling 2). |

**What can still make an approved app refused.** Reading the code, it takes one of three things:

1. **A new connection**, whose client then answers anything but accept.
2. **An accept that was never remembered**, so every bind asks again and the client's answer at that moment decides.
   This happens with `CUA_SHIM_PERSIST=none` and no `persist` from the client, or when a client's accept carries its
   own `_meta` without `persist`. The second case is the client's contract above.
3. **The client's own later decline for the same app.** The client declines an older request for that app (a late
   reply, or a concurrent one) after an accept was recorded, and the decline replaces the accept.

Each of these is the client's answer for that one app. None of them is one app's decline reaching another.

**The client's side.** Claude Code 2.1.330's own handling was read from its binary. It is today's version; the
report's version is not.

- An Elicitation hook's answer goes back as `{action, content}`, with no `_meta`, so an accept by the plugin's hook
  (`hooks/cua-approve.sh`) is remembered.
- A hook that returns a blocking error becomes **decline**. The same happens for an ElicitationResult hook.
- **Cancel** comes back without any answer being given when:
  - the request was aborted;
  - its handler failed;
  - in print or SDK sessions, one of the client's own limits refused it before any hook ran. The limits are the
    outstanding cap, a brake on repeated unanswered questions, the per-minute rate and the request size.

So a decline that reaches cua need not be a person's, and cua remembers a decline for the rest of the connection.

**The reading most consistent with the report** (not proven):

- Two facts point the same way. The REPL state was gone (`maws is not defined`), and Electron was asked again (only
  the client's answer can refuse it). So Electron's remembered accept was not consulted.
- That points to a new connection, where the client had reconnected and started a new `cua serve`. An accept that
  had never been remembered would also explain it.
- At that time the client answered non-accept for every new ask: ChatGPT first, then Electron.
- On a new connection, Electron's decline would then be remembered there. That fits the end_task cycles not helping.
- The recovery at 23:08Z fits a further connection, or the client answering again.

Nothing in the report records server pids, elicitation traffic or hook output, so none of this is established.
`cua/approval` (below) is what would establish it next time.

**Fix or guarantee.** cua's code has no mechanism that loses one app's approval because another app was declined. Nothing
was changed to "repair" approvals:

- nothing is approved automatically;
- no approval is widened;
- a declined app stays declined for its connection;
- the no-retry guidance is unchanged;
- which replies are accepted or remembered is unchanged.

What changed is the refusal's provenance, which the ticket's title asks for, and the diagnostic channel behind it.

## The change

**The refusal.** The vendor's sentence still opens every refusal. One clause follows it, chosen by who answered
(`src/services/engine/policy.mjs` `notApproved`, shared by the macOS and Linux policies):

| The answer | The refusal |
|---|---|
| The client declined this request | `Computer Use was not approved to use <app>: the client declined the approval request; it is not asked again on this connection.` |
| The connection's memory declined it | `Computer Use was not approved to use <app>: it was declined earlier on this connection, so it was not asked again.` |
| The client cancelled | `Computer Use was not approved to use <app>: the client cancelled the approval request without an answer.` |
| Anything else (unreachable through the host's rule) | the vendor's sentence alone |

A few points about the wording:

- No sentence says a person declined. "The client" covers a person, a hook, and the client's own rules.
- No sentence suggests a way around the answer.
- The vendor's sentence stays a prefix, so the secret wrapper's `not_approved` class
  (`src/services/sky.mjs` `vendorFailureKind`) still matches.
- The vendor's engine keeps its own bare sentence, because its policy is the vendor's JS. Only cua's engine and the
  Linux wrapper speak the clause.
- No harness or matrix row matches the bare sentence exactly.

**Who answered is the connection's to say** (`src/mcp/approval-memory.mjs`, `src/mcp/server.mjs`). The first cut read
"remembered" from the persisted-state mark in the answer's content. The proxy forwards a client's reply, and the host
keeps its `content`, so a fresh client decline that carried the mark was labelled "declined earlier, not asked". Now:

- The connection removes the mark from a client's reply to a computer-use approval before the runtime sees it.
- Every computer-use answer the runtime gets is stamped with `_meta["cua/approval"]`, whether it was remembered or
  the client's: `{connection, runtimeGeneration, scope: "connection", answeredBy: "memory" | "client"}`. The
  connection overwrites any client copy of that key.
  - `connection` is the connection's opaque id: the first 12 hex digits of a SHA-256 of its session id, not the
    session id itself.
  - `runtimeGeneration` is the generation the answer went to. An idle stop starts the next one.
- The policy reads who answered from the stamp. It falls back to the mark only when there is no stamp, which means the
  vendor host's own store answered below cua's connection.
- A reply whose `content` or `_meta` is malformed passes unchanged and still fails. The stamp is added after the
  memory has recorded the reply, so what is taken and what is remembered do not move.

**The diagnostic channel.** On every app-scoped call that asked, the policy sets the result meta
`cua/approval: {action, answeredBy, connection, runtimeGeneration, scope}`. It is reset to null at the start of each
call.

- Every field is checked. `connection` must be up to 32 hex digits and `runtimeGeneration` a non-negative integer;
  anything else reads null.
- No app name is added beyond what the result already carries (`codex/toolSurface`), and nothing of the reply's
  content is included.
- It rides in `_meta`, which the model does not read.
- It lets a harness or a log:
  - tell a new connection (a new id) from a new runtime on the same connection (the same id, a later generation);
  - tell a remembered answer from a fresh one;
  - see that an approval passed before a later failure in the same call.

`list_apps` does not go through the policy. A `list_apps` after an app-scoped call in the same cell leaves that
call's `cua/approval` standing, which is the execution's last approval and still true.

## Hosted witness (prepared, not run)

**The script.** `scripts/approval-cycles.mjs`, with its judge in `scripts/probe/approval-cycles.mjs`
(`judgeApprovalCycles`, unit-tested in `test/probe-approval-cycles.test.mjs`). It drives the installed `cua serve`
the way `verify.mjs` does. It refuses unless all of these hold:

- `RUNNER_ENVIRONMENT=github-hosted`;
- macOS;
- `CUA_SHIM_SURFACES=computer,browser`;
- `--engine cua`, with the launcher selecting cua's own host.

**Connection one:**

1. Bind the approved app, the declined app, then the approved app again.
2. Twenty cycles, each an end_task followed by a bind of each app. Cycle 5 runs js_reset first. Cycle 10 waits out
   `CUA_RUNTIME_IDLE_MS` (8 s by default) first.

**Connection two** is a new `cua serve` that binds each app once.

**How the client answers.** As `verify.mjs --bind` does: it accepts only the policy's approval for `--approve`
(`isAppApproval`), declines the one for `--decline`, and declines and counts anything else. `CUA_SHIM_PERSIST=session`
is pinned.

**The fixture.** FrontWindowProbe is compiled once (it falls back to the interpreter). The script waits up to 60 s for
the approved app's window to be on screen. It never observes the app to check this.

- Before every bind, the same process must still hold that window, through verify's `bindRefusal` rule.
- A lost fixture stops the run as NO VERDICT. Binding a TextEdit with no window would make the engine reopen it, and
  TextEdit answers that with its Open panel.

**The alert rule** (rulings 1136 and 1141: replayd's capture alert stays up on a runner):

- Before every bind, the approved app is activated (`open -b`). It must then take front (lsappinfo) and key (the top
  on-screen window's owner, from FrontWindowProbe).
- Front and key are sampled again after the bind.
- A system prompt (UserNotificationCenter, SecurityAgent, CoreServicesUIAgent) in front or key at either sample, or an
  activation that did not take, makes the bind NO VERDICT.

**What each bind keeps:**

- the number of asks while it ran;
- its refusal class, from the sentence;
- its `cua/approval`;
- a non-approval failure's first line;
- whether its result opened with the restart notice;
- its task id;
- the two samples' verdicts.

It never keeps the app's text. Each end_task must return status `ended`, and each js_reset must return no error.
Every js result must attest cua's engine on cua's host, and any mismatch stops the run as a fail.

**The judge.** A bind proves an approval only when it completed, or when it failed but its `cua/approval` says
accept. The policy sets that once the answer is in, before the engine is asked. Any other failed bind is
inconclusive. The verdict is **pass** only when all of these hold:

- each app is asked once per connection, at its first bind that reached the approval;
- the approved app is never refused;
- the declined app reads `declinedNow` at its first answer and `declinedEarlier` after;
- `cua/approval` agrees with the asks (the asking bind answered by the client, the rest by memory) and names one
  connection throughout;
- nothing else is asked;
- every end_task and js_reset succeeded;
- connection one runs one task per cycle and never reuses one;
- the bind after the idle stop opens with the restart notice, on a later runtime generation;
- connection two is another process with another connection id;
- no bind is inconclusive.

Any departure is a **fail**. Inconclusive binds without one give **NO VERDICT**, which never counts as a pass. A fresh
ask for the approved app after its first answer fails the run, even when the client accepts again.

**What it needs:**

  Accessibility and Screen Recording rows for the engine (H0's order: system-database rows, then a relaunch). The

- **Nothing of replayd.** The approval is asked before the engine observes anything. A capture that fails after the

- **An approval answered by the harness**, the way `verify.mjs --bind` answers one. The script is that client, so it
